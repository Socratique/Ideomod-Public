## [2026-10-22c] Hollowstone takes full blocks only; frames carry no redstone; Track indicator

Found while testing in the Ideomod test world.

### Hollowstone: full blocks only

Right-clicking empty Hollowstone with a button (or lever, torch, slab, any
non-full block) put it inside, where it floated in the middle. `HollowstoneBlock.use`
now also requires the block's collision shape to be a full cube.
GameTest: `hollowstoneTakesOnlyFullBlocks` (button refused, glowstone taken).

### Iron and Copper Frames don't carry redstone

Frames are see-through like glass but used the default "redstone conductor"
rule, so a powered frame powered what was behind it (and a Pulser touching a
frame could fire a piston on the far side). Both frames now set
`isRedstoneConductor` to false. Framed Blocks are unchanged: they already take
this from their inner block. The Machine Frame (a solid machine block) still
conducts. GameTest: `framesDoNotCarryRedstone` (a repeater into each frame must
not light the lamp behind; control lane with stone must).

### Machine Track: grey indicator

The Track now has the same two-layer model as the redstone machines: a 4x4
window in the middle of `machine_track.png` over the shared `machine_indicator`
texture, tinted GREY by the Track's POWER (dark 0x303030 at 0 to 0xE0E0E0 at 15,
`ModColorHandlers.TRACK_GREYS`). Grey, not red, because Track power is the
Track's own signal and invisible to vanilla redstone. Since Track power drops by
1 per Track, a pulse shows fading along the line.

## [2026-10-22b] Known Issues: GameTests, Conductor/Dust Fix, Pulse Jump Fix

Worked through the Known Issues list (Beta Release ToDo, 2026-04-07) with
in-world GameTests, so each one is reproduced before it is fixed and stays
checked afterwards.

### GameTests

New `gametest/IdeomodGameTests.java` (6 tests) and an empty 7x5x7 template
(`data/ideomod/structures/empty.nbt`) that each test builds its own setup in.
Run them with `./gradlew runGameTestServer`: a headless server places the
blocks, ticks the world, prints "All N required tests passed" and exits 0, or
names each failure and exits 1. CI now runs them on every push. They only run
when the gametest namespace is enabled, never in a normal game.
Set `-Dideomod.gametest.trace=true` on the run to log the pulse ring tick by tick.

### Known Issue #3 fixed: dust read a Conductor's power through a solid block

[redstone block] [Conductor] [stone] [dust] left the dust at power 15. Vanilla
dust never reads other dust through a block: while dust works out its power it
switches every dust's strong power off (RedStoneWireBlock.shouldSignal). The
Conductor is a different class, so that switch never reached it.

Fix: `RedStoneWireBlockMixin` wraps `calculateTargetStrength()` and sets
`MachineConductorBlock.setDustScanning(true/false)`; the Conductor's
`getDirectSignal()` returns 0 inside that window. Unchanged: a Conductor still
strongly powers the block it outputs into (lamps, pistons, repeaters work through
it), and dust touching a Conductor is still powered.

### Known Issue #4: verified, not a bug

`FramedBlock.getSignal/getDirectSignal` delegate to the inner block regardless of
ACTIVE, so frame activation can't change the output. The test places a Framed
Redstone Block through the real item path: the lamp beside it lights at once and
stays lit after a Machine Brace activates the frame.

### Known Issue #6 fixed: pulse jump when a piston moves a Pulser ring

A ring of 8 Pulsers with one pulse circulating, shoved sideways by a piston: at
three of four timings the pulse carried on cleanly, but with the piston at tick 8
five Pulsers fired in the same tick. Cause: after a move, `onMovementRestored`
scheduled a tick for EVERY machine block, idle ones included. `tick()` turns an
unpowered block on whenever its input is lit (the 2026-03-31e recovery scan), so
the idle Pulsers woke together and each one lit the next within the tick.

Fix: `saveMovementData()` records whether the block had a scheduled tick waiting
(`MovementPendingTick`); `onMovementRestored()` re-schedules only blocks that are
POWERED (mid-countdown) or had a tick pending. Idle blocks hear about lit
neighbours through `neighborChanged()` edge detection like any other block. The
2026-03-31d/e cases (a receiver waiting to turn on, a sender mid-pulse) are both
pending-tick or powered, so they still resume. The test moves the ring at ticks
8, 9, 10 and 11 (every phase of the 2-tick pulse); all pass.

### Known Issue #1: already fixed

The config reload is wired: `/ideomod reload` (op level 2) calls
`IdeomodConfig.reloadConfig()`. Marked fixed in the table.

## [2026-04-19] Frame Family Simplification, Audit Cleanup, Oddstone Silk Touch Fix

### Oddstone silk touch drop fix

Mining Oddstone with a Silk Touch pickaxe now drops Cobbled Oddstone, matching
the design doc inverse-of-stone behavior. Previously the loot table dropped
`ideomod:oddstone` unconditionally with no silk-touch branch.

Fix: replaced the flat single-entry pool in `oddstone.json` loot table with a
`minecraft:alternatives` entry. Silk Touch (level >= 1) drops cobbled_oddstone;
otherwise drops raw oddstone. Smelting in a furnace still converts raw to
cobbled (the other half of the inverted-stone pair).

Files modified:
- `src/main/resources/data/ideomod/loot_tables/blocks/oddstone.json`

### Vanilla iron_block / copper_block removed from Frame Family

Previously: vanilla iron_block and copper_block participated in Frame Family
activation networks and piston sticky groups. They had no ACTIVE blockstate --
activation was tracked in an ephemeral `Set<Long>` of packed positions. When
connected to a machine source, they conducted frame signal for their material
and formed sticky connections with same-material active frame members.

Problem: the feature added substantial code complexity (parallel activation
tracking, per-network remove-then-add to avoid network-overlap wipes, BFS
extensions in resolver and scan helpers, bidirectional vanilla-metal walker
in the resolver) for a behavior that had **no visual indication**. A vanilla
iron_block adjacent to an iron frame looked identical to one not adjacent --
players could not tell from appearance whether a given vanilla metal was
currently part of a frame network or sticky group.

Removed:
- `FrameActivation.activatedVanillaMetals` set and `isVanillaMetalActivated()`
  query.
- `FrameActivation.isActivatedConductor()` vanilla-metal branch. Now returns
  true only for active IFrameBlocks.
- `FrameActivation.recalculate()` vanilla-metal wipe/apply steps.
- `FrameActivation.isConductor()` vanilla-metal branch -- networks only
  propagate through IFrameBlock members now.
- `FrameActivation.getConductiveMaterials()` raw-metal branch.
- `FrameBlock.canStickTo()` vanilla metal same-material check.
- `FramedBlock.canStickTo()` vanilla metal branch.
- `MovementScanHelper.scanStickyGroup()` vanilla metal adjacency and expansion
  checks. Deleted `isVanillaMetalConnection()` helper entirely.
- `PistonStructureResolverMixin.ideomod$addVanillaMetalConductors()` +
  helpers `ideomod$isVanillaMetalStickyNeighbor()`,
  `ideomod$shouldVanillaMetalStick()`, `ideomod$shouldVanillaMetalGrabNeighbor()`.
- `PistonBaseBlockMixin.scanSympathetic()` and
  `PistonBaseBlockClientMixin.ideomod$captureSympathetic()`
  `FrameMaterial.fromVanillaBlock()` fallbacks.
- `FrameMaterial.isVanillaConductor()` (zero callers after above removals).

Behavior changes visible to players:
- Chains like frame -- iron_block -- iron_block -- frame no longer form a
  single sticky group. Pistons treat vanilla iron_block as any other
  non-sticky mineral block.
- Vanilla iron_block adjacent to a Machine Block does not transmit frame
  activation. Machine-frame networks no longer extend through raw metals.
- Existing worlds: any saved vanilla-metal activation state is silently
  dropped at load (the `activatedVanillaMetals` set was ephemeral, never
  serialized).
- iron_block / copper_block remain framable into iron_framed_block /
  copper_framed_block as before.

### Cross-frame mediation removed (INNER_CONDUCTOR property deleted)

Previously: framed blocks tracked their inner block's vanilla-metal material
in the `INNER_CONDUCTOR` IntegerProperty (0=none, 1=IRON, 2=COPPER). When
active, a framed block with a non-matching INNER_CONDUCTOR acted as a
MEDIATOR -- it conducted ALL materials in `FrameActivation` and stuck to
frames matching either its frame material or its inner conductor material.
Example: a copper-framed iron_block bridged iron and copper frame networks
and stuck to both iron and copper frames.

Same complaint as the vanilla metal feature: complex behavior with no clean
visual signal. The framed block does show its inner block, but the rule
"this framed copper acts like both copper and iron" required players to
remember which inners were vanilla metals AND mentally cross-reference the
two materials.

Removed:
- `FramedBlock.INNER_CONDUCTOR` IntegerProperty (declaration, default-state
  setup, state-definition builder entry, placement-time population in
  `getStateForPlacement`).
- `FramedBlockEntity.updateBlockstateFromInner` no longer writes
  INNER_CONDUCTOR.
- `FramedBlock.canStickTo` -- removed cross-frame mediation branches.
  Framed blocks now stick to frame family only when frame materials match
  exactly (and both ACTIVE).
- `FrameBlock.canStickTo` -- removed cross-frame mediation branch reading
  INNER_CONDUCTOR.
- `FrameActivation.isMediator()` -- entire method deleted.
- `FrameActivation.getConductiveMaterials()` -- simplified to return only
  the frame's own material; no longer adds inner conductor material.
- `FrameActivation.propagateSignal` -- mediators no longer pass ALL
  materials; outgoing materials = block's own materials only.
- `PistonStructureResolverMixin.ideomod$wouldFrameStickinessAllow` --
  simplified to same-frame-material match only.
- `FrameMaterial.toConductorValue()` and `fromConductorValue()` -- zero
  callers after above removals.

Blockstate count for framed blocks: was 2 (ACTIVE) x 6 (FACING) x 5
(INNER_STICKY) x 3 (INNER_CONDUCTOR) x 16 (INNER_LIGHT) = 2880 per type.
Now 2 x 6 x 5 x 16 = 960 per type. Two-thirds smaller blockstate registry.

Behavior changes visible to players:
- Iron frames stick to iron frames only (when both ACTIVE). Copper frames
  to copper only. No more bridging via copper-framed-iron or
  iron-framed-copper.
- A framed block that contains a vanilla iron/copper inner is now an
  ordinary same-material framed block. No special routing role.
- Existing worlds with saved framed blocks: blockstate values for
  INNER_CONDUCTOR (1 or 2) silently coerce to the new state def's defaults
  on chunk load. The block entity NBT (which holds the actual inner
  block ID) is unaffected, so framed blocks continue rendering and
  behaving correctly.

Retained:
- `FrameMaterial.fromVanillaBlock()` -- still used by `FramedBlockRecipe`
  to reject same-material crafting (iron frame + iron_block, copper frame
  + copper_block remain non-craftable as redundant combinations).
- `frameable_blocks` tag entries for iron_block / copper_block.

### OddstoneConfig deleted

Deleted `config/OddstoneConfig.java`. The class had been marked @Deprecated
with a "safe to delete" note but still contained full JSON file I/O, a
synchronized lock, and mutable static state. Zero call sites in the source

### Furnace array frame tag consolidated

`FurnaceArrayDefinition` defined its own `FRAME_TAG` TagKey pointing at
`ideomod:furnace_array_frame`, duplicating `ModTags.FURNACE_ARRAY_FRAME`
(which had zero references). Two TagKey objects for the same resource --
hash-equal but separate instances. Now a single source of truth in
`ModTags.FURNACE_ARRAY_FRAME`. Removed unused `BlockTags` / `TagKey<Block>`
/ `Block` / `StructureManager` imports.

## [2026-04-05] Machine Transmitter, Machine Grabber, Piston Settlement, Spec Item Lifecycle

### Machine Transmitter -- Wireless Redstone

New Machine Family specialization: wireless redstone link via Oddstone channels.
Specialization item: any Oddstone variant (oddstone, cobbled_oddstone, oddstone_bricks,
etc.). The specific variant determines the wireless channel.

Two mutually exclusive modes:
- SOURCE (POWERED=true, SOURCE=true): Receiving external redstone, broadcasts
  wirelessly to matching-channel transmitters in range. Does NOT output redstone.
  Activation is IMMEDIATE in neighborChanged (no tick delay) so even 1-tick pulses
  are captured and transmitted.
- RECEIVER (POWERED=true, SOURCE=false): Receiving wireless signal from a source,
  outputs redstone at (sourceStrength - 1) on all faces, simulating signal
  attenuation. Does NOT accept external input. Does NOT re-broadcast (no chaining).

Anti-feedback architecture (5 layers):
1. SOURCE blockstate enforces mode exclusivity (sources don't output, receivers
   don't read external)
2. shouldSignal ThreadLocal<BlockPos> for self-read suppression through solid blocks
3. updatingPos ThreadLocal<BlockPos> for re-entrant protection during setBlock
4. Receiver self-read guard in tick() -- receivers never call getExternalSignalStrength
   (would read own output back through dust, flip to SOURCE, collapse circuit)
5. Source power-off ordering -- receivers turned off BEFORE source notifies own
   neighbors, preventing stale feedback through dust

Channel system: channel = registry name of oddstone item in spec slot. Matching is
exact string equality. Range is cubic (config sympathetic_radius, default 5).

Level-aware indicator tint: reads transmitterSignalStrength from BE (not blockstate),
returns POWER_COLORS[0-15] gradient. Avoids bloating blockstate JSON from 4 to 64
entries. Client sync via syncToClients() + onDataPacket() with requestModelDataUpdate()
for chunk re-render on strength change.

### Machine Grabber -- Toggleable Sticky Block

New Machine Family specialization: toggleable sticky block. Two variants:
- Slime Grabber (MachineType.SLIME_GRABBER, specialization item: Slime Block)
- Honey Grabber (MachineType.HONEY_GRABBER, specialization item: Honey Block)

When POWERED=false: standard Machine Family stickiness only. When POWERED=true:
additionally behaves like the corresponding vanilla sticky block (with mutual
exclusions -- slime excludes honey/odd_slime, honey excludes slime/odd_slime).

Rising-edge toggle via inputWasLow (same pattern as MachineToggleBlock). No redstone
output, so no anti-feedback architecture needed.

Visual: BESR renders inner slime/honey block through transparent outer texture.

### Piston Settlement Window

Fixed spurious toggles on Grabber and Toggle blocks during piston movement. When
blocks in a push group are placed sequentially, edge-triggered blocks may see
temporary signal drops (adjacent transmitter not placed yet) followed by rises
(transmitter lands), falsely triggering a toggle.

Fix: 1-tick pistonSettling flag in MachineFrameBlockEntity.
- onPlace with movedByPiston=true: sets pistonSettling=true, schedules 1-tick tick
- neighborChanged: returns immediately if isPistonSettling()
- tick (settlement): clears flag, re-snapshots signal state for correct edge arming

Applied to: MachineGrabberBlock, MachineToggleBlock. Field is transient (not saved
to disk).

### Spec Item Change Lifecycle

New two-phase callback system for specialization item changes:

1. AbstractMachineBlock.onSpecItemChanging(Level, BlockPos, ItemStack oldItem)
   Called BEFORE triggerSwapCheck. Allows cleanup of old state (e.g., transmitter
   turns off old-channel receivers).

2. AbstractMachineBlock.onSpecItemChanged(Level, BlockPos, ItemStack newItem)
   Called AFTER triggerSwapCheck on whatever block is at the position (covers both
   same-block and cross-block swap cases).

MachineFrameBlockEntity.setItem() rewritten to call onSpecItemChanging before
triggerSwapCheck and onSpecItemChanged after. Captures old item copy for the
pre-swap callback.

Fixes resolved:
- Receiver not updating when source's oddstone channel changes
- Newly placed transmitters not receiving from active sources
- Cross-block swap (conductor->transmitter) not notifying receivers when powered

### Receiver Signal Strength Updates

Fixed receiver output not updating when source signal strength changes while
transmitting. Root cause: the !stateChanged branch in tick() only called
updateNeighborsAt(pos.relative(dir)) for secondary/indirect neighbors but never
updateNeighborsAt(pos) for direct neighbors like dust. No setBlock call meant
direct neighbors weren't notified.

Fix: added level.updateNeighborsAt(pos, this) before the secondary neighbor updates
in the receiver's !stateChanged path.

### Receiver Self-Read Anti-Feedback

Fixed receiver signal cutting to zero randomly. Root cause: receiver in tick()
read its own output back through adjacent dust via getExternalSignalStrength(),
flipped to SOURCE (output=0), everything collapsed.

Fix: receivers skip external signal check in tick() entirely
(externalStrength = wasPowered && !wasSource ? 0 : getExternalSignalStrength).

### Hollowstone Inner Block Transit Rendering

Added hollowstone inner block capture alongside framed blocks in BlockMoveHelper's
client-side capture loop. Reads innerBlockId from HollowstoneBlockEntity, stores to
MovingFrameData with dummy facing=NORTH and innerSticky=0. The transit renderer
(PistonMovingBlockEntityRendererMixin) draws the inner block during piston animation.

- Block model/blockstate/texture/loot/lang files for all three new blocks

## [2026-03-31e] Fix Pulse Cascade Dying During Piston Movement

Fixed pulser rings "randomly" losing their cascading signal after piston
movement. The pulse would sometimes survive and sometimes die, depending
on which game tick the piston happened to fire during the 2-tick pulse.

Root cause: two interacting timing problems in the post-movement tick
scheduling.

1. TICK ORDERING: onMovementRestored scheduled ALL machine blocks' ticks
   at the same delay (1). So a POWERED pulser (mid-countdown) and its
   UNPOWERED neighbor (waiting for the signal) both ticked at delay 1.
   If the sender's tick fired first, it expired and turned off. When the
   receiver's tick fired, the sender was already off — no signal detected.
   Cascade dead.

   Fix: POWERED blocks now tick at delay 2, UNPOWERED at delay 1. This
   gives receivers a 1-tick head start to detect the sender's signal
   before the sender's countdown expires. The movedState from vanilla
   preserves POWERED=true, so the signal IS visible at the new position.

2. MISSING SCAN: When a pulser expires "clean" (input signal already gone
   at expiry time), it clears inputFace to null. After movement, the
   UNPOWERED tick() path checked inputFace — if null, it did nothing.
   A powered neighbor could be right there and the pulser would ignore it
   because it had no tracked input direction.

   Fix: Added a full face scan in tick()'s UNPOWERED path when inputFace
   is null. In normal gameplay this path is unreachable (neighborChanged
   always sets inputFace before scheduling tick), so it only activates
   after piston movement when state was lost during the move cycle.

Files modified:
- `MachineFrameBlockEntity.java` -- onMovementRestored now schedules ticks
  at delay 2 for POWERED blocks, delay 1 for UNPOWERED (staggered timing)
- `MachinePulserBlock.java` -- tick() UNPOWERED path now scans all faces
  when inputFace is null, recovering input direction after movement
- `MachineTimerBlock.java` -- same scan guard added to UNPOWERED tick path
- `MachineToggleBlock.java` -- same scan guard added to UNPOWERED tick path
  (MachineRepeaterBlock already does an unconditional scan, so no change needed)

## [2026-03-31c] Fix Retraction Save Timing — Remove Piston Head Before Resolver

Fixed a critical timing bug where spec items were deleted and pulser states
(powered, countdown, inputFace) were lost during piston retraction.

Root cause: Our mixin injects at HEAD of moveBlocks(), but vanilla removes
the piston head BEFORE creating its resolver. Our resolver's forward walk
from startPos hit the still-present piston head (which isn't pushable),
causing addBlockLine to return false, resolve() to return false, and the
entire save to be skipped. Meanwhile, vanilla (running moments later after
head removal) resolved successfully and moved the blocks — but without any
saved data. Every retraction cycle lost all block entity data.

Fix: Before creating our resolver for retraction, we now explicitly remove
the piston head block (mirroring vanilla's behavior). We don't need to
restore it because vanilla's very next line after our HEAD injection
returns will remove it anyway. If our resolver fails, we restore the head
so vanilla finds the world in the expected state.

This also supersedes [2026-03-31b] which incorrectly removed the fallback
path — the fallback was actually compensating for this timing issue. The
correct fix is to match vanilla's world preparation, not add fallbacks.

Symptoms fixed:
- Spec items deleted from machine blocks during piston retraction
- Pulsers stuck permanently in powered state after retraction
- All machine block state (inputFace, countdown, edge detection) lost

Files modified:
- `PistonBaseBlockMixin.java` -- added piston head removal before retraction
  resolver, updated Javadoc to explain timing requirement
- `PistonBaseBlockClientMixin.java` -- same fix for client-side transit
  rendering capture

Written by Claude, directed and guided by The Ideomancer.

## [2026-03-25] Machine Toggle Piston Movement Bugfix -- Latch State Preservation

Fixed a bug where moving a powered Machine Toggle via piston would reset it to OFF.
The Toggle is a latch (holds ON without continuous input), but the post-movement tick
restoration from [2026-03-24] unconditionally scheduled a re-evaluation tick for ALL
machine blocks. The Toggle's tick() treats any tick on a POWERED toggle as a "toggle OFF"
event, so the scheduled tick immediately undid the latch state.

### Root Cause

onMovementRestored() scheduled a tick for every AbstractMachineBlock after piston movement.
For signal-following blocks (Repeater, Transformer, Timer, Pulser) this is correct -- they
re-evaluate their input and settle into the right state. But the Toggle is edge-triggered:
its tick() method's POWERED branch unconditionally sets POWERED=false (it's the "toggle OFF"
handler, only meant to fire in response to a rising edge detected by neighborChanged).

Vanilla preserves the original blockstate (including POWERED=true) through the
MovingPistonBlockEntity's movedState field. So the blockstate was correct after placement,
but the tick immediately turned it off again.

### Changes

**MachineFrameBlockEntity.java**:
- New `movementPowered` transient field + `TAG_MOVEMENT_POWERED` constant
- `saveMovementData()` now captures the block's powered state via `getRedstoneOutput() > 0`
- `loadMovementData()` restores `movementPowered` from the tag
- `onMovementRestored()`:
  - For powered Toggles: restores POWERED=true + INPUT_FACE blockstate as safety net,
    and SKIPS scheduling a tick (latch holds -- no re-evaluation needed)
  - For all other machine blocks: schedules tick as before

### Why Only Toggle Is Affected

The other 4 tick-based machine blocks (Repeater, Transformer, Timer, Pulser) are all
signal-following -- they're ON when input signal is present, OFF when it's gone. Their
tick() methods correctly re-evaluate the current signal and settle into the right state.
The Toggle is the only latch in the Machine Family: its ON state persists independently
of input signal. The tick's POWERED branch is a "toggle OFF" handler, not a re-evaluation.

## [2026-03-24] Machine Pulser Specialization + Observer Tick Fix + Piston Movement Tick Restoration

New Machine Family specialization: Machine Pulser. Rising-edge-triggered fixed-duration
pulse generator. Converts any incoming signal edge into a clean, config-driven pulse
(default 2 game ticks). Specialization item: any vanilla button (tag-based:
`ideomod:pulser_items`, 13 button types).

Also: fixed observer compatibility bug across all 5 tick-based machine blocks, and added
piston movement tick restoration via new IPistonMovable.onMovementRestored() callback.

### Machine Pulser -- Behaviour

- Specialization item: Any vanilla button (tag: `ideomod:pulser_items`)
- MachineType.PULSER, shares MachineFrameBlockEntity
- Blockstate: POWERED (boolean)
- Output: strength 15 on all non-input faces while pulse is active
- Edge-triggered: same rising-edge-only pattern as Toggle/Timer
- Duration: fixed from config (`pulser.pulse_duration`, default 2 game ticks, range 1-100)
- No GUI controls beyond specialization slot (unlike Timer's duration buttons)
- Tag-based specialization: FIRST machine to use item tag instead of single Items.XXX constant

### Observer Tick Priority Fix

All 5 tick-based machine blocks (Repeater, Transformer, Toggle, Timer, Pulser) now use
TickPriority.HIGH for scheduleTick calls in neighborChanged. Previously used default
NORMAL priority, causing a race condition with observer 2-tick pulses: the observer's
turn-off tick ran before the machine's response tick (FIFO within same priority),
so the machine read zero signal. Matches vanilla DiodeBlock approach.

### Piston Movement Tick Restoration

New IPistonMovable.onMovementRestored(Level, BlockPos) callback, called by
PistonMovingBlockEntityMixin after loadMovementData() restores block entity data.
MachineFrameBlockEntity implementation schedules a 1-tick re-evaluation for any
AbstractMachineBlock, ensuring powered blocks resume their countdowns after piston
movement (scheduled ticks are lost during transit).

### Known Issue: Pulse Jump on Piston Movement

When multiple edge-triggered machine blocks form a signal chain (e.g., a ring of
Pulsers with a pulse circulating), moving the group by piston can cause the active
pulse to "jump" forward, instantly powering several blocks ahead of where it should
be. Root cause: onMovementRestored schedules ticks for ALL machine blocks (not just
powered ones), and loadMovementData overwrites onPlace's absorption state, restoring
inputWasLow=true on unpowered-but-armed blocks. These blocks then see adjacent
still-powered blocks as new rising edges and fire prematurely. See Known Issue #6
in documentation. Not game-breaking; only affects moving signal chains.

## [2026-03-22b] Machine Timer Specialization + Fixed GUI Height + Button Spritesheet Expansion

Also: expanded numbered button spritesheet from 64 to 128 buttons. Fixed all

needing runtime Slot.y modification (final in Forge 1.20.1). Added timer config

### Machine Timer -- Behaviour

- Specialization item: Vanilla Clock (Items.CLOCK)
- MachineType.TIMER, shares MachineFrameBlockEntity
- Blockstate: POWERED (boolean)
- Output: strength 15 on all non-input faces while timer is running
- Edge-triggered: same rising-edge-only pattern as Toggle. Signal must
  drop to 0 and the timer must have expired before re-triggering.
- Duration: player-configurable via GUI buttons. 16 presets from config
  (default: 5,10,15,20,25,30,35,40,45,50,55,60,65,70,75,80 ticks).
- Countdown: self-rescheduling tick loop. Each game tick decrements
  timerTicksRemaining. When it reaches 0, POWERED -> false.

### Machine Timer -- Edge Detection

Same pattern as MachineToggleBlock. Uses inputWasLow in MachineFrameBlockEntity.

Timer cycle:
1. Signal arrives on face X -> inputFace=X, start timer, POWERED=true,
   inputWasLow=false
2. Timer counts down each tick
3. Timer expires -> POWERED=false
4. If signal still present, absorbed (inputWasLow=false, needs drop+rise)
5. Signal drops -> inputWasLow=true (armed)
6. Signal rises -> can fire again (new timer starts)

While the timer is running, input signal changes are tracked for arming
but don't affect the countdown — the timer always runs to completion.

### Machine Timer -- Anti-Feedback Architecture

Same 5-layer architecture as Repeater/Transformer:
1. getSignal/getDirectSignal: return 0 toward input face, 15 on others.
   shouldSignal ThreadLocal suppresses self-reads through solid blocks.
2. neighborChanged output-face early-return when POWERED.
3. Protected inputFace: only modified in tick() when powered.
4. updatingPos ThreadLocal blocks re-entrant neighborChanged during setBlock.
5. absorbing ThreadLocal guards onPlace signal snapshot.

Input face stored in MachineFrameBlockEntity (not blockstate — Timer has
no directional model variants, unlike Toggle's INPUT_FACE property).

### Machine Timer -- GUI

"Pulse Tick Duration" label centered above 16 buttons in 2 rows (8+8).
Each button shows the tick value from the config's timer.durations array.

    "default_index": 3

Durations array is fully configurable. default_index selects which preset

## [2026-03-21b] Machine Toggle Specialization + Vanilla-Style Color Ramp

New Machine Family specialization: Machine Toggle. Omnidirectional flip-flop /
T-latch that toggles between ON and OFF on each rising edge of its input signal.
Specialization item: Lever.

Also updated: indicator color ramp across all Machine Family redstone
specializations from pure black (0x000000) at power 0 to vanilla-style dark
maroon, matching RedStoneWireBlock's feel. Greyscale shading in indicator
textures now renders as dark red gradations when unpowered.

### Machine Toggle -- Behaviour

- Specialization item: Vanilla Lever (Items.LEVER)
- MachineType.TOGGLE, shares MachineFrameBlockEntity
- Blockstate: POWERED (boolean) + INPUT_FACE (EnumProperty: none/north/south/
  east/west/up/down)
- Output: always strength 15 on all non-input faces when POWERED
- Edge-triggered: only responds to rising edges (signal going from 0 to >0)
- No GUI controls beyond the specialization slot

### Machine Toggle -- Edge Detection

The Toggle tracks whether the input signal has been "seen low" since the last
state change. This prevents static signals from triggering unwanted toggles.

Toggle cycle:
1. Signal arrives on face X -> inputFace=X, POWERED=true, inputWasLow=false
2. Signal drops to 0 -> inputWasLow=true (block stays ON, armed for next edge)
3. Signal rises again on face X -> POWERED=false (toggle OFF)
4. After toggle-off, if signal is still present, it's absorbed (inputWasLow=false)
5. Different face gets signal while OFF -> new input face, cycle restarts

inputWasLow stored in MachineFrameBlockEntity. Persists through saves and
piston movement via IPistonMovable.

### Machine Toggle -- Placement Signal Absorption

When placed next to an already-active signal source, the Toggle does NOT
immediately turn on. Instead, it snapshots the current signal landscape in
onPlace() and treats it as pre-existing:
- Sets inputFace to strongest signal face
- Sets inputWasLow = false (haven't seen it drop yet)
- Stays OFF
- absorbing ThreadLocal prevents neighborChanged from scheduling a turn-on tick

The signal must drop and rise again before the Toggle will respond. This
prevents unwanted activation when building binary counters or placing toggles
near active redstone.

### Machine Toggle -- Anti-Feedback Architecture

Simplified from Repeater (no delay complication):
1. getSignal/getDirectSignal: return 0 toward input face, 15 on others.
   INPUT_FACE read from blockstate (not BE) for BlockGetter compatibility.
2. neighborChanged output-face early-return when POWERED.
3. shouldSignal ThreadLocal for solid-block self-read suppression.
4. updatingPos ThreadLocal for re-entrant protection during setBlock.
5. Tick scheduling: 2 game ticks (1 redstone tick) for all state changes.

### Machine Toggle -- Visual System

## [2026-03-21] Machine Repeater Specialization + Networking + Numbered Button Spritesheet

New Machine Family specialization: Machine Repeater. Omnidirectional redstone
repeater that receives signal on one face, outputs full-strength 15 on all
other faces with configurable delay (1-4 redstone ticks). First specialization
requiring custom networking (Forge SimpleChannel) and GUI buttons.

Also added: numbered button spritesheet (1-64) and deploy script convention doc.

### Machine Repeater -- Behaviour

- Specialization item: Vanilla Repeater (Items.REPEATER)
- MachineType.REPEATER, shares MachineFrameBlockEntity
- Blockstate: POWERED (boolean) + DELAY (IntegerProperty 1-4)
- Output: always strength 15 on all non-input faces when POWERED
- Delay: 1-4 redstone ticks (2-8 game ticks). Default 1. Set via GUI buttons.
- No locking (three-axis makes locking impractical)
- Input face model: same as Conductor -- strongest incoming signal wins

### Machine Repeater -- Anti-Feedback Architecture

The Repeater required a fundamentally different anti-feedback approach from the
Conductor (which uses shouldSignal ThreadLocal + variable power decay). The
Repeater always outputs 15, meaning any feedback path is full-strength and
self-sustaining. Seven iterations were needed to reach a stable design.

Final architecture (derived from vanilla DiodeBlock analysis):

1. **getSignal/getDirectSignal**: return 0 toward input face (direction ==
   inputFace.getOpposite()), 15 on all other faces. shouldSignal ThreadLocal
   suppresses self-reads through solid blocks during scan.

2. **neighborChanged output-face early-return**: when POWERED and the update
   comes from a non-input face, return immediately. This is the omnidirectional
   equivalent of vanilla DiodeBlock only reading from FACING.

3. **Protected inputFace**: neighborChanged NEVER modifies inputFace when
   powered. Only tick() does. Prevents intermediate dust states (power=0 during
   vanilla recalculation) from corrupting inputFace to null.

4. **Input-face-first tick**: when powered, tick() checks only the current
   input face. Does NOT full-scan (output-face dust has POWER=15 from us,
   creating false positive signal 14). Only does full scan when unpowered.

5. **setBlock flag 3**: tick() uses UPDATE_NEIGHBORS | UPDATE_CLIENTS so
   adjacent blocks learn about our state change. No manual updateNeighborsAt
   calls except in onRemove.

6. **updatingPos ThreadLocal**: during tick()'s setBlock, blocks re-entrant
   neighborChanged at THIS position only. Adjacent repeaters at different
   positions still receive their updates normally.

### Challenges Resolved (7 iterations)

1. **Cascading neighbor updates (v1-v3)**: neighborChanged or onPlace calling
   updateNeighborsAt triggered infinite cascading through adjacent dust. Fix:
   removed all manual updateNeighborsAt except onRemove. Let setBlock flag 3
   handle propagation.

2. **inputFace corruption (v3-v4)**: scanAllFaces during neighborChanged read
   dust at intermediate power=0 during vanilla recalculation, setting inputFace
   to null. This disabled both the getSignal suppression and the output-face
   early-return guard. Fix: never modify inputFace in neighborChanged when
   powered.

3. **setBlock flag 2 vs 3 (v4-v6)**: flag 2 (UPDATE_CLIENTS only) doesn't
   fire neighborChanged on adjacent blocks. Dust never learned about our state
   change. Fix: use flag 3 (UPDATE_NEIGHBORS | UPDATE_CLIENTS).

4. **getSignal direction convention (v5)**: Incorrectly flipped the input
   face suppression from inputFace.getOpposite() to inputFace. Caused output
   on input face and suppression on output faces. Fix: reverted to the correct
   Conductor convention (inputFace.getOpposite()).

5. **Output-face dust false positives (v6-v7)**: when powered and outputting 15
   to adjacent dust, that dust had POWER=15. Full rescan in tick() read this
   as signal 14 and jumped inputFace to the output face. Fix: when powered,
   tick() only checks the current input face, not all 6.

6. **Stale dust reads on turn-off (v6-v7)**: setBlock(POWERED=false, flag 3)
   triggered synchronous neighborChanged on output dust. Dust recalculated but
   some hadn't finished yet. Re-entrant neighborChanged on us read stale
   POWER=15 from un-recalculated dust. Fix: updatingPos ThreadLocal blocks
   re-entrant calls at our position.

7. **Global isUpdating blocking adjacent repeaters (v7)**: boolean ThreadLocal
   blocked ALL repeaters' neighborChanged, not just the one doing the update.
   Fix: changed to BlockPos ThreadLocal (updatingPos) so only the specific
   position being updated is blocked.

### Key Learning: Vanilla DiodeBlock Pattern

Vanilla repeaters prevent feedback through static geometry: they only read from
FACING (back) and only output on FACING.getOpposite() (front). Our omnidirectional
version achieves the same property dynamically: once an input face is locked,
only that face can trigger state changes. Output-face activity is completely
ignored while powered. This is the "dynamic facing" pattern -- functionally
identical to a vanilla repeater that chose its direction at runtime.

## [2026-03-15b] Issue #15 Fix & Issue #14 Status Update

### Issue #15 Fix: Vanilla metal first-push failure after frame network change [FIXED]

Root cause: activatedVanillaMetals was a global volatile Set<Long> that got entirely
replaced via atomic swap on every recalculate() call. Each recalculate() built a fresh
set containing only its own network's vanilla metals, then swapped out the global set.
When flushIfDirty() processed multiple networks in one flush cycle (which happens when
breaking a frame triggers dirty positions that span a network split), the second
recalculate() would overwrite the first's results -- wiping vanilla metals from
previously-processed networks.

Fix: Changed activatedVanillaMetals from volatile atomic-swap to ConcurrentHashMap-backed
key set with per-network remove-then-add. Each recalculate() now only removes vanilla
metal entries belonging to the network it's processing (step 2 WIPE), then adds back the
ones that should be active (step 6 APPLY). This preserves vanilla metals from unrelated
networks.

Thread safety preserved: ConcurrentHashMap.newKeySet() provides thread-safe individual
add/remove/contains. Concurrent reads from stickiness checks always see consistent
per-element state.

Key learning: Global state replaced atomically per-network is not safe when multiple
networks are processed in the same flush cycle. Per-element mutation with a thread-safe
collection is the correct pattern.

Files modified: FrameActivation.java

### Issue #14 Status Update: Framed redstone blocks don't emit power on frame activation

Status changed from OPEN to NEEDS VERIFICATION. During 2026-03-15 testing, Issue #14
appeared to work correctly (framed redstone blocks emit power on activation) with no
intentional fix applied. May have been incidentally resolved by the Cowork BFS refactors
(Audit #15) or AbstractMachineBlock extraction (Audit #13).

An attempted fix using level.updateNeighborsAt() in FrameActivation.recalculate() caused
infinite neighbor cascade loops: updateNeighborsAt triggers neighborChanged on frame
network blocks, which calls markDirty(), which re-enters recalculate() during the same
neighbor update chain. Vanilla's CollectingNeighborUpdater safety cap ("Too many chained
neighbor updates") fires but the world state is corrupted enough to loop on reload. The
attempted fix was reverted.

If Issue #14 resurfaces, the correct approach is deferred notification with re-entrancy
protection -- collect transitioned positions during recalculate(), process neighbor
notifications in the TickHandler AFTER all dirty networks are done, with a guard to
prevent the resulting markDirty() calls from re-entering the same tick's processing.

Files modified: FrameActivation.java (updateNeighborsAt added then reverted)

### Audit #14: Frame activation batching/debouncing

Replaced immediate recalculate() calls with a dirty-mark + end-of-tick processing system.
All block lifecycle hooks (onPlace, onRemove, neighborChanged) now call

recalculation per unique network. Placing 50 frame blocks now triggers 1 recalculation
instead of 50.

activation state before the tick ends. Called at HEAD of PistonStructureResolver.resolve().

## [2026-03-14] Audit Code Fixes Batch 2 (items B, K, L, P, #20)

### Audit fix B: FrameActivation.activatedVanillaMetals thread safety

The `activatedVanillaMetals` set was a plain `HashSet<Long>` that was cleared
and rebuilt in place during every `recalculate()` call. Concurrent reads from
stickiness checks on different code paths (e.g., chunk loading, Forge parallel
dispatch) could see a partially-rebuilt set.

Fix: Changed to a volatile reference with atomic swap pattern. During
recalculate(), a new set is built locally and swapped in at the end via
`activatedVanillaMetals = Collections.unmodifiableSet(newSet)`. Readers
always see a complete, consistent snapshot. The step 2 wipe no longer
mutates the shared set — vanilla metals are replaced wholesale in step 6.

File: FrameActivation.java

### Audit fix K: MovingBlockEntityData key collision risk

Keys were built as `dimension:x,y,z` using colons and commas. While vanilla
dimension names don't contain these characters, modded dimensions theoretically
could (e.g., `mymod:my:dimension`), creating ambiguous keys.

Fix: Changed delimiter to pipe `|` between dimension and coordinates, semicolons
`;` between coordinate components: `minecraft:overworld|0;64;0`. Neither pipe
nor semicolon is valid in ResourceLocation strings, so collisions are impossible.

Note: Any block entity data stored with the old format during a mid-animation
piston move will not be retrievable after updating. In practice this only
matters if a piston is mid-animation at the exact moment the mod JAR is swapped,
which is not a realistic scenario.

File: MovingBlockEntityData.java

### Audit fix L: StructureManager defensive copy during block entity iteration

`findAndScanNearbyCores()` iterated `chunk.getBlockEntities().keySet()` directly.
If a chunk's block entity map was modified during iteration (possible during
rapid block changes), a ConcurrentModificationException could occur.

Fix: Wrapped in `new HashSet<>(chunk.getBlockEntities().keySet())` before
iterating.

File: StructureManager.java

### Audit fix P: StructureDefinition ScanMode stub documentation

PROXIMITY and PROXIMITY_WALLED enum values exist but throw
UnsupportedOperationException if used. This could surprise someone who tries
to use them in a new StructureDefinition.

Fix: Added per-value javadoc on the ScanMode enum clearly stating which modes
are implemented and which will throw. No runtime behavior change.

File: StructureDefinition.java

## [2026-03-12] Machine Conductor Specialization -- Solid-Block Redstone Wire

New Machine Family specialization: Machine Conductor. Insert redstone dust into
a Machine Frame to create a solid-block redstone wire. Carries vanilla redstone
signal (0-15, decays by 1 per block) through a full solid block. Connects to
vanilla redstone components on all 6 faces. Machine Family member with stickiness
and frame activation.

### Input/Output Face Model

The Conductor receives signal on ONE face (the input face) and outputs on the
other 5 faces. Input face is determined by which face has the strongest incoming
signal. This model prevents feedback structurally -- the block never outputs
back toward its source.

Input face selection rules:
- Strongest signal across all 6 faces wins
- If current input face still has strongest signal, it stays
- If input source turns off, all faces rescanned for new input
- If no signal on any face, inputFace=null, POWER=0

Input face stored in MachineFrameBlockEntity as nullable Direction field.
Persists through saves and piston movement via IPistonMovable.

### Signal Types (source vs wire decay)

- Source blocks (levers, repeaters, redstone blocks): no decay.
  Lever(15) -> Conductor gives POWER=15.
- Wire blocks (dust, other Conductors): decay by 1.
  Dust(14) -> Conductor gives POWER=13.

Both getSignal (weak) and getDirectSignal (strong) output on all faces except
the input face. Strong power enables Conductor -> Solid Block -> Piston/Repeater
(matching vanilla dust behavior).

### Anti-Feedback Mechanisms

1. Input face suppression: getSignal and getDirectSignal return 0 when queried
   from the input face direction. Prevents direct Conductor<->wire feedback.

2. Direction convention: getSignal(state, level, pos, direction) where direction
   is FROM the querying block TO us. Suppress when
   direction == inputFace.getOpposite().

### Known Issues

1. Dust on the far side of a solid block sees Conductor's strong power (issue #12).
   Vanilla dust avoids this because all dust shares one block instance and the
   shouldSignal flag suppresses ALL dust during any dust's scan. Our Conductor is
   a different block class, so dust's shouldSignal doesn't affect us. Fix requires
   a mixin into RedStoneWireBlock to suppress our getDirectSignal during dust's
   calculateTargetStrength scan.

2. Base texture renders black (issue #13). The two-layer model JSON approach
   (base texture + tinted indicator overlay) has rendering issues. The indicator
   overlay tints correctly, but the base texture appears black. Needs investigation
   -- may require switching to a BESR approach like framed blocks use.

### Color Handler

ModColorHandlers registers block+item color handlers for tintIndex 1 (power
indicator overlay). Squared curve gradient: POWER 0 = black (0x000000),
POWER 1-15 = dim-to-bright red. Item shows unpowered (black) color.

## [2026-03-08b] Issue #8 Fix -- Track-Trolley Signal Bleed [FIXED]

Resolved the last tracked known issue: Machine Track redstone signal bleeding
through Trolleys into Machine Frames, causing unintended frame network
deactivation.

### Root cause:

Two problems combined:

1. MachineTrackBlock exposed its POWER value to vanilla's redstone system via
   isSignalSource()=true, getSignal()=POWER, getDirectSignal()=POWER. This
   meant solid blocks adjacent to a powered Track (like Trolleys) picked up
   "weak power" through vanilla's standard mechanics. A Machine Frame on the
   other side of the Trolley then saw that weak power via getBestNeighborSignal()
   and flipped into suppressor mode, emitting anti-signal into its frame network.

2. FrameActivation treated ALL Machine Family blocks identically for both
   activation and suppression. Any IMachineFamily member receiving redstone
   power would become a suppressor -- but only Machine Frames should have
   that authority.

### Fix part 1: Track redstone isolation (MachineTrackBlock.java)

isSignalSource() now returns false. getSignal() and getDirectSignal() both
return 0. Track's POWER blockstate is now purely internal bookkeeping.

Track-to-Track conduction is unaffected because calculatePower() reads
neighbor POWER values directly from the blockstate (via isRedstoneConduit
check), completely bypassing vanilla's signal query system. Tagged
REDSTONE_COMPONENTS (levers, repeaters, etc.) still feed into Tracks via
vanilla's level.getSignal() call.

Result: Track POWER cannot leak through solid blocks. Trolleys, stone, and
all other non-Track blocks see zero signal from Tracks.

### Fix part 2: Machine Frame-only suppression (FrameActivation.java)

Step 4 (activation propagation) now branches on block type:
- MachineFrameBlock: only emits activation when unpowered (existing behavior)
- All other Machine Family blocks: ALWAYS emit activation at strength 15,
  regardless of their redstone state

Step 5 (anti-signal propagation) now skips any source that is not a
MachineFrameBlock. Only Machine Frames can suppress frame networks.

This future-proofs all Machine specializations (Clock, Repeater, Pulser, etc.)
-- their redstone activity stays in their own lane and never accidentally
deactivates frame networks they're adjacent to.

### Design rule established:

- Any Machine Family block = frame activation source (always strength 15)
- Only Machine Frame = can become frame suppressor when receiving redstone
- Track POWER = private to Track network, invisible to vanilla redstone
- Machine Frame has no POWER property and is not a redstone conduit

- MachineTrackBlock.java: isSignalSource=false, getSignal=0, getDirectSignal=0
- FrameActivation.java: steps 4-5 branch on MachineFrameBlock instanceof

## [2026-03-07] Bug #10 Fix — Immovable Frame Anchor Detection (Feature 7)

Fixed bug #10: active framed blocks with immovable inners (obsidian, crying
obsidian, reinforced deepslate, bedrock-type) were not anchoring piston move
groups when positioned behind a group member in the push direction.

### Root cause analysis:

The issue was NOT in the backward walk's canStickTo logic as originally
theorized. Through diagnostic logging, the actual cause was identified:

When vanilla's backward walk (inside addBlockLine) encounters a block where
isPushable returns false, it treats it as a wall and silently stops walking
(returns true = "this line is fine, stop here"). It never makes a recursive
addBlockLine call for that position. Since Feature 5's immovable inner check
lives at HEAD of addBlockLine, it never fires for blocks the backward walk
skips. The framed obsidian was invisible to the resolver.

Sideways grabs (branching phase) worked correctly because branching calls
addBlockLine directly on the neighbor position, which DOES trigger Feature 5.

### Fix: Feature 7 — Immovable Frame Anchor Detection [IMPLEMENTED]

File: mixin/PistonStructureResolverMixin.java

Added a post-gathering anchor scan in the TAIL injection of addBranchingBlocks
(same location as Feature 3 sympathetic search and Feature 6 vanilla metal
conductors). After all blocks have been gathered into toPush, the new
ideomod$hasImmovableFrameAnchor() method scans every block in toPush and
checks all 6 neighbors for framed blocks with immovable inners that:
  1. Are NOT already in toPush (already handled by Feature 5)
  2. ARE active (inactive framed obsidian has no frame stickiness connection)
  3. Would be frame-sticky with the group member (same material, cross-frame
     mediation, or machine family adjacency)

If any such anchor is found, the resolve fails (cir.setReturnValue(false)),
preventing the group from moving. This mirrors Feature 5's behavior but
catches the case vanilla's backward walk silently skips.

### Key design constraint discovered during testing:

The immovable framed block must be ACTIVE to anchor. An inactive framed
obsidian sitting next to an active group is just inert — it has no frame
stickiness connection and should not prevent movement. Players can
intentionally deactivate framed obsidian (e.g., via machine block frame
deactivation from a different end) to disconnect it from a group.

defaultBlockState().getLightEmission(). This may have been added during a
prior behavioral delegation session without changelog entry. Issue #11
status updated to NEEDS VERIFICATION — requires in-game testing to confirm

## [2026-03-02a] Frame System Overhaul — Cross-Frame Mediation, Vanilla Metal Conductors, Signal-Based Activation

Major overhaul of the frame activation and stickiness systems. Introduces INNER_CONDUCTOR
blockstate property for cross-frame mediation, vanilla metal blocks (iron_block, copper_block)
as frame network conductors, redstone-style signal strength activation with anti-signal
suppression, and unified scanning pipelines.

### Feature 1: INNER_CONDUCTOR Blockstate Property

FramedBlock gains INNER_CONDUCTOR IntegerProperty (0=none, 1=iron, 2=copper). Exposes the
inner block's conductor material at the blockstate level, enabling cross-frame mediation
in canStickTo() without block entity access.

FramedBlockEntity.updateBlockstateFromInner() now syncs both INNER_STICKY and INNER_CONDUCTOR.
Uses FrameMaterial.fromVanillaBlock() to detect metal inners and toConductorValue() for the
mapping. Called on setInnerBlock(), onLoad(), loadMovementData(), and onPlace().

FrameMaterial gains toConductorValue()/fromConductorValue() for int<->enum conversion.
fromVanillaBlock() returns IRON for iron_block, COPPER for copper_block.

Blockstate count: 60 -> 180 per framed block type (x3 for conductor values).

Files: FramedBlock.java, FramedBlockEntity.java, FrameMaterial.java

### Feature 2: Vanilla Metal Blocks as Frame Network Conductors

Vanilla iron_block and copper_block now participate in frame activation networks and
piston sticky group scanning. They conduct for their respective material and form sticky
connections with same-material active frame family members.

Activation tracking: FrameActivation maintains ephemeral Set<Long> activatedVanillaMetals,
rebuilt every recalculate(). Public query: FrameActivation.isVanillaMetalActivated(pos).
Vanilla metals only form sticky connections when activated (connected to machine source).

PistonStructureResolverMixin: bidirectional vanilla metal scan in addVanillaMetalConductors().
Direction A: find vanilla metals adjacent to pushed frame family members. Direction B: find
frame family members adjacent to pushed vanilla metals. Loops until stable.

MovementScanHelper.scanStickyGroup(): vanilla metal connection checks alongside standard
isStickyBlock()/canStickTo(). Vanilla metals expand BFS (their neighbors get queued).
isVanillaMetalConnection() checks activation state, material match, and cross-frame mediation.

Files: FrameActivation.java, PistonStructureResolverMixin.java, MovementScanHelper.java

### Feature 3: Cross-Frame Mediation via Mediators

Framed blocks with a different-material inner conductor (e.g., copper-framed iron block)
are MEDIATORS. When activated, mediators become universal conductors that pass ALL materials,
like mini machine blocks. This enables unlimited material family hops without chain spawning.

Example: Machine -> iron frame -> iron-framed copper -> copper frame -> copper-framed iron
-> iron frame -> ... Each mediator resets available materials to ALL.

Same-material inner conductors (iron-framed iron) are NOT mediators -- they just conduct
for their single material like a normal frame.

isMediator() check: FramedBlock with INNER_CONDUCTOR != 0 and inner material != frame material.

Files: FrameActivation.java, FrameBlock.java, FramedBlock.java, PistonStructureResolverMixin.java

### Feature 4: Redstone-Style Signal Strength Activation

FrameActivation completely rewritten. Replaces flat MAX_ACTIVATION_RANGE=12 cap with
redstone-style signal strength 0-15.

Activation signal: unpowered Machine Block emits strength 15. Decays by 1 per conductor
block. Max range: 15 blocks from source. Each block records strongest signal received.

Anti-activation signal: redstone-powered Machine Block stops emitting activation, instead
emits anti-signal with strength = redstone input level. Decays by 1 per block. Binary
override: any block reached by anti-signal is deactivated regardless of activation strength.

Algorithm:
1. DISCOVER: BFS through all conductors (unchanged)
2. WIPE: Set IFrameBlocks to ACTIVE=false, clear vanilla metal activation set
3. FIND SOURCES: Find adjacent Machine Blocks (unchanged)
4. PROPAGATE ACTIVATION: BFS from unpowered machines, strength 15, decaying. Each entry
   carries available materials + strength. Mediators pass ALL materials.
5. PROPAGATE ANTI-SIGNAL: BFS from powered machines, strength = redstone level, decaying.
6. APPLY: Block activates only if activation > 0 AND anti-signal == 0.

Example: Machine -- 15 frames -- Machine(redstone=5). First 10 frames active, last 5
suppressed by anti-signal.

Signal decay prevents backward activation (same as redstone dust). No block can send a
stronger signal back to its source.

Files: FrameActivation.java

### Feature 5: Activation Required for Stickiness

Active frames no longer stick to inactive frames. Machine blocks no longer grab inactive

## [2026-03-01] Backward Walk Grab Immunity Fix — Call-Pair Toggle

Fixed a bug where sticky blocks could not grab blocks behind them in the push
axis during piston, Repulser, and Attractor moves. Oddstone couldn't hold slime
behind it, and slime couldn't hold framed blocks behind it. Sideways grabs
(branching) worked correctly — only the backward walk (chain cohesion along the
push axis) was affected.

### Root cause

Vanilla's backward walk in addBlockLine checks canStickTo in BOTH directions:
  oldState.canStickTo(blockstate) && blockstate.canStickTo(oldState)

Our @Redirect intercepted BOTH calls and applied grab immunity to each one.
When oddstone (front) walked backward to slime (behind):
  Call 1: oddstone.canStickTo(slime) -> passed
  Call 2: slime.canStickTo(oddstone) -> passed canStickTo, but then
          isGrabBlocked(slime, oddstone) hit Rule 1 (non-oddstone can't grab
          oddstone) -> BLOCKED
Since vanilla ANDs both results, the chain broke.

### The fix: call-pair toggle

Added ThreadLocal<Boolean> ideomod$firstCanStickToCall that tracks which call
in the pair we're on:

  Call 1 (first=true):  self=front block (oldState), other=behind block
    -> Grab immunity IS checked. The front block is the active grabber
       reaching backward. Example: slime reaching back to oddstone -> blocked.

  Call 2 (first=false): self=behind block, other=front block (oldState)
    -> Grab immunity is NOT checked. This is the behind block's passive
       compatibility response. Only canStickTo + directional rules apply.

The toggle flips on each call and resets to true after the pair completes
(or when Call 1 returns false, since vanilla short-circuits the &&).

### Debugging journey

First attempt removed grab immunity from the backward walk entirely.
This overcorrected — slime could then chain backward to oddstone because
Call 1 (slime->oddstone) went unchecked. The toggle approach is the correct
granularity: check grab immunity on the front block reaching back, skip it
on the behind block responding.

### Removed: isActivePuller exemption

The isActivePuller() helper method and its special-case logic in the backward
walk redirect were removed. This was a workaround for the original bug —
it exempted Odd Slime from grab immunity in the backward walk so it could
pull blocks behind it. With the toggle fix, this exemption is unnecessary:
Odd Slime's Call 1 (reaching back) passes normally, and Call 2 (behind block
responding) skips grab immunity entirely.

Removed imports: OddSlimeBlock, DirectionalBlock, ModBlocks, OddstoneBlock
(all were only used by the removed isActivePuller helper or were already unused).

## [2026-02-28c] Framed Blocks — Transit Rendering + Sympathetic Data Fixes

Resolved three framed block bugs: sympathetic retraction data loss (Priority 1),
transit rendering during BlockMoveHelper moves (visual), and sympathetic transit
rendering during piston retraction (visual). All three shared a common pattern:

### Bug Fix 1: Sympathetic retraction with machine-activated framed blocks [FIXED]

File: mixin/PistonBaseBlockMixin.java (scanSympathetic method)

Issue: When a sticky piston retracts a group containing sympathetically linked
oddstone, any framed blocks attached to the REMOTE sympathetic oddstone via
machine activation lost their inner block data. scanSympathetic() saved the
remote oddstone itself but never scanned its sticky group for additional
IPistonMovable blocks (machine frames, activated framed blocks, etc.).

Root cause: scanSympathetic() called saveBlockEntityAt() on each sympathetically
found oddstone but did NOT call scanStickyGroup() on it. The blocks attached
to the remote oddstone via stickiness were never saved, so vanilla's block
entity destruction during the move wiped their data permanently.

Fix: After saving each sympathetically found oddstone, check if it's sticky
(isStickyBlock()) and if so call scanStickyGroup() to walk and save all
attached blocks. savedPositions is shared between both methods, preventing
duplicates.

### Bug Fix 2: Framed block transit rendering — BlockMoveHelper path [FIXED]

File: block/movement/BlockMoveHelper.java (new step 2.6)

Issue: Framed blocks moved by Repulser, Attractor, or Machine Track/Trolley
had invisible inner blocks during the 2-tick sliding animation. The client-side
transit renderer (PistonMovingBlockEntityRendererMixin) reads from MovingFrameData,
but MovingFrameData was only populated by PistonBaseBlockClientMixin which hooks
into vanilla's PistonBaseBlock.moveBlocks(). BlockMoveHelper has its own movement
pipeline and never calls moveBlocks().

Fix: Added step 2.6 in BlockMoveHelper — on the client side, iterates the same
toPush list (which already includes sympathetic blocks from the resolver mixin)
and stores FrameTransitInfo in MovingFrameData for any framed blocks found.
Mirrors the capture pattern from PistonBaseBlockClientMixin.

New imports added to BlockMoveHelper: FramedBlock, FramedBlockEntity,
MovingFrameData, ResourceLocation.

### Bug Fix 3: Sympathetic transit rendering during piston retraction [FIXED]

File: mixin/client/PistonBaseBlockClientMixin.java

Issue: When a vanilla sticky piston retracts a group containing sympathetically

## [2026-02-28] Oddstone Pull Immunity, Frameability Whitelist, INNER_STICKY=4 (Oddstone)

Major session implementing Oddstone piston pull immunity, frameability whitelist
tag system, and full Framed Oddstone stickiness (INNER_STICKY=4). Five bugs
discovered and fixed during integration testing.

### Feature 1: Oddstone Piston Pull Immunity [IMPLEMENTED]

File: mixin/PistonBaseBlockMixin.java

Oddstone blocks cannot be pulled by sticky pistons. When a sticky piston
retracts, if the directly pulled block is Oddstone (real or framed with
INNER_STICKY=ODDSTONE), the piston retracts freely without pulling anything.

Implementation: ThreadLocal<BlockPos> `ideomod$pullTargetPos` stores the exact
pull position (pistonPos + direction * 2) during retraction. isPushable HEAD
inject checks: if block at pos is oddstone AND pos matches pullTargetPos,
return false. This is position-specific — only the DIRECTLY pulled block is
immune, not oddstone elsewhere in a sticky group.

Key design: if slime is stuck to oddstone and the piston pulls the slime, the
whole group moves (oddstone dragged by its own stickiness to slime, not grabbed
by piston). Only direct piston-on-oddstone retraction is blocked.

v1 had ghost piston head bug (check in moveBlocks left phantom heads). v2 used
boolean flag (too broad — blocked ALL oddstone during retraction). v3 (final)
uses position-specific BlockPos check.

### Feature 2: Frameability Whitelist Tag System [IMPLEMENTED]

File: block/frame/FrameabilityHelper.java
Tag: data/ideomod/tags/blocks/frameable_blocks.json

Replaced heuristic-based frameability checks with a tag-driven whitelist.
~290 vanilla blocks explicitly enumerated in the tag. Infested block variants
excluded (framing infested blocks would bypass the silverfish emergence
mechanic). Tag-based approach is deterministic, predictable, and easily
extensible by datapacks or other mods.

FrameabilityHelper.isFrameable() now checks: (1) block is in #ideomod:frameable_blocks
tag, (2) NOT already a FramedBlock, (3) NOT an IFrameBlock. Removed all prior
heuristic checks (full cube collision, no BE, not indestructible, etc.).

### Feature 3: INNER_STICKY=4 — Framed Oddstone [IMPLEMENTED]

Files: block/frame/FramedBlock.java, block/frame/FramedBlockEntity.java

Extended INNER_STICKY IntegerProperty range from 0-3 to 0-4. Added constant

### Bug fix 1: Portal division-by-zero in linkedTeleport [FIXED]

File: block/portal/OddstonePortalBlock.java

Issue: linkedTeleport() computed horizontal and vertical fractions by dividing
player offset by portal span (maxH - minH, maxV - minV). If a corrupted
SavedData entry produced a portal with zero span, this would divide by zero,
producing NaN coordinates and breaking teleportation.

Fix: Pre-compute hSpan and vSpan. If either is <= 0, default the fraction to

destination portal rather than crashing.

### Bug fix 2: OddstoneConfig lazy-load race condition [FIXED]

File: config/OddstoneConfig.java

Issue: loaded flag was checked without synchronization in getSympatheticRadius()
and isMobAffected(). Two threads could both see loaded == false simultaneously
and trigger concurrent loadConfig() calls, corrupting the affectedMobs set.

Fix: Double-checked locking pattern. Added private static final Object LOCK.
Made loaded volatile. Both accessor methods now use:
if (!loaded) { synchronized (LOCK) { if (!loaded) loadConfig(); } }
reloadConfig() also synchronized on LOCK. Outer check is the fast path -- once
config is loaded, zero synchronization overhead.

### Bug fix 3: FramedBlockRenderer sampleBestLight NPE [ALREADY FIXED]

File: client/render/FramedBlockRenderer.java

Issue was listed as: be.getLevel() used before null guard in sampleBestLight().
Finding: The null guard already exists (if (level == null) return fallbackLight).

ForgeRegistries.ENTITY_TYPES.getKey(mob.getType()).toString() without checking
if getKey() returned null. Unregistered entity types (from other mods) could

## [2026-02-22f] Framed Blocks — Rendering Overhaul + FACING + INNER_STICKY

Major rendering rewrite and two new blockstate properties for framed blocks.
Resolves all known framed block rendering issues and implements directional
inner sticky behavior.

### New blockstate properties: FACING + INNER_STICKY

Added two properties to FramedBlock:

1. **FACING** (DirectionProperty, 6 values): Set from player look direction on
   placement (piston-style). Transfers to inner block's orientation property
   during rendering — DirectionalBlock.FACING (6-way), HorizontalDirectionalBlock
   .FACING (4-way, vertical clamped to NORTH), RotatedPillarBlock.AXIS (logs,
   mapped FACING→axis). Also controls Framed Odd Slime's directional stickiness.

2. **INNER_STICKY** (IntegerProperty, 0-3): Synced from inner block type.
   0=none, 1=slime, 2=honey, 3=odd_slime. Computed by
   FramedBlockEntity.updateBlockstateFromInner() on setInnerBlock(), onLoad(),
   loadMovementData(), and onPlace(). Enables inner sticky behavior at the
   blockstate level without needing block entity lookups in hot paths.

Total blockstate count: 2 → 48 (ACTIVE × FACING × INNER_STICKY).

### Inner sticky behavior

Framed blocks with sticky inner blocks (slime, honey, odd slime) now preserve
their native stickiness. A Framed Slime Block grabs normal blocks like real
slime. Implementation:

- FramedBlock.isStickyBlock(): returns true when ACTIVE || INNER_STICKY > 0
- FramedBlock.canStickTo(): combines frame rules (ACTIVE-gated, same-material
  + machine family) with inner sticky rules (INNER_STICKY-gated, applies
  vanilla exclusions per type)
- Grab immunity rules 1-3 extended: Framed Slime/Honey/Odd Slime also blocked
  from grabbing Oddstone (matching real sticky behavior)
- Grab immunity rules 9-11 carve-out: when a FramedBlock's INNER_STICKY matches
  the target sticky type, grab immunity is lifted (Framed Slime CAN grab slime)

### Framed Odd Slime directional behavior

Framed Odd Slime only has inner stickiness when pushed in FACING direction.
However, frame stickiness (ACTIVE + same-material) must work in ALL directions.
A blanket directional rule would kill both, so directional gating is handled in
PistonStructureResolverMixin with a second-chance check:

- ideomod$isFramedOddSlimeDirectionallyBlocked(): checks if inner stickiness
  should be blocked by direction
- ideomod$wouldFrameStickinessAllow(): second-chance — if ACTIVE and neighbor
  is same-material frame or machine family, allow despite directional block
- ideomod$isActivePuller(): covers both real Odd Slime and Framed Odd Slime
  for backward-walk active puller exemption

No blanket directional rule registered in Ideomod.java. Rule count: 11 grab
immunity + 1 directional (real Odd Slime only).

### Rendering overhaul — renderSingleBlock approach

Replaced manual per-face quad drawing with BlockRenderDispatcher.renderSingleBlock().
This handles all model geometry natively:

- **Multi-element models**: Slime's nested cubes render correctly
- **Translucent/cutout blocks**: Glass, slime, odd slime render with proper

## [2026-02-22c] Framed Blocks — Piston Transit Flicker Fix

Resolved the dark flicker artifact during piston transit of framed blocks.
The flicker was most noticeable on vertical pushes (especially downward)
and appeared as a brief brightness pop mid-animation.

### Root cause:

The transit renderer (PistonMovingBlockEntityRendererMixin) was using a
SINGLE light value for all 6 faces of the inner block cuboid. The BESR
(FramedBlockRenderer) uses PER-FACE light sampling — each face checks
its own directional neighbor for light. The mismatch between these two
lighting models caused a visible brightness "pop" at the transition
boundaries (BESR → transit renderer → BESR).

Vertical movement was worst because the UP face (bright sky neighbor)
and DOWN face (dark ground neighbor) have the largest light difference.
When the transit renderer averaged them into a single value, the UP face
suddenly dimmed and the DOWN face suddenly brightened for the duration
of the animation. Horizontal movement was barely affected because all
side-face neighbors are at the same Y level with similar light.

### Fix:

PistonMovingBlockEntityRendererMixin now samples light PER FACE from
the face-direction neighbor, matching the BESR approach exactly. It
samples at both the source and destination positions and smoothly
interpolates based on animation progress using Mth.lerp(). At
progress=0.0 the lighting matches the BESR at the source position; at
progress=1.0 it matches the BESR at the destination. No pop at either
boundary.

### Updated files:
- mixin/client/PistonMovingBlockEntityRendererMixin.java — per-face
  light sampling with source/dest interpolation

### Diagnostic tooling:
- Added per-push diagnostic counter (DIAG_FRAMES_PER_PUSH). Set to 0
  (disabled) by default. Set to e.g. 60 to log per-frame light data
  for debugging. Resets per piston operation, not globally.
- Previous diagnostic (global counter) was broken — burned through all
  frames on first push, never logged subsequent pushes. Fixed by
  resetting when a new destPos is detected.

## [2026-02-21] Frame Blocks -- Machine-Activated Stickiness System

Implemented Iron Frame and Copper Frame blocks with activation-based stickiness
driven by adjacent Machine Blocks. Frame blocks are passive conductors analogous
to redstone dust: Machine Blocks are the signal source, and frames propagate
activation through same-material chains.

### New system: Frame Activation (redstone-style wipe-and-rebuild)

The activation system uses a "turn it off and on again" approach. When anything
changes (machine or frame placed/broken/neighbor updated), the entire connected
frame network is discovered via BFS, wiped to inactive, then rebuilt from all
adjacent Machine Block sources. This avoids incremental update race conditions
where frames in chains would see still-active neighbors and incorrectly retain
their activation state.

- FrameActivation.recalculate(level, pos): Single entry point called by all
  lifecycle hooks on both Machine Blocks and Frame Blocks.
  1. DISCOVER: BFS from change point through all connected frames (any material)
  2. WIPE: Set all frames to active=false (UPDATE_CLIENTS only)
  3. FIND SOURCES: Check all frames + change position for adjacent Machine Blocks
  4. RE-ACTIVATE: Flood-fill from each Machine Block through same-material chains
     (capped at 12 blocks per chain, matching piston push limit)

### Bugs resolved:

Bug 1 -- "item deleted on move" (onPlace timing):
Block lifecycle order during setBlock(): onPlace() fires BEFORE
newBlockEntity() creates the block entity. If onPlace() calls
MovingBlockEntityData.retrieve(), data is consumed but block entity
does not exist yet to receive it. Fix: removed all retrieval logic from
onPlace(). PistonMovingBlockEntityMixin is the sole consumer.

Bug 2 -- "client overwrites server data":
moveBlocks() runs on BOTH client and server (via triggerEvent block
events). Client-side block entities do not have synced inventory data
(container inventories are not sent to clients by default). Without a
client guard, the client's save (with empty inventory) overwrites the
server's valid save in the shared static MovingBlockEntityData map.
Fix: added if (level.isClientSide()) return; to both PistonBaseBlockMixin
and BlockMoveHelper step 2.5.

Bug 3 -- "retraction resolver fails":
PistonStructureResolver.resolve() returns false for retraction
(extending=false) with our IPistonMovable blocks. Root cause: the
resolver's internal isPushable calls use different parameters during
retraction that our HEAD mixin does not intercept the same way. Yet
vanilla's own moveBlocks succeeds because its triggerEvent pre-check
passes separately. Fix: retraction path bypasses the resolver entirely.
Instead scans the pull position directly and BFS-scans the sticky group.

### Key lessons learned:
1. Vanilla block lifecycle: setBlock() -> onPlace() -> newBlockEntity().
   Block entity does NOT exist during onPlace().
2. Static maps shared between logical sides: integrated server shares
   JVM statics between client and server threads. Client writes can
   clobber server data. Always guard with isClientSide().
3. retrieve() is destructive: ConcurrentHashMap.remove() consumes data.
   Multiple consumers = race condition. Single consumer only.
4. PistonStructureResolver behaves differently for extension vs
   retraction. Do not assume a resolver that works for push will work
   for pull.
5. Debug logging at INFO level is essential during development. Forge
   filters DEBUG by default in latest.log.

## [2026-02-18] Multiblock Structure Framework -- Phase 1 & Furnace Array

Implemented the Multiblock Structure Framework and its first structure type,
the Furnace Array. The framework provides registration-based detection,
tracking, and evaluation of multiblock structures as world data -- individual
blocks don't know they're part of a structure. The Structure Manager (SavedData)
holds all knowledge.

### Framework architecture (9 new Java files):

- **StructureDefinition.java**: Abstract base for structure type rulesets.
  Defines core blocks, frame tags, scan parameters. Subclassed per type.
- **FurnaceArrayDefinition.java**: Concrete definition for furnace arrays.
  Cores: furnace, blast_furnace, smoker. Frame tag: #ideomod:furnace_array_frame.
  Max cluster 3x2 (6 furnaces), requires open front face (air).
- **StructureScanner.java**: Directional pattern scanner. Phase 1: flood-fill
  cluster of adjacent same-type cores. Phase 2: compute frame bounds from
  cluster + facing direction. Phase 3: validate back/side/top/bottom frame
  layers + front face air openings. Normalizes bounds with Math.min/max to
  handle all facing directions (NORTH/WEST produce inverted coordinates).
  Normalizes core position to clusterMin for consistent exclusivity keying.
- **StructureResult.java**: Immutable scan output. Holds core pos, facing,
  cluster bounds, structure bounds, effector positions, frame positions,
  validity. Builder pattern for construction.
- **StructureRegistration.java**: Persistent registration entry. UUID, definition
  name, core position, last valid scan result, bounding box for chunk indexing.
  NBT serialization. Null bounds guard on load.
- **StructureManager.java**: Per-dimension SavedData. Stores all registrations,
  chunk index, type index, core exclusivity map, event-populated trackedCores
  set. Listens for block place/break events. Reactive core detection via block
  entity iteration (no chunk scanning). Query API for consuming systems.
  Debug stick notifications for register/deregister events.
- **StructureEffectHandler.java**: Interface for structure-type-specific effects.
  onFormed(), onRemoved(), onTick(), onUpdated().
- **FurnaceArrayEffect.java**: Sets custom GUI names ("Enhanced Furnace" etc.)
  on formation, clears on removal.
- **AbstractFurnaceBlockEntityMixin.java**: Injects into furnace tick to boost
  cooking speed by 50% (extra +1 progress on even ticks) when furnace is part
  of a registered furnace array. Safety clamp prevents progress from meeting or
  exceeding cookingTotalTime (vanilla uses equality check, not >=).

### Wiring files:

- **Ideomod.java**: Registers StructureManager.EventHandler on FORGE event bus
  and registers FurnaceArrayDefinition with StructureManager in commonSetup().
- **ideomod.mixins.json**: Added AbstractFurnaceBlockEntityMixin.
- **furnace_array_frame.json**: New block tag at
  data/ideomod/tags/blocks/furnace_array_frame.json. Contains 18 stone-family
  blocks (stone, cobblestone, stone_bricks, deepslate variants, etc.).
- **en_us.json**: Added Enhanced Furnace/Blast Furnace/Smoker container names
  and Structure Debug Stick item name.

### Debug tooling:

- **Structure Debug Stick**: New item (ModItems.STRUCTURE_DEBUG_STICK). Hold in
  either hand (mainhand or offhand). Color-coded chat messages appear when
  structures register (green) or deregister (red), showing structure type,
  core position, and core count. Zero overhead when nobody holds it.
- **structure_debug_stick.json**: Item model using vanilla stick texture.

### Key design decisions:

- **Reactive core detection**: Instead of scanning ~98K blocks per chunk on load
  (which froze the game), uses two complementary approaches: (1) block entity
  map iteration from nearby chunks when a frame block is placed (catches
  furnaces, typically 0-10 entries per chunk), and (2) event-populated
  trackedCores set for future non-block-entity cores. Combined with
  isRelevantForAnyDefinition() filter, most block placements skip the search
  entirely.
- **Canonical core position**: Scanner normalizes corePos to clusterMin so that
  scanning from any furnace in a cluster produces the same exclusivity key.
  Without this, each furnace registered a separate duplicate structure.
- **Bounds normalization**: Direction.relative() offsets can produce inverted
  min/max coordinates when facing NORTH or WEST (negative axis directions).
  Scanner normalizes with Math.min/max after directional calculation.
- **Cooking progress clamp**: Vanilla completes smelts via equality check
  (cookingProgress == cookingTotalTime), not >=. Mixin clamps progress to
  totalTime - 1 after boosting, so vanilla's next increment lands exactly
  on the target.

### Bugs found and fixed during testing:

1. **World load freeze**: onChunkLoaded() scanned 98K blocks per chunk.
   Hundreds of chunks loading during spawn prep = millions of lookups on
   server thread. Fix: eliminated chunk scanning entirely in favor of
   reactive block entity iteration.
2. **Duplicate structure registration**: Each furnace in a cluster registered
   its own structure because corePos differed. Fix: normalize to clusterMin.
3. **Bounds inversion**: NORTH/WEST facing structures had frameMin > frameMax,
   causing expanded bounds checks to always fail. Frame block breaks didn't
   trigger rescans. Fix: Math.min/max normalization.
4. **Infinite smelting progress**: Mixin could push cookingProgress past
   cookingTotalTime. Vanilla's equality check never passed, progress climbed
   forever, GUI arrow extended infinitely. Fix: safety clamp to totalTime - 1.
5. **Missing re-formation on block break**: Breaking a block covering a
   furnace's front face didn't trigger re-scan. Fix: added
   findAndScanNearbyCores() to block break path (cheap with BE iteration).
6. **Six messages per registration**: Debug stick showed one message per
   furnace. Same root cause as bug #2 (duplicate registrations). Fixed by
   canonical core position.

## [2026-02-15] Portal System -- Deactivation Fix, Cross-Axis Rotation, Break Effects
- Fixed critical bug: Z-axis portals randomly deactivating when blocks
  placed/broken near the frame exterior. X-axis portals less affected.
  Root cause: OddstonePortalHandler.onNeighborChanged() checked ALL
  neighbors of ALL frame Oddstone blocks, interpreting any non-frame
  neighbor (levers, redstone dust, dirt, air) as "corner broken" and
  triggering deactivation. Z-axis portals hit harder because redstone
  wiring on East/West faces caused more false-positive triggers.
- Secondary bug: power-loss check was hair-trigger. Single neighborChanged
  where hasNeighborSignal() momentarily returned false would kill portal,
  even from unrelated block updates. Caused flicker on Z-axis portals.

### Fix -- full frame re-validation (validateOrDeactivate):
- Replaced single-block deactivation logic with full frame re-validation.
  When any frame Oddstone gets neighborChanged and is adjacent to a portal:
  1. Navigate from adjacent portal block to frame structure
  2. Measure interior dimensions, derive all four corner positions
  3. Check all four corners are still valid corner blocks
  4. Walk entire frame perimeter: every Oddstone must be present AND powered
  5. Only deactivate if validation genuinely fails
- Mirrors activation path (which also validates full frame). Prevents false
  deactivation from exterior block updates or momentary signal fluctuations.

### Previous attempts that informed the fix:
- Attempt 1: isCornerPosition() -- checked if neighborPos was adjacent to
  portal block. But corners are DIAGONAL to portal blocks, not adjacent.
  Check always returned false, corners could never trigger deactivation.
- Attempt 2: isInPortalPlane() filter -- only ran check on in-plane neighbors.
  Still false-triggered because hasNeighborSignal() could return false
  during update cascades. Fundamental problem was reacting to single block's
  momentary state rather than validating the whole frame.

### New feature -- cross-axis portal rotation:
- When linked portals have different axes (X vs Z), player's yaw is rotated
  90 degrees to face through the destination portal's plane.
- Same-axis pairs: no rotation, player keeps their facing.
- X-axis to Z-axis: yaw += 90 (clockwise)
- Z-axis to X-axis: yaw -= 90 (counterclockwise)
- Uses player.teleportTo(level, x, y, z, yaw, pitch) overload with rotation.

### Break effects fix:
- Portal deactivation from corner break, power loss, or frame validation
  failure now produces same break particles and sound as when portal blocks
  cascade-break from mining a frame Oddstone.
- Changed PortalUtils.clearPortalBlocks() from level.setBlock(pos, AIR, 2)
  to level.destroyBlock(pos, false). destroyBlock handles break particles
  and the block's SoundType break sound automatically. false = no item drops.
- Removed manual SoundEvents.GLASS_BREAK from unregisterAndClear() since
  destroyBlock covers it.

### VoxelShape hitbox fix:
- Fixed portal block hitbox being 90 degrees off from rendered model.
- Swapped shape mapping in getShape(): X-axis portals (thin along X) now
  correctly use the X-pinched VoxelShape, Z-axis uses Z-pinched shape.

## [2026-02-15] Ranged Piston -- Device Destination Protection Fix
- Fixed bug where Attractor could be overwritten by blocks pulled into
  its position. Scenario: Attractor at pos 0, Oddstone at pos 1 and pos 3
  with air at pos 2. Sympathetic movement connected both Oddstones across
  the gap. The pull moved pos 3 -> 2 correctly, but also moved pos 1 -> 0,
  overwriting the Attractor block.
- Root cause: resolveAndMove() checked that the device wasn't IN the push
  list, but never checked if any block's DESTINATION was the device position.
- Fix: Added destination check loop after existing safety checks. For each
  block in toPush, computes destPos = sourcePos + pushDir. If any destination
  equals devicePos, the entire move is rejected. Mirrors how vanilla pistons
  can't push blocks into the piston base.
- Also protects Repulser from similar edge cases with sticky/sympathetic
  chains routing blocks back toward the device.

### Files changed:
- RangedPistonUtil.java: added destination safety check in resolveAndMove()

## [2026-02-14] Ranged Piston System -- Repulser & Attractor (Animation Fix)
- Repulser and Attractor blocks now animate correctly using vanilla's
  MovingPistonBlock + PistonMovingBlockEntity system. Blocks slide smoothly
  from source to destination over 2 ticks with proper texture, entity
  pushing, collision, waterlogging, and all vanilla edge-case handling.

### Sympathetic boundary fix:
- Fixed bug where Attractor couldn't pull sympathetic Oddstone at the
  boundary of scan range (e.g. Oddstone at pos 13 not joining when target
  at pos 12). Caused by resolver's pistonPos overlapping with sympathetic
  block positions.
- Fix: Virtual piston placed at devicePos (far from action). ThreadLocal
  in RangedPistonFlags stores real target position. PistonStructureResolver
  mixin redirects startPos from (devicePos + pushDir) to actual targetPos.
  Resolver walks from correct position, pistonPos can't collide.

### Animation fix (the hard one):
- Root cause: MovingPistonBlock.newBlockEntity() returns null. The client
  never creates PistonMovingBlockEntity through the normal block entity path.
  Vanilla creates it on BOTH client and server by running moveBlocks() inside
  triggerEvent(), which executes on both sides via the block event packet system.
- Our code was running movement in neighborChanged() (server-only), so the
  client never had a PistonMovingBlockEntity to render -- blocks disappeared
  for 2 ticks then popped into place at the destination.
- Fix: Repulser/Attractor now use level.blockEvent() in neighborChanged()
  and do the actual movement in triggerEvent(), matching vanilla piston
  architecture. triggerEvent runs on BOTH client and server. RangedPistonUtil
  accepts Level (not ServerLevel) so both sides execute the full resolve-
  and-move logic, creating PistonMovingBlockEntity on both sides.
- Movement logic in RangedPistonUtil closely mirrors vanilla
  PistonBaseBlock.moveBlocks(): same ordering (snapshot -> destroy -> place
  MovingPistonBlock at destinations while sources still exist -> clear
  sources -> neighbor updates -> sound), same flags (68 placement, 82 cleanup),
  same factory method (MovingPistonBlock.newMovingBlockEntity()).

### Files changed:
- OddstoneRepulserBlock.java: blockEvent + triggerEvent pattern
- OddstoneAttractorBlock.java: blockEvent + triggerEvent pattern
- RangedPistonUtil.java: rewritten to mirror vanilla moveBlocks(), accepts Level
- RangedPistonFlags.java: new -- ThreadLocal for resolver startPos redirect
- PistonStructureResolverMixin.java: added Feature 4 -- startPos redirect
- Ideomod.java: no custom entity registration needed (vanilla handles rendering)

### Key lessons -- see BLOCK_EVENT_LESSON.md for full writeup:
- Vanilla's MovingPistonBlock is a BaseEntityBlock whose newBlockEntity()
  returns null. Client-side PistonMovingBlockEntity is created by running
  moveBlocks() on the client via the block event system -- NOT via chunk sync.
- Any mod feature that places MovingPistonBlock MUST use the block event
  system (level.blockEvent -> triggerEvent on both sides) or the animation
  will be invisible.
