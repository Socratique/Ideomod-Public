# Ideomod Changelog

## [2026-02-15] Ranged Piston — Device Destination Protection Fix
- Fixed bug where Attractor could be overwritten by blocks pulled into
  its position. Scenario: Attractor at pos 0, Oddstone at pos 1 and pos 3
  with air at pos 2. Sympathetic movement connected both Oddstones across
  the gap. The pull moved pos 3 → 2 correctly, but also moved pos 1 → 0,
  overwriting the Attractor block.
- Root cause: resolveAndMove() checked that the device wasn't IN the push
  list, but never checked if any block's DESTINATION was the device position.
- Fix: Added destination check loop after existing safety checks. For each
  block in toPush, computes destPos = sourcePos + pushDir. If any destination
  equals devicePos, the entire move is rejected. Mirrors how vanilla pistons
  can't push blocks into the piston base.
- Also protects Repulser from similar edge cases with sticky/sympathetic
  chains routing blocks back toward the device.

### Files changed:
- RangedPistonUtil.java: added destination safety check in resolveAndMove()

- Repulser and Attractor blocks now animate correctly using vanilla's

### Sympathetic boundary fix:
- Fixed bug where Attractor couldn't pull sympathetic Oddstone at the
  boundary of scan range (e.g. Oddstone at pos 13 not joining when target
  at pos 12). Caused by resolver's pistonPos overlapping with sympathetic

- Root cause: MovingPistonBlock.newBlockEntity() returns null. The client
  never creates PistonMovingBlockEntity through the normal block entity path.
  Vanilla creates it on BOTH client and server by running moveBlocks() inside
  triggerEvent(), which executes on both sides via the block event packet system.
- Our code was running movement in neighborChanged() (server-only), so the
  client never had a PistonMovingBlockEntity to render â€” blocks disappeared
  for 2 ticks then popped into place at the destination.
- Fix: Repulser/Attractor now use level.blockEvent() in neighborChanged()
  and do the actual movement in triggerEvent(), matching vanilla piston
  architecture. triggerEvent runs on BOTH client and server. RangedPistonUtil
  accepts Level (not ServerLevel) so both sides execute the full resolve-
  and-move logic, creating PistonMovingBlockEntity on both sides.
- Movement logic in RangedPistonUtil closely mirrors vanilla
  PistonBaseBlock.moveBlocks(): same ordering (snapshot â†’ destroy â†’ place
  MovingPistonBlock at destinations while sources still exist â†’ clear
  sources â†’ neighbor updates), same flags (68 placement, 82 cleanup),
  same factory method (MovingPistonBlock.newMovingBlockEntity()).

## [2026-02-12] Oddstone Portals
- Added Oddstone Portal system - overworld-to-overworld teleportation
  - Frame: rectangular ring of Oddstone (minimum 5x5 outer, 3x3 interior)
    with crafted mineral blocks in all 4 corners
  - Corner Address System: the 4 corner blocks form a "frequency" / address
    - Position-sensitive: TL, TR, BR, BL order matters
    - Normalized across viewing direction (front/back produce same address)
    - 14 valid corner types: coal, iron, copper, gold, redstone, lapis,
      diamond, emerald, netherite, quartz, amethyst, raw_iron, raw_copper,
      raw_gold blocks
    - 14^4 = 38,416 possible unique addresses per dimension
  - Activation: ALL Oddstone blocks in the frame must receive redstone signal
    - Any Oddstone receiving power triggers frame detection
    - Frame detector scans from interior outward (nether portal style)
    - Validates structure, checks all Oddstone blocks are powered
    - Registers address in per-dimension saved data
    - If matching address found: portals link automatically
    - If address already has a linked pair: portal refuses to light
    - Sound: flint & steel ignition on success, fire extinguish on failure
  - Deactivation: portal clears and unregisters when:
    - Any Oddstone frame block loses redstone signal
    - Any Oddstone frame block is broken
    - Any corner block is broken
  - Linked Travel: teleports player to partner portal
    - Preserves relative position within the frame (like nether portals)
    - Position mapped as fraction (0.0-1.0) horizontally and vertically
    - Works across different-sized portals (scales proportionally)
  - Unlinked Travel: scatter teleport as penalty
    - Random direction, 200-1000 blocks distance
    - Lands on surface (heightmap) - no air drops
    - Deals 5 hearts (10 HP) magic damage
    - Portal looks identical to linked - player doesn't know until they step in
  - Per-dimension address spaces: overworld and nether store separate registries
    - Same corner code can exist as independent pairs in each dimension
    - Uses Minecraft SavedData system, persists across saves/chunk unloads
  - Portal block: light blue tinted nether portal texture
    - Axis property (X/Z) for proper visual orientation
    - Light level 11, no collision, indestructible by hand
    - Cannot be pushed by pistons
    - No item form (not placeable by hand, like nether portal blocks)
    - Color tint via block color handler (0x44DDFF cyan, reuses nether portal texture)
  - 4-second cooldown between teleports (vanilla portal cooldown system)
- New files:
  - OddstonePortalBlock.java (com.ideomancer.ideomod.block)
  - OddstonePortalFrameDetector.java (com.ideomancer.ideomod.block)
  - OddstonePortalSavedData.java (com.ideomancer.ideomod.block)
- Modified files:
  - OddstoneBlock.java - added neighborChanged for portal activation/deactivation
  - MachineBlockColor.java - added portal block color handler (light blue tint)
  - ModBlocks.java - registered ODDSTONE_PORTAL block
  - ModItems.java - note: no item form for portal block
- Assets: blockstate (X/Z axis variants), 2 block models (ew/ns thin planes),
  lang file update
- Status: Working

### Implementation fixes during development:
- Frame detection: original approach traced frame from the triggered block
  outward, which was position-dependent and fragile. Rewrote to scan from
  interior air blocks outward (nether portal style) - works from any frame
  block position.
- Corner blocks: originally used ore blocks (diamond_ore, iron_ore).
  Changed to crafted mineral blocks (diamond_block, iron_block) per design.
- Activation sound: initially used END_PORTAL_SPAWN (too loud), then
  PORTAL_TRIGGER (triggers nether teleport connotation). Settled on
  FLINTANDSTEEL_USE (matches nether portal lighting).
- Teleport: initially used handleInsidePortal() for nether-style screen
  effect, but this is hardcoded to send player to the nether. Reverted
  to instant teleport with cooldown.
- Scatter teleport: originally picked random Y level, causing air drops.
  Fixed to use heightmap for surface landing.
- Deactivation: initial approach had individual Oddstone blocks checking
  their own power state, causing newly-powered blocks to immediately
  deactivate portals lit by other frame blocks. Fixed with "all must be
  powered" rule - frame detector validates all Oddstone blocks have signal.
- Corner block breaking: portal blocks are diagonal to corners, so
  updateShape never fires on portal blocks when corner breaks. Fixed by
  detecting corner removal in OddstoneBlock.neighborChanged - Oddstone
  frame blocks adjacent to the corner DO receive the notification.
- Stale saved data: old registrations from ore-corner testing persisted
  in world save, blocking new mineral-block addresses. Clearing
  ideomod_oddstone_portals.dat from world data folder resolves this.

### Known issues / future work:
- No nether portal screen overlay effect. Adding it properly requires

- Portal has no custom particles (could add light blue particles later).
- Portal texture is recolored nether portal via tint. Could create a

## [2026-02-11] Oddstone Block
- Added OddstoneBlock - a strange stone with three unique properties
  - Mob Avoidance: all mobs refuse to pathfind over it
    - JSON config (config/ideomod/oddstone.json) lists affected mobs
    - Auto-generated on first launch with all vanilla 1.20.1 land mobs
    - Remove mobs from list to create exceptions
  - Redstone Insulation: does not conduct redstone signal
    - Behaves like glass for redstone purposes
    - Achieved via .isRedstoneConductor(false) in block properties
  - Sympathetic Movement: wireless slime block behavior
    - Each face searches outward (configurable radius, default 5) for nearest Oddstone
    - Max 6 connections per block (one per face), searches through solid blocks
    - Connected Oddstones form a group that moves together when pushed by piston
    - Sympathetic Oddstones push non-Oddstone blocks ahead of them
    - All pushed blocks count toward the 12-block piston limit
    - Exceeding 12 blocks cancels the piston push entirely
    - Obstructed sympathetic blocks (immovable block ahead) stay put
    - Chains through connected Oddstones (A grabs B, B grabs C, etc.)
- New package: com.ideomancer.ideomod.config (OddstoneConfig.java)
- New file: OddstoneMovementHandler.java (piston event listener)
- Assets: blockstate, block/item models, placeholder texture (purple-grey stone)
- Data: loot table, placeholder recipe (4 stone + 1 redstone = 4 oddstone), pickaxe tag
- Status: Working

### Implementation fixes during development:
- Mob pathfinding: Forge's getBlockPathType hook alone was not blocking mobs.
  Fixed by adding vanilla isPathfindable() override returning false (same
  approach as fences/walls). Also changed DANGER_OTHER to DAMAGE_OTHER in
  Forge hooks for stronger avoidance penalty.
- Sympathetic obstruction: initially the whole piston push would fail if ANY
  sympathetic oddstone was blocked. Changed so obstructed oddstones simply
  stay put, and only the 12-block limit causes a full piston failure.
- Sympathetic push chains: initially sympathetic oddstones could only move
  into empty spaces. Fixed so they push blocks ahead of them (like any
  piston-pushed block would), with those pushed blocks counting toward
  the 12-block limit.

### Known issues / future work:
- Sympathetic oddstone push chains don't trigger slime block stickiness.
  If a sympathetically moved oddstone pushes a slime block, blocks attached
  to that slime block don't come along. Works correctly for catalyst

  integration with PistonStructureResolver.
- Future feature: Oddstone should stick to slime blocks when the ODDSTONE
