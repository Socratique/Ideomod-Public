# Ideomod Changelog

## [2026-03-15c] Removed REDSTONE_COMPONENTS Tag (Redundant)

The REDSTONE_COMPONENTS block tag was originally created to whitelist which
vanilla redstone devices could provide signal to the old Machine Block,
preventing feedback loops (since Machine Block was itself a signal source).

This tag is now redundant for two reasons:
1. Machine Track has full redstone isolation (isSignalSource=false, getSignal=0,
   getDirectSignal=0) since 2026-03-08 (Issue #8 fix), so it cannot create
   feedback loops regardless of what feeds signal into it.
2. The Machine Conductor block now handles vanilla redstone signal propagation
   as its own specialization, with its own anti-feedback mechanism (input face
   suppression).

### Changes

**MachineTrackBlock.java**:
- Removed import of ModTags
- Removed isRedstoneComponent() helper method (was the tag check)
- calculatePower(): replaced `else if (isRedstoneComponent(nBlock))` with
  plain `else` -- any non-conduit neighbor is now queried via level.getSignal()
- scheduleAllPushes(): same change for direction detection
- Updated class javadoc explaining no-feedback reasoning
- Net result: simpler code, Tracks now accept signal from ANY vanilla source

**ModTags.java**:
- Removed REDSTONE_COMPONENTS TagKey constant and javadoc

**Deleted file**:
- data/ideomod/tags/blocks/redstone_components.json

### Documentation sync
- IDEOMOD_DOCUMENTATION.md: ModTags table (5 tags -> 4), Machine Track spec
  updated, Section 13 redstone_components subsection removed
- CODEBASE_REFERENCE.md: ModTags entry, MachineTrackBlock entry (2 locations),
  Machine Track block spec -- all updated to reflect vanilla signal query
- IDEOMOD_CHANGELOG.txt: This entry

## [2026-03-15b] Issue #15 Fix & Issue #14 Status Update

### Issue #15 Fix: Vanilla metal first-push failure after frame network change [FIXED]

Root cause: activatedVanillaMetals was a global volatile Set<Long> that got entirely
replaced via atomic swap on every recalculate() call. Each recalculate() built a fresh
set containing only its own network's vanilla metals, then swapped out the global set.
When flushIfDirty() processed multiple networks in one flush cycle (which happens when
breaking a frame triggers dirty positions that span a network split), the second
recalculate() would overwrite the first's results -- wiping vanilla metals from
previously-processed networks.

Fix: Changed activatedVanillaMetals from volatile atomic-swap to ConcurrentHashMap-backed
key set with per-network remove-then-add. Each recalculate() now only removes vanilla
metal entries belonging to the network it's processing (step 2 WIPE), then adds back the
ones that should be active (step 6 APPLY). This preserves vanilla metals from unrelated
networks.

Thread safety preserved: ConcurrentHashMap.newKeySet() provides thread-safe individual
add/remove/contains. Concurrent reads from stickiness checks always see consistent
per-element state.

Key learning: Global state replaced atomically per-network is not safe when multiple
networks are processed in the same flush cycle. Per-element mutation with a thread-safe
collection is the correct pattern.

Files modified: FrameActivation.java

### Issue #14 Status Update: Framed redstone blocks don't emit power on frame activation

Status changed from OPEN to NEEDS VERIFICATION. During 2026-03-15 testing, Issue #14
appeared to work correctly (framed redstone blocks emit power on activation) with no
intentional fix applied. May have been incidentally resolved by the Cowork BFS refactors
(Audit #15) or AbstractMachineBlock extraction (Audit #13).

An attempted fix using level.updateNeighborsAt() in FrameActivation.recalculate() caused
infinite neighbor cascade loops: updateNeighborsAt triggers neighborChanged on frame
network blocks, which calls markDirty(), which re-enters recalculate() during the same
neighbor update chain. Vanilla's CollectingNeighborUpdater safety cap ("Too many chained
neighbor updates") fires but the world state is corrupted enough to loop on reload. The
attempted fix was reverted.

If Issue #14 resurfaces, the correct approach is deferred notification with re-entrancy
protection -- collect transitioned positions during recalculate(), process neighbor
notifications in the TickHandler AFTER all dirty networks are done, with a guard to
prevent the resulting markDirty() calls from re-entering the same tick's processing.

Files modified: FrameActivation.java (updateNeighborsAt added then reverted)

## [2026-03-15] Architecture Cleanup, Performance, & Bug Fixes

### Audit #13: AbstractMachineBlock base class extraction

Extracted AbstractMachineBlock as a shared base class for all Machine Family blocks.
Default implementations cover: use() (GUI open), newBlockEntity(), getRenderShape(),
isStickyBlock(), canStickTo(), onPlace()/onRemove()/neighborChanged() (frame activation
lifecycle via markDirty()), setPlacedBy() (specialization swap on placement), getDrops(),
getCloneItemStack(). MachineFrameBlock and MachineTrolleyBlock reduced to ~20 lines each,
overriding only getMachineType(). MachineConductorBlock and MachineTrackBlock override
lifecycle hooks for their unique redstone/push behavior. New specializations are now a
~20-line task.

Files created: AbstractMachineBlock.java
Files rewritten: MachineFrameBlock.java, MachineTrolleyBlock.java,
                 MachineConductorBlock.java, MachineTrackBlock.java

### Audit #14: Frame activation batching/debouncing

Replaced immediate recalculate() calls with a dirty-mark + end-of-tick processing system.
All block lifecycle hooks (onPlace, onRemove, neighborChanged) now call
FrameActivation.markDirty(level, pos) instead of recalculate() directly. Dirty positions
are stored per-dimension in a ConcurrentHashMap<ServerLevel, Set<BlockPos>>. At end of
each server tick, FrameActivation.TickHandler (registered on Forge event bus via
TickEvent.ServerTickEvent(Phase.END)) calls processDirtyNetworks(), which discovers
connected networks from dirty positions, deduplicates overlapping positions, and runs one
recalculation per unique network. Placing 50 frame blocks now triggers 1 recalculation
instead of 50.

Added flushIfDirty(Level) for time-critical paths (piston resolution) that need fresh
activation state before the tick ends. Called at HEAD of PistonStructureResolver.resolve().

Files modified: FrameActivation.java (major rewrite), FrameBlock.java, FramedBlock.java,
                Ideomod.java, PistonStructureResolverMixin.java
Inner class created: FrameActivation.TickHandler

### Audit #15: BFS frontier queues replacing O(n^2) fixed-point loops

Replaced O(n^2) fixed-point loops with single-pass BFS in two algorithms:

ideomod$addVanillaMetalConductors() in PistonStructureResolverMixin: Seeds frontier with
initial toPush positions. Each position processed once via processed HashSet. 256-iteration
safety cap. Complexity reduced from O(n^2) to O(n).

scanSympathetic() in MovementScanHelper: Seeds frontier with oddstone blocks from start
set. Uses found.add() return value to detect new discoveries. Complexity reduced from
O(n^2) to O(n).

Files modified: PistonStructureResolverMixin.java, MovementScanHelper.java

### Bug fix: Machine Frame GUI item invisible after specialization swap

When swapping specialization items in the machine block GUI, the new item was invisible
in the slot until the GUI was reloaded. Root cause: MachineFrameBlockEntity lacked client
sync methods. When level.setBlock() fires during a swap, the client creates a new empty
BE but never receives the item data.

Fix: Implemented getUpdatePacket(), getUpdateTag(), and syncToClients() on
MachineFrameBlockEntity, with syncToClients() called after setItemDirect() in the swap
flow.

Files modified: MachineFrameBlockEntity.java, MachineSwapHelper.java

### Known Bug #15: Vanilla metal first-push failure after frame network change

(See [2026-03-15b] above for the fix.)

## [2026-03-14b] Audit Fixes: Portal Geometry Caching, InputFace Reset, Conductor Render Fix, Portal Debug Stick

### Audit fix #16: Portal geometry caching in SavedData

Portal teleportation previously called PortalGeometry.detect() twice per teleport
(once for source portal, once for destination) to determine interior dimensions.
Each detection scans the portal frame edges.

Fix: Interior geometry (bottom-left position, width, height) is now computed from
the FrameResult's corner positions during portal activation and passed directly
into OddstonePortalSavedData.registerPortal(). Cached in the PortalEntry and
persisted to NBT. Teleportation reads cached values (zero block lookups).
Falls back to live PortalGeometry.detect() for portals registered before this
update (old saves without cached geometry).

Challenge: Initial implementation tried to run PortalGeometry.detect() inside
registerPortal(), but registration happens BEFORE portal blocks are filled into
the interior. Detection needs existing portal blocks to scan from. Fixed by
computing geometry from FrameResult corner positions instead of re-scanning.

Files: OddstonePortalSavedData.java, OddstonePortalHandler.java, OddstonePortalBlock.java

### Audit fix O/#21: InputFace reset on specialization swap

The inputFace field on MachineFrameBlockEntity stores which face receives
redstone signal (used by Conductor, future Arm/Transformer). Since all Machine
Family blocks share the same block entity class, swapping specialization items
left stale directional data. E.g. Conductor facing NORTH -> swap to Track ->
swap back to Conductor -> inherits old NORTH inputFace.

Fix: Added `this.inputFace = null;` at the top of triggerSwapCheck(). Every
specialization swap starts with a clean directional slate. The new specialization
sets its own inputFace when it first receives a signal.

File: MachineFrameBlockEntity.java

### Fix Issue #13: Machine Conductor base texture renders black

Root cause identified: the indicator overlay element (tintIndex 1) extends
slightly outside the base cube (-0.05 to 16.05) and was rendering as an opaque
black shell at power 0 (POWER_COLORS[0] = 0x000000). The indicator texture has
transparency, but the model used the default "solid" render type which treats
transparent pixels as opaque black.

Fix: Added `"render_type": "minecraft:cutout"` to the model JSON. Cutout render
type discards transparent pixels, allowing the base texture to show through the
indicator overlay. Also removed unnecessary tintindex from the base layer faces.

File: assets/ideomod/models/block/machine_conductor.json

### Portal debug stick notifications

Added debug stick notifications to OddstonePortalHandler, matching the existing
pattern from StructureManager. Players holding the Structure Debug Stick now
see color-coded chat messages for portal events:

- Yellow [Portal] ACTIVATED (unlinked) — position, geometry, shortened address
- Green [Portal] ACTIVATED + LINKED — position, partner position, geometry, address
- Red [Portal] FAILED: address full — position
- Red [Portal] DEACTIVATED — position, address

Address display shortened: "minecraft:iron_block,minecraft:diamond_block,..."
becomes "iron,diamond,..." for readability.

Files: OddstonePortalHandler.java

### New Known Issue #14: Framed redstone blocks don't emit power on frame activation

When a framed redstone block is activated via the frame network, it doesn't emit
redstone power until it receives a redstone update (not a regular block/neighbor
update). Works fine if placed while frame is already inactive. Root cause: frame
activation changes block behavior but doesn't notify redstone neighbors. Fix:
FrameActivation needs to call level.updateNeighborsAt() when a framed redstone
source transitions between active/inactive states.

Location: FrameActivation.java


## [2026-03-14] Audit Code Fixes Batch 2 (items B, K, L, P, #20)

### Audit fix B: FrameActivation.activatedVanillaMetals thread safety

The `activatedVanillaMetals` set was a plain `HashSet<Long>` that was cleared
and rebuilt in place during every `recalculate()` call. Concurrent reads from
stickiness checks on different code paths (e.g., chunk loading, Forge parallel
dispatch) could see a partially-rebuilt set.

Fix: Changed to a volatile reference with atomic swap pattern. During
recalculate(), a new set is built locally and swapped in at the end via
`activatedVanillaMetals = Collections.unmodifiableSet(newSet)`. Readers
always see a complete, consistent snapshot. The step 2 wipe no longer
mutates the shared set — vanilla metals are replaced wholesale in step 6.

File: FrameActivation.java

### Audit fix K: MovingBlockEntityData key collision risk

Keys were built as `dimension:x,y,z` using colons and commas. While vanilla
dimension names don't contain these characters, modded dimensions theoretically
could (e.g., `mymod:my:dimension`), creating ambiguous keys.

Fix: Changed delimiter to pipe `|` between dimension and coordinates, semicolons
`;` between coordinate components: `minecraft:overworld|0;64;0`. Neither pipe
nor semicolon is valid in ResourceLocation strings, so collisions are impossible.

Note: Any block entity data stored with the old format during a mid-animation
piston move will not be retrievable after updating. In practice this only
matters if a piston is mid-animation at the exact moment the mod JAR is swapped,
which is not a realistic scenario.

File: MovingBlockEntityData.java

### Audit fix L: StructureManager defensive copy during block entity iteration

`findAndScanNearbyCores()` iterated `chunk.getBlockEntities().keySet()` directly.
If a chunk's block entity map was modified during iteration (possible during
rapid block changes), a ConcurrentModificationException could occur.

Fix: Wrapped in `new HashSet<>(chunk.getBlockEntities().keySet())` before
iterating.

File: StructureManager.java

### Audit fix P: StructureDefinition ScanMode stub documentation

PROXIMITY and PROXIMITY_WALLED enum values exist but throw
UnsupportedOperationException if used. This could surprise someone who tries
to use them in a new StructureDefinition.

Fix: Added per-value javadoc on the ScanMode enum clearly stating which modes
are implemented and which will throw. No runtime behavior change.

File: StructureDefinition.java

### Audit recommendation #20: Tag-based immovable inner blocks

PistonBaseBlockMixin Feature 4 (framed block inner push reaction) previously
hardcoded three specific blocks: obsidian, crying_obsidian, reinforced_deepslate.
Adding new immovable-when-framed blocks required a code change.

Fix: Created `ideomod:immovable_when_framed` block tag containing the three
previously hardcoded blocks. PistonBaseBlockMixin now checks
`innerState.is(ModTags.IMMOVABLE_WHEN_FRAMED)` instead of three separate
`.is()` calls. The destroySpeed == -1 fallback (for bedrock-type blocks)
still runs after the tag check.

Other mods and datapacks can now add blocks to the tag without code changes.

Files: ModTags.java, PistonBaseBlockMixin.java
New file: data/ideomod/tags/blocks/immovable_when_framed.json


## [2026-03-13b] Sympathetic Movement Bug Fix + Audit Code Fixes

### BUG FIX: Sympathetic movement only worked at distance 2 or exact radius

Oddstone sympathetic movement was broken for distances 3 through (radius-1).
The regression was in PistonStructureResolverMixin's sympathetic search phase.
After refactoring to use MovementScanHelper.scanSympathetic() (shared scan),
the resolver code that adds found blocks to the push list used a broken check:

  if (checkPos.equals(oddPos.relative(face, radius)) ||
      checkPos.equals(oddPos.relative(face, 2)))

This only matched oddstone at exactly the configured radius OR exactly distance
2, skipping all distances in between. The scan itself found them correctly --
they just never got added to the push list.

Fix: Replace the distance check with proper direction derivation from position
delta. New helper ideomod$getAxisDirection(from, to) extracts the cardinal
direction between two axis-aligned positions, which is passed to addBlockLine.

File: PistonStructureResolverMixin.java

## [2026-03-12] Machine Conductor Specialization -- Solid-Block Redstone Wire

New Machine Family specialization: Machine Conductor. Insert redstone dust into
a Machine Frame to create a solid-block redstone wire. Carries vanilla redstone
signal (0-15, decays by 1 per block) through a full solid block. Connects to
vanilla redstone components on all 6 faces. Machine Family member with stickiness
and frame activation.

### Input/Output Face Model

The Conductor receives signal on ONE face (the input face) and outputs on the
other 5 faces. Input face is determined by which face has the strongest incoming
signal. This model prevents feedback structurally -- the block never outputs
back toward its source.

Input face selection rules:
- Strongest signal across all 6 faces wins
- If current input face still has strongest signal, it stays
- If input source turns off, all faces rescanned for new input
- If no signal on any face, inputFace=null, POWER=0

Input face stored in MachineFrameBlockEntity as nullable Direction field.
Persists through saves and piston movement via IPistonMovable.

### Signal Types (source vs wire decay)

- Source blocks (levers, repeaters, redstone blocks): no decay.
  Lever(15) -> Conductor gives POWER=15.
- Wire blocks (dust, other Conductors): decay by 1.
  Dust(14) -> Conductor gives POWER=13.

Both getSignal (weak) and getDirectSignal (strong) output on all faces except
the input face. Strong power enables Conductor -> Solid Block -> Piston/Repeater
(matching vanilla dust behavior).

### Anti-Feedback Mechanisms

1. Input face suppression: getSignal and getDirectSignal return 0 when queried
   from the input face direction. Prevents direct Conductor<->wire feedback.

2. Direction convention: getSignal(state, level, pos, direction) where direction
   is FROM the querying block TO us. Suppress when
   direction == inputFace.getOpposite().

### Known Issues

1. Dust on the far side of a solid block sees Conductor's strong power (issue #12).
   Vanilla dust avoids this because all dust shares one block instance and the
   shouldSignal flag suppresses ALL dust during any dust's scan. Our Conductor is
   a different block class, so dust's shouldSignal doesn't affect us. Fix requires
   a mixin into RedStoneWireBlock to suppress our getDirectSignal during dust's
   calculateTargetStrength scan.

2. Base texture renders black (issue #13). The two-layer model JSON approach
   (base texture + tinted indicator overlay) has rendering issues. The indicator
   overlay tints correctly, but the base texture appears black. Needs investigation
   -- may require switching to a BESR approach like framed blocks use.

### Color Handler

ModColorHandlers registers block+item color handlers for tintIndex 1 (power
indicator overlay). Squared curve gradient: POWER 0 = black (0x000000),
POWER 1-15 = dim-to-bright red. Item shows unpowered (black) color.

## [2026-03-09] Machine Specialization System -- Universal Block Swap + Type-Aware Stickiness

Major rework of the Machine Family system. Every specialization is now its own
registered block with a shared block entity, GUI, and specialization swap logic.
The Machine Frame is the universal connector; specializations only stick to their
own type + Machine Frames + Frame Family.

### New architecture: Specialization as distinct blocks with shared block entity

All Machine Family blocks (Machine Frame, Machine Track, Machine Trolley, and
future specializations) share MachineFrameBlockEntity -- a single-slot container
that stores the specialization item. Each specialization is a unique registered
block implementing EntityBlock and IMachineFamily with a MachineType.

  FRAME is the universal connector. canStickToMachineType() encodes the rule.
- MachineSwapHelper.java: Central swap utility. Item<->Block registry,

- ModBlocks.java: pushReaction(NORMAL) on Track and Trolley.
- ModCreativeTabs.java: Pre-loaded stacks for specializations.
- Ideomod.java: MachineSwapHelper.registerMappings() call.

### Specialization item mapping (currently implemented):
  Powered Rail -> Machine Track (MachineType.TRACK)
  Minecart -> Machine Trolley (MachineType.TROLLEY)

### Stickiness model change -- MachineType isolation:
  OLD: All Machine Family blocks stick to all other Machine Family blocks.
  NEW: Each specialization sticks to same-type + Machine Frame (FRAME) only.
  - Track <-> Track: YES | Track <-> Trolley: NO | Track <-> Frame: YES

## [2026-03-08b] Issue #8 Fix -- Track-Trolley Signal Bleed [FIXED]

Resolved the last tracked known issue: Machine Track redstone signal bleeding
through Trolleys into Machine Frames, causing unintended frame network
deactivation.

### Root cause:

Two problems combined:

1. MachineTrackBlock exposed its POWER value to vanilla's redstone system via
   isSignalSource()=true, getSignal()=POWER, getDirectSignal()=POWER. This
   meant solid blocks adjacent to a powered Track (like Trolleys) picked up
   "weak power" through vanilla's standard mechanics. A Machine Frame on the
   other side of the Trolley then saw that weak power via getBestNeighborSignal()
   and flipped into suppressor mode, emitting anti-signal into its frame network.

2. FrameActivation treated ALL Machine Family blocks identically for both
   activation and suppression. Any IMachineFamily member receiving redstone
   power would become a suppressor -- but only Machine Frames should have
   that authority.

### Fix part 1: Track redstone isolation (MachineTrackBlock.java)

isSignalSource() now returns false. getSignal() and getDirectSignal() both
return 0. Track's POWER blockstate is now purely internal bookkeeping.

Track-to-Track conduction is unaffected because calculatePower() reads
neighbor POWER values directly from the blockstate (via isRedstoneConduit
check), completely bypassing vanilla's signal query system. Tagged
REDSTONE_COMPONENTS (levers, repeaters, etc.) still feed into Tracks via
vanilla's level.getSignal() call.

Result: Track POWER cannot leak through solid blocks. Trolleys, stone, and
all other non-Track blocks see zero signal from Tracks.

### Fix part 2: Machine Frame-only suppression (FrameActivation.java)

Step 4 (activation propagation) now branches on block type:
- MachineFrameBlock: only emits activation when unpowered (existing behavior)
- All other Machine Family blocks: ALWAYS emit activation at strength 15,
  regardless of their redstone state

Step 5 (anti-signal propagation) now skips any source that is not a
MachineFrameBlock. Only Machine Frames can suppress frame networks.

This future-proofs all Machine specializations (Clock, Repeater, Pulser, etc.)
-- their redstone activity stays in their own lane and never accidentally
deactivates frame networks they're adjacent to.

### Design rule established:

- Any Machine Family block = frame activation source (always strength 15)
- Only Machine Frame = can become frame suppressor when receiving redstone
- Track POWER = private to Track network, invisible to vanilla redstone
- Machine Frame has no POWER property and is not a redstone conduit

## [2026-03-07] Bug #10 Fix — Immovable Frame Anchor Detection (Feature 7)

Fixed bug #10: active framed blocks with immovable inners (obsidian, crying
obsidian, reinforced deepslate, bedrock-type) were not anchoring piston move
groups when positioned behind a group member in the push direction.

### Root cause analysis:

The issue was NOT in the backward walk's canStickTo logic as originally
theorized. Through diagnostic logging, the actual cause was identified:

When vanilla's backward walk (inside addBlockLine) encounters a block where
isPushable returns false, it treats it as a wall and silently stops walking
(returns true = "this line is fine, stop here"). It never makes a recursive
addBlockLine call for that position. Since Feature 5's immovable inner check
lives at HEAD of addBlockLine, it never fires for blocks the backward walk
skips. The framed obsidian was invisible to the resolver.

Sideways grabs (branching phase) worked correctly because branching calls
addBlockLine directly on the neighbor position, which DOES trigger Feature 5.

### Fix: Feature 7 — Immovable Frame Anchor Detection [IMPLEMENTED]

File: mixin/PistonStructureResolverMixin.java

Added a post-gathering anchor scan in the TAIL injection of addBranchingBlocks
(same location as Feature 3 sympathetic search and Feature 6 vanilla metal
conductors). After all blocks have been gathered into toPush, the new
ideomod$hasImmovableFrameAnchor() method scans every block in toPush and
checks all 6 neighbors for framed blocks with immovable inners that:
  1. Are NOT already in toPush (already handled by Feature 5)
  2. ARE active (inactive framed obsidian has no frame stickiness connection)
  3. Would be frame-sticky with the group member (same material, cross-frame
     mediation, or machine family adjacency)

If any such anchor is found, the resolve fails (cir.setReturnValue(false)),
preventing the group from moving. This mirrors Feature 5's behavior but
catches the case vanilla's backward walk silently skips.

### Key design constraint discovered during testing:

The immovable framed block must be ACTIVE to anchor. An inactive framed
obsidian sitting next to an active group is just inert — it has no frame
stickiness connection and should not prevent movement. Players can
intentionally deactivate framed obsidian (e.g., via machine block frame
deactivation from a different end) to disconnect it from a group.

redstone-style signal strength 0-15.

block. Max range: 15 blocks from source. Each block records strongest signal received.

override: any block reached by anti-signal is deactivated regardless of activation strength.

1. DISCOVER: BFS through all conductors (unchanged)
2. WIPE: Set IFrameBlocks to ACTIVE=false, clear vanilla metal activation set
3. FIND SOURCES: Find adjacent Machine Blocks (unchanged)

5. PROPAGATE ANTI-SIGNAL: BFS from powered machines, strength = redstone level, decaying.
6. APPLY: Block activates only if activation > 0 AND anti-signal == 0.

Example: Machine -- 15 frames -- Machine(redstone=5). First 10 frames active, last 5
suppressed by anti-signal.

Signal decay prevents backward activation (same as redstone dust). No block can send a
stronger signal back to its source.

## [2026-03-01] Backward Walk Grab Immunity Fix — Call-Pair Toggle

Fixed a bug where sticky blocks could not grab blocks behind them in the push
axis during piston, Repulser, and Attractor moves. Oddstone couldn't hold slime
behind it, and slime couldn't hold framed blocks behind it. Sideways grabs
(branching) worked correctly — only the backward walk (chain cohesion along the
push axis) was affected.

### Root cause

Vanilla's backward walk in addBlockLine checks canStickTo in BOTH directions:
  oldState.canStickTo(blockstate) && blockstate.canStickTo(oldState)

Our @Redirect intercepted BOTH calls and applied grab immunity to each one.
When oddstone (front) walked backward to slime (behind):
  Call 1: oddstone.canStickTo(slime) -> passed
  Call 2: slime.canStickTo(oddstone) -> passed canStickTo, but then
          isGrabBlocked(slime, oddstone) hit Rule 1 (non-oddstone can't grab
          oddstone) -> BLOCKED
Since vanilla ANDs both results, the chain broke.

### The fix: call-pair toggle

Added ThreadLocal<Boolean> ideomod$firstCanStickToCall that tracks which call
in the pair we're on:

  Call 1 (first=true):  self=front block (oldState), other=behind block
    -> Grab immunity IS checked. The front block is the active grabber
       reaching backward. Example: slime reaching back to oddstone -> blocked.

  Call 2 (first=false): self=behind block, other=front block (oldState)
    -> Grab immunity is NOT checked. This is the behind block's passive
       compatibility response. Only canStickTo + directional rules apply.

The toggle flips on each call and resets to true after the pair completes
(or when Call 1 returns false, since vanilla short-circuits the &&).

### Debugging journey

First attempt removed grab immunity from the backward walk entirely.
This overcorrected — slime could then chain backward to oddstone because
Call 1 (slime->oddstone) went unchecked. The toggle approach is the correct
granularity: check grab immunity on the front block reaching back, skip it
on the behind block responding.

### Removed: isActivePuller exemption

The isActivePuller() helper method and its special-case logic in the backward
walk redirect were removed. This was a workaround for the original bug —
it exempted Odd Slime from grab immunity in the backward walk so it could
pull blocks behind it. With the toggle fix, this exemption is unnecessary:
Odd Slime's Call 1 (reaching back) passes normally, and Call 2 (behind block
responding) skips grab immunity entirely.

Removed imports: OddSlimeBlock, DirectionalBlock, ModBlocks, OddstoneBlock
(all were only used by the removed isActivePuller helper or were already unused).

  - Added ideomod$firstCanStickToCall ThreadLocal toggle
  - Rewrote ideomod$checkCanStickToWithRules to use toggle

## [2026-02-28c] Framed Blocks — Transit Rendering + Sympathetic Data Fixes

Resolved three framed block bugs: sympathetic retraction data loss (Priority 1),
transit rendering during BlockMoveHelper moves (visual), and sympathetic transit
rendering during piston retraction (visual). All three shared a common pattern:
code paths that handled the directly-moved blocks but missed blocks added via
sympathetic links or the BlockMoveHelper path.

### Bug Fix 1: Sympathetic retraction with machine-activated framed blocks [FIXED]

File: mixin/PistonBaseBlockMixin.java (scanSympathetic method)

Issue: When a sticky piston retracts a group containing sympathetically linked
oddstone, any framed blocks attached to the REMOTE sympathetic oddstone via
machine activation lost their inner block data. scanSympathetic() saved the
remote oddstone itself but never scanned its sticky group for additional
IPistonMovable blocks (machine frames, activated framed blocks, etc.).

Root cause: scanSympathetic() called saveBlockEntityAt() on each sympathetically
found oddstone but did NOT call scanStickyGroup() on it. The blocks attached
to the remote oddstone via stickiness were never saved, so vanilla's block
entity destruction during the move wiped their data permanently.

Fix: After saving each sympathetically found oddstone, check if it's sticky
(isStickyBlock()) and if so call scanStickyGroup() to walk and save all
attached blocks. savedPositions is shared between both methods, preventing
duplicates.

### Bug Fix 2: Framed block transit rendering — BlockMoveHelper path [FIXED]

File: block/movement/BlockMoveHelper.java (new step 2.6)

Issue: Framed blocks moved by Repulser, Attractor, or Machine Track/Trolley
had invisible inner blocks during the 2-tick sliding animation. The client-side
transit renderer (PistonMovingBlockEntityRendererMixin) reads from MovingFrameData,
but MovingFrameData was only populated by PistonBaseBlockClientMixin which hooks
into vanilla's PistonBaseBlock.moveBlocks(). BlockMoveHelper has its own movement
pipeline and never calls moveBlocks().

Fix: Added step 2.6 in BlockMoveHelper — on the client side, iterates the same
toPush list (which already includes sympathetic blocks from the resolver mixin)
and stores FrameTransitInfo in MovingFrameData for any framed blocks found.
Mirrors the capture pattern from PistonBaseBlockClientMixin.

New imports added to BlockMoveHelper: FramedBlock, FramedBlockEntity,
MovingFrameData, ResourceLocation.

### Bug Fix 3: Sympathetic transit rendering during piston retraction [FIXED]

File: mixin/client/PistonBaseBlockClientMixin.java

Issue: When a vanilla sticky piston retracts a group containing sympathetically
linked oddstone, framed blocks on the remote sympathetic group had invisible
inner blocks during transit. The client capture (ideomod$captureRetraction)
used a BFS to find the sticky group but did not scan for sympathetic links,
so remote framed blocks were never captured into MovingFrameData.

Fix: Added three helper methods:
- ideomod$captureSympathetic() — mirrors server-side scanSympathetic(). Scans
  from each oddstone in allBlocks along all 6 axes for sympathetically linked
  oddstone. When found, also scans the remote oddstone's sticky group.
- ideomod$scanStickyGroupInto() — BFS sticky group scan that adds found blocks
  to the shared allBlocks set for subsequent capture.
- ideomod$isOddstoneOrFramedOddstone() — checks block identity for sympathetic
  eligibility.

New imports: OddstoneBlock, OddstoneConfig.

### Pattern note:

### Feature: Framed Block Immovable Inner (PistonBaseBlockMixin Feature 4) [IMPLEMENTED]

File: mixin/PistonBaseBlockMixin.java

Framed blocks wrapping immovable inner blocks (obsidian, crying obsidian,
reinforced deepslate, or destroySpeed -1 blocks) are now immovable by pistons.
Mirrors vanilla's hardcoded isPushable checks on the inner block's default state.
Uses BlockState.is() for registry-safe comparison. Runs before Feature 1
(IPistonMovable) so framed obsidian is blocked despite having IPistonMovable BE.

Key discovery: Vanilla isPushable does NOT use PushReaction.BLOCK for obsidian.
It hardcodes block identity checks and destroySpeed == -1. Initial implementation
using PushReaction.BLOCK silently failed because obsidian returns NORMAL.

### Feature: Framed Obsidian Anchors Sticky Groups (Resolver Feature 5) [IMPLEMENTED]

File: mixin/PistonStructureResolverMixin.java

When a sticky group (e.g. active frame chain) contains framed obsidian, the
entire push fails — framed obsidian anchors the group.

Key discovery: Vanilla's addBlockLine returns TRUE (skip) when isPushable
returns false, not FALSE (fail). This is correct for vanilla — an unrelated
immovable block shouldn't fail the push — but wrong for framed obsidian that
IS part of the sticky group via frame activation. The fix checks for immovable
inner blocks at HEAD of addBlockLine (before the branching guard), returning
false to fail the entire resolve. Fires in ALL phases (line-building + branching).

Helper: ideomod$isFramedBlockWithImmovableInner(BlockState, BlockPos).

### Bug Fix 1: Framed Slime No Bounce [FIXED]

File: block/frame/FramedBlock.java

Symptom: Framed slime cancelled fall damage but entities didn't bounce.

Root cause: SlimeBlock's bounce is split across two methods. fallOn() cancels
fall damage (calls super with 0 distance). updateEntityAfterFallOn() reverses

Fix: Added updateEntityAfterFallOn() override. Uses entity.blockPosition().below()
to find the framed block (method receives BlockGetter + Entity, no BlockPos).

### Bug Fix 2: Framed Obsidian Still Movable [FIXED]

File: mixin/PistonBaseBlockMixin.java

Symptom: Framed obsidian could be pushed by pistons.

block's default state. But vanilla doesn't use PushReaction for obsidian —

getPistonPushReaction() actually returns NORMAL.

Fix: Replaced PushReaction check with vanilla-mirroring approach: BlockState.is()
checks for Blocks.OBSIDIAN/CRYING_OBSIDIAN/REINFORCED_DEEPSLATE, plus
getDestroySpeed == -1 for bedrock-type blocks.

### Bug Fix 3: Framed Obsidian Left Behind by Sticky Group [FIXED]

File: mixin/PistonStructureResolverMixin.java

Symptom: When an active frame group contained framed obsidian, the group moved
and left the framed obsidian behind instead of failing the entire push.

Root cause: Vanilla's addBlockLine returns TRUE when isPushable returns false.
This means "skip this block, everything's fine" — not "fail the push." For
blocks that aren't part of the sticky group this is correct. But framed obsidian
IS part of the group via frame activation stickiness. The resolver skipped it

## [2026-02-28] Oddstone Pull Immunity, Frameability Whitelist, INNER_STICKY=4 (Oddstone)

Major session implementing Oddstone piston pull immunity, frameability whitelist
tag system, and full Framed Oddstone stickiness (INNER_STICKY=4). Five bugs
discovered and fixed during integration testing.

### Feature 1: Oddstone Piston Pull Immunity [IMPLEMENTED]

File: mixin/PistonBaseBlockMixin.java

Oddstone blocks cannot be pulled by sticky pistons. When a sticky piston
retracts, if the directly pulled block is Oddstone (real or framed with
INNER_STICKY=ODDSTONE), the piston retracts freely without pulling anything.

Implementation: ThreadLocal<BlockPos> `ideomod$pullTargetPos` stores the exact
pull position (pistonPos + direction * 2) during retraction. isPushable HEAD
inject checks: if block at pos is oddstone AND pos matches pullTargetPos,
return false. This is position-specific — only the DIRECTLY pulled block is
immune, not oddstone elsewhere in a sticky group.

Key design: if slime is stuck to oddstone and the piston pulls the slime, the
whole group moves (oddstone dragged by its own stickiness to slime, not grabbed
by piston). Only direct piston-on-oddstone retraction is blocked.

v1 had ghost piston head bug (check in moveBlocks left phantom heads). v2 used
boolean flag (too broad — blocked ALL oddstone during retraction). v3 (final)
uses position-specific BlockPos check.

### Feature 2: Frameability Whitelist Tag System [IMPLEMENTED]

File: block/frame/FrameabilityHelper.java
Tag: data/ideomod/tags/blocks/frameable_blocks.json

Replaced heuristic-based frameability checks with a tag-driven whitelist.
~290 vanilla blocks explicitly enumerated in the tag. Infested block variants
excluded (framing infested blocks would bypass the silverfish emergence
mechanic). Tag-based approach is deterministic, predictable, and easily
extensible by datapacks or other mods.

FrameabilityHelper.isFrameable() now checks: (1) block is in #ideomod:frameable_blocks
tag, (2) NOT already a FramedBlock, (3) NOT an IFrameBlock. Removed all prior
heuristic checks (full cube collision, no BE, not indestructible, etc.).

### Feature 3: INNER_STICKY=4 — Framed Oddstone [IMPLEMENTED]

Files: block/frame/FramedBlock.java, block/frame/FramedBlockEntity.java

Extended INNER_STICKY IntegerProperty range from 0-3 to 0-4. Added constant
STICKY_ODDSTONE=4. FramedBlockEntity.computeStickyType() returns STICKY_ODDSTONE
for OddstoneBlock instances.

FramedBlock.canStickTo() STICKY_ODDSTONE case mirrors OddstoneBlock behavior:
sticks to real+framed oddstone, all slime types (real+framed), NOT normal blocks
or machine family via inner stickiness. Frame stickiness (ACTIVE-gated) still
works independently for machine family and same-material connections.

Total blockstate count: 2 x 6 x 5 = 60 states per framed block type (was 48).

### Feature 4: Framed Oddstone Stickiness Rules [IMPLEMENTED]

File: Ideomod.java (registerStickinessRules)

Rule 1 expanded: Protects both real OddstoneBlock AND FramedBlock with
INNER_STICKY=ODDSTONE from being grabbed by non-oddstone blocks.
  Carve-out A: Oddstone-type grabbers (real or framed) can grab oddstone targets.
  Carve-out B (framed oddstone targets only, not bare):
    - Machine Family (activation source, must connect to network)
    - ACTIVE same-material IFrameBlock (core frame connection)

Rule 4 expanded: Each slime/honey/odd_slime branch now exempts INNER_STICKY=
ODDSTONE in addition to the matching type, since real Oddstone is a universal
grabber of all slime types. Oddstone target branch + framed oddstone target
branch added with same carve-outs as Rule 1.

Design principle: "Framing is the only way other blocks can grab oddstone."
Bare oddstone NEVER grabbed by frames/machines. Framed oddstone CAN be grabbed

File: block/OddstoneBlock.java

OddstoneBlock.canStickTo() now recognizes FramedBlock targets. Checks

## [2026-02-25] Priority 1 Bug Fixes — Defensive Guards

Resolved three Priority 1 potential crash bugs identified during the 2026-02-23a
codebase review. One previously-listed item (FramedBlockRenderer NPE) was found
to already be guarded.

### Bug fix 1: Portal division-by-zero in linkedTeleport [FIXED]

File: block/portal/OddstonePortalBlock.java

Issue: linkedTeleport() computed horizontal and vertical fractions by dividing
player offset by portal span (maxH - minH, maxV - minV). If a corrupted
SavedData entry produced a portal with zero span, this would divide by zero,
producing NaN coordinates and breaking teleportation.

Fix: Pre-compute hSpan and vSpan. If either is <= 0, default the fraction to
0.5 (center of portal) instead of dividing. Player lands at the center of the
destination portal rather than crashing.

### Bug fix 2: OddstoneConfig lazy-load race condition [FIXED]

File: config/OddstoneConfig.java

Issue: loaded flag was checked without synchronization in getSympatheticRadius()
and isMobAffected(). Two threads could both see loaded == false simultaneously
and trigger concurrent loadConfig() calls, corrupting the affectedMobs set.

Fix: Double-checked locking pattern. Added private static final Object LOCK.
Made loaded volatile. Both accessor methods now use:
if (!loaded) { synchronized (LOCK) { if (!loaded) loadConfig(); } }
reloadConfig() also synchronized on LOCK. Outer check is the fast path -- once
config is loaded, zero synchronization overhead.

### Bug fix 3: FramedBlockRenderer sampleBestLight NPE [ALREADY FIXED]

File: client/render/FramedBlockRenderer.java

Issue was listed as: be.getLevel() used before null guard in sampleBestLight().
Finding: The null guard already exists (if (level == null) return fallbackLight).
No code change needed. Struck from the issues list.

### Bug fix 4: OddstoneBlock unsafe ForgeRegistries.ENTITY_TYPES.getKey() [FIXED]

File: block/OddstoneBlock.java

Issue: Both getBlockPathType() and getAdjacentBlockPathType() called
ForgeRegistries.ENTITY_TYPES.getKey(mob.getType()).toString() without checking
if getKey() returned null. Unregistered entity types (from other mods) could
trigger an NPE.

Fix: Extract ResourceLocation into a local variable, null-check it, fall back
to DAMAGE_OTHER / DANGER_OTHER if null. Unknown entity types are repelled by
Oddstone rather than crashing.

## [2026-02-22f] Framed Blocks — Rendering Overhaul + FACING + INNER_STICKY

Major rendering rewrite and two new blockstate properties for framed blocks.
Resolves all known framed block rendering issues and implements directional
inner sticky behavior.

### New blockstate properties: FACING + INNER_STICKY

Added two properties to FramedBlock:

1. **FACING** (DirectionProperty, 6 values): Set from player look direction on
   placement (piston-style). Transfers to inner block's orientation property
   during rendering — DirectionalBlock.FACING (6-way), HorizontalDirectionalBlock
   .FACING (4-way, vertical clamped to NORTH), RotatedPillarBlock.AXIS (logs,
   mapped FACING→axis). Also controls Framed Odd Slime's directional stickiness.

2. **INNER_STICKY** (IntegerProperty, 0-3): Synced from inner block type.
   0=none, 1=slime, 2=honey, 3=odd_slime. Computed by
   FramedBlockEntity.updateBlockstateFromInner() on setInnerBlock(), onLoad(),
   loadMovementData(), and onPlace(). Enables inner sticky behavior at the
   blockstate level without needing block entity lookups in hot paths.

Total blockstate count: 2 → 48 (ACTIVE × FACING × INNER_STICKY).

### Inner sticky behavior

Framed blocks with sticky inner blocks (slime, honey, odd slime) now preserve
their native stickiness. A Framed Slime Block grabs normal blocks like real
slime. Implementation:

- FramedBlock.isStickyBlock(): returns true when ACTIVE || INNER_STICKY > 0
- FramedBlock.canStickTo(): combines frame rules (ACTIVE-gated, same-material
  + machine family) with inner sticky rules (INNER_STICKY-gated, applies
  vanilla exclusions per type)
- Grab immunity rules 1-3 extended: Framed Slime/Honey/Odd Slime also blocked
  from grabbing Oddstone (matching real sticky behavior)
- Grab immunity rules 9-11 carve-out: when a FramedBlock's INNER_STICKY matches
  the target sticky type, grab immunity is lifted (Framed Slime CAN grab slime)

### Framed Odd Slime directional behavior

Framed Odd Slime only has inner stickiness when pushed in FACING direction.
However, frame stickiness (ACTIVE + same-material) must work in ALL directions.
A blanket directional rule would kill both, so directional gating is handled in
PistonStructureResolverMixin with a second-chance check:

- ideomod$isFramedOddSlimeDirectionallyBlocked(): checks if inner stickiness
  should be blocked by direction
- ideomod$wouldFrameStickinessAllow(): second-chance — if ACTIVE and neighbor
  is same-material frame or machine family, allow despite directional block
- ideomod$isActivePuller(): covers both real Odd Slime and Framed Odd Slime
  for backward-walk active puller exemption

No blanket directional rule registered in Ideomod.java. Rule count: 11 grab
immunity + 1 directional (real Odd Slime only).

### Rendering overhaul — renderSingleBlock approach

Replaced manual per-face quad drawing with BlockRenderDispatcher.renderSingleBlock().
This handles all model geometry natively:

- **Multi-element models**: Slime's nested cubes render correctly
- **Translucent/cutout blocks**: Glass, slime, odd slime render with proper
  alpha blending via the block's native render type
- **Block tinting**: Grass, leaves get biome colors
- **Directional textures**: Inner state constructed with FACING from framed
  block — odd slime front/back/side textures match placement direction
- **Axis-based blocks**: Logs, pillars, hay bales rotate via AXIS property
  mapped from FACING

Inner block rendered at 0.998 scale (0.001 inset per side) via poseStack
scale + translate, replacing old manual epsilon vertex positions.

Lighting: brightest-of-6-neighbors (max block + max sky light from all face
neighbors). Single packed light value passed to renderSingleBlock.

### See-through-world fix

Root cause: framed blocks were registered WITHOUT noOcclusion() in their block
properties. Neighboring blocks culled their faces against the framed block.
When the inner block was translucent (glass, slime), the culled neighbor faces
were invisible, and the inner block's transparent pixels showed void.

Fix: Added .noOcclusion() to both IRON_FRAMED_BLOCK and COPPER_FRAMED_BLOCK
in ModBlocks.java. Neighbors now keep all faces rendered.

Previous attempts at renderer-level fixes (custom depth-only render types,
two-pass rendering, depth backing cuboids) were all unnecessary — the single
missing noOcclusion() was the root cause.

### Transit data pipeline update

MovingFrameData expanded from Map<BlockPos, ResourceLocation> to
Map<BlockPos, FrameTransitInfo> where FrameTransitInfo is a record containing
innerBlockId, facing, and innerSticky. PistonBaseBlockClientMixin captures all
three values before vanilla destroys block entities during piston movement.
Transit renderer constructs inner state with correct FACING from cached data.

### Item model update

FramedBlockItemModel.CompositeModel now stores and uses the inner block's
defaultBlockState() when querying quads (was passing null). Fixes multi-element
model resolution and state-dependent texture lookup for item display.

Known limitation: translucent inner blocks don't show transparency in item
rendering. The quad-compositing approach renders everything in one pass.
Purely cosmetic — in-world rendering is correct.

## [2026-02-22c] Framed Blocks — Piston Transit Flicker Fix

Resolved the dark flicker artifact during piston transit of framed blocks.
The flicker was most noticeable on vertical pushes (especially downward)
and appeared as a brief brightness pop mid-animation.

### Root cause:

The transit renderer (PistonMovingBlockEntityRendererMixin) was using a
SINGLE light value for all 6 faces of the inner block cuboid. The BESR
(FramedBlockRenderer) uses PER-FACE light sampling — each face checks
its own directional neighbor for light. The mismatch between these two
lighting models caused a visible brightness "pop" at the transition
boundaries (BESR → transit renderer → BESR).

Vertical movement was worst because the UP face (bright sky neighbor)
and DOWN face (dark ground neighbor) have the largest light difference.
When the transit renderer averaged them into a single value, the UP face
suddenly dimmed and the DOWN face suddenly brightened for the duration
of the animation. Horizontal movement was barely affected because all
side-face neighbors are at the same Y level with similar light.

### Fix:

PistonMovingBlockEntityRendererMixin now samples light PER FACE from
the face-direction neighbor, matching the BESR approach exactly. It
samples at both the source and destination positions and smoothly
interpolates based on animation progress using Mth.lerp(). At
progress=0.0 the lighting matches the BESR at the source position; at
progress=1.0 it matches the BESR at the destination. No pop at either
boundary.

### Updated files:
- mixin/client/PistonMovingBlockEntityRendererMixin.java — per-face
  light sampling with source/dest interpolation

### Diagnostic tooling:
- Added per-push diagnostic counter (DIAG_FRAMES_PER_PUSH). Set to 0
  (disabled) by default. Set to e.g. 60 to log per-frame light data
  for debugging. Resets per piston operation, not globally.
- Previous diagnostic (global counter) was broken — burned through all
  frames on first push, never logged subsequent pushes. Fixed by
  resetting when a new destPos is detected.

## [2026-02-21] Frame Blocks -- Machine-Activated Stickiness System

Implemented Iron Frame and Copper Frame blocks with activation-based stickiness
driven by adjacent Machine Blocks. Frame blocks are passive conductors analogous
to redstone dust: Machine Blocks are the signal source, and frames propagate
activation through same-material chains.

### New system: Frame Activation (redstone-style wipe-and-rebuild)

The activation system uses a "turn it off and on again" approach. When anything
changes (machine or frame placed/broken/neighbor updated), the entire connected
frame network is discovered via BFS, wiped to inactive, then rebuilt from all
adjacent Machine Block sources. This avoids incremental update race conditions
where frames in chains would see still-active neighbors and incorrectly retain
their activation state.

- FrameActivation.recalculate(level, pos): Single entry point called by all
  lifecycle hooks on both Machine Blocks and Frame Blocks.
  1. DISCOVER: BFS from change point through all connected frames (any material)
  2. WIPE: Set all frames to active=false (UPDATE_CLIENTS only)
  3. FIND SOURCES: Check all frames + change position for adjacent Machine Blocks
  4. RE-ACTIVATE: Flood-fill from each Machine Block through same-material chains
     (capped at 12 blocks per chain, matching piston push limit)

### Bugs resolved:

Bug 1 -- "item deleted on move" (onPlace timing):
Block lifecycle order during setBlock(): onPlace() fires BEFORE
newBlockEntity() creates the block entity. If onPlace() calls
MovingBlockEntityData.retrieve(), data is consumed but block entity
does not exist yet to receive it. Fix: removed all retrieval logic from
onPlace(). PistonMovingBlockEntityMixin is the sole consumer.

Bug 2 -- "client overwrites server data":
moveBlocks() runs on BOTH client and server (via triggerEvent block
events). Client-side block entities do not have synced inventory data
(container inventories are not sent to clients by default). Without a
client guard, the client's save (with empty inventory) overwrites the
server's valid save in the shared static MovingBlockEntityData map.
Fix: added if (level.isClientSide()) return; to both PistonBaseBlockMixin
and BlockMoveHelper step 2.5.

Bug 3 -- "retraction resolver fails":
PistonStructureResolver.resolve() returns false for retraction
(extending=false) with our IPistonMovable blocks. Root cause: the
resolver's internal isPushable calls use different parameters during
retraction that our HEAD mixin does not intercept the same way. Yet
vanilla's own moveBlocks succeeds because its triggerEvent pre-check
passes separately. Fix: retraction path bypasses the resolver entirely.
Instead scans the pull position directly and BFS-scans the sticky group.

### Key lessons learned:
1. Vanilla block lifecycle: setBlock() -> onPlace() -> newBlockEntity().
   Block entity does NOT exist during onPlace().
2. Static maps shared between logical sides: integrated server shares
   JVM statics between client and server threads. Client writes can
   clobber server data. Always guard with isClientSide().
3. retrieve() is destructive: ConcurrentHashMap.remove() consumes data.
   Multiple consumers = race condition. Single consumer only.
4. PistonStructureResolver behaves differently for extension vs
   retraction. Do not assume a resolver that works for push will work
   for pull.
5. Debug logging at INFO level is essential during development. Forge
   filters DEBUG by default in latest.log.

## [2026-02-18] Multiblock Structure Framework -- Phase 1 & Furnace Array

Implemented the Multiblock Structure Framework and its first structure type,
the Furnace Array. The framework provides registration-based detection,
tracking, and evaluation of multiblock structures as world data -- individual
blocks don't know they're part of a structure. The Structure Manager (SavedData)
holds all knowledge.

### Framework architecture (9 new Java files):

- **StructureDefinition.java**: Abstract base for structure type rulesets.
  Defines core blocks, frame tags, scan parameters. Subclassed per type.
- **FurnaceArrayDefinition.java**: Concrete definition for furnace arrays.
  Cores: furnace, blast_furnace, smoker. Frame tag: #ideomod:furnace_array_frame.
  Max cluster 3x2 (6 furnaces), requires open front face (air).
- **StructureScanner.java**: Directional pattern scanner. Phase 1: flood-fill
  cluster of adjacent same-type cores. Phase 2: compute frame bounds from
  cluster + facing direction. Phase 3: validate back/side/top/bottom frame
  layers + front face air openings. Normalizes bounds with Math.min/max to
  handle all facing directions (NORTH/WEST produce inverted coordinates).
  Normalizes core position to clusterMin for consistent exclusivity keying.
- **StructureResult.java**: Immutable scan output. Holds core pos, facing,
  cluster bounds, structure bounds, effector positions, frame positions,
  validity. Builder pattern for construction.
- **StructureRegistration.java**: Persistent registration entry. UUID, definition
  name, core position, last valid scan result, bounding box for chunk indexing.
  NBT serialization. Null bounds guard on load.
- **StructureManager.java**: Per-dimension SavedData. Stores all registrations,
  chunk index, type index, core exclusivity map, event-populated trackedCores
  set. Listens for block place/break events. Reactive core detection via block
  entity iteration (no chunk scanning). Query API for consuming systems.
  Debug stick notifications for register/deregister events.
- **StructureEffectHandler.java**: Interface for structure-type-specific effects.
  onFormed(), onRemoved(), onTick(), onUpdated().
- **FurnaceArrayEffect.java**: Sets custom GUI names ("Enhanced Furnace" etc.)
  on formation, clears on removal.
- **AbstractFurnaceBlockEntityMixin.java**: Injects into furnace tick to boost
  cooking speed by 50% (extra +1 progress on even ticks) when furnace is part
  of a registered furnace array. Safety clamp prevents progress from meeting or
  exceeding cookingTotalTime (vanilla uses equality check, not >=).

### Wiring files:

- **Ideomod.java**: Registers StructureManager.EventHandler on FORGE event bus
  and registers FurnaceArrayDefinition with StructureManager in commonSetup().
- **ideomod.mixins.json**: Added AbstractFurnaceBlockEntityMixin.
- **furnace_array_frame.json**: New block tag at
  data/ideomod/tags/blocks/furnace_array_frame.json. Contains 18 stone-family
  blocks (stone, cobblestone, stone_bricks, deepslate variants, etc.).
- **en_us.json**: Added Enhanced Furnace/Blast Furnace/Smoker container names
  and Structure Debug Stick item name.

### Debug tooling:

- **Structure Debug Stick**: New item (ModItems.STRUCTURE_DEBUG_STICK). Hold in
  either hand (mainhand or offhand). Color-coded chat messages appear when
  structures register (green) or deregister (red), showing structure type,
  core position, and core count. Zero overhead when nobody holds it.
- **structure_debug_stick.json**: Item model using vanilla stick texture.

### Key design decisions:

- **Reactive core detection**: Instead of scanning ~98K blocks per chunk on load
  (which froze the game), uses two complementary approaches: (1) block entity
  map iteration from nearby chunks when a frame block is placed (catches
  furnaces, typically 0-10 entries per chunk), and (2) event-populated
  trackedCores set for future non-block-entity cores. Combined with
  isRelevantForAnyDefinition() filter, most block placements skip the search
  entirely.
- **Canonical core position**: Scanner normalizes corePos to clusterMin so that
  scanning from any furnace in a cluster produces the same exclusivity key.
  Without this, each furnace registered a separate duplicate structure.
- **Bounds normalization**: Direction.relative() offsets can produce inverted
  min/max coordinates when facing NORTH or WEST (negative axis directions).
  Scanner normalizes with Math.min/max after directional calculation.
- **Cooking progress clamp**: Vanilla completes smelts via equality check
  (cookingProgress == cookingTotalTime), not >=. Mixin clamps progress to
  totalTime - 1 after boosting, so vanilla's next increment lands exactly
  on the target.

### Bugs found and fixed during testing:

1. **World load freeze**: onChunkLoaded() scanned 98K blocks per chunk.
   Hundreds of chunks loading during spawn prep = millions of lookups on
   server thread. Fix: eliminated chunk scanning entirely in favor of
   reactive block entity iteration.
2. **Duplicate structure registration**: Each furnace in a cluster registered
   its own structure because corePos differed. Fix: normalize to clusterMin.
3. **Bounds inversion**: NORTH/WEST facing structures had frameMin > frameMax,
   causing expanded bounds checks to always fail. Frame block breaks didn't
   trigger rescans. Fix: Math.min/max normalization.
4. **Infinite smelting progress**: Mixin could push cookingProgress past
   cookingTotalTime. Vanilla's equality check never passed, progress climbed
   forever, GUI arrow extended infinitely. Fix: safety clamp to totalTime - 1.
5. **Missing re-formation on block break**: Breaking a block covering a
   furnace's front face didn't trigger re-scan. Fix: added
   findAndScanNearbyCores() to block break path (cheap with BE iteration).
6. **Six messages per registration**: Debug stick showed one message per
   furnace. Same root cause as bug #2 (duplicate registrations). Fixed by
   canonical core position.

## [2026-02-15] Portal System -- Deactivation Fix, Cross-Axis Rotation, Break Effects
- Fixed critical bug: Z-axis portals randomly deactivating when blocks
  placed/broken near the frame exterior. X-axis portals less affected.
  Root cause: OddstonePortalHandler.onNeighborChanged() checked ALL
  neighbors of ALL frame Oddstone blocks, interpreting any non-frame
  neighbor (levers, redstone dust, dirt, air) as "corner broken" and
  triggering deactivation. Z-axis portals hit harder because redstone
  wiring on East/West faces caused more false-positive triggers.
- Secondary bug: power-loss check was hair-trigger. Single neighborChanged
  where hasNeighborSignal() momentarily returned false would kill portal,
  even from unrelated block updates. Caused flicker on Z-axis portals.

### Fix -- full frame re-validation (validateOrDeactivate):
- Replaced single-block deactivation logic with full frame re-validation.
  When any frame Oddstone gets neighborChanged and is adjacent to a portal:
  1. Navigate from adjacent portal block to frame structure
  2. Measure interior dimensions, derive all four corner positions
  3. Check all four corners are still valid corner blocks
  4. Walk entire frame perimeter: every Oddstone must be present AND powered
  5. Only deactivate if validation genuinely fails
- Mirrors activation path (which also validates full frame). Prevents false
  deactivation from exterior block updates or momentary signal fluctuations.

### Previous attempts that informed the fix:
- Attempt 1: isCornerPosition() -- checked if neighborPos was adjacent to
  portal block. But corners are DIAGONAL to portal blocks, not adjacent.
  Check always returned false, corners could never trigger deactivation.
- Attempt 2: isInPortalPlane() filter -- only ran check on in-plane neighbors.
  Still false-triggered because hasNeighborSignal() could return false
  during update cascades. Fundamental problem was reacting to single block's
  momentary state rather than validating the whole frame.

### New feature -- cross-axis portal rotation:
- When linked portals have different axes (X vs Z), player's yaw is rotated
  90 degrees to face through the destination portal's plane.
- Same-axis pairs: no rotation, player keeps their facing.
- X-axis to Z-axis: yaw += 90 (clockwise)
- Z-axis to X-axis: yaw -= 90 (counterclockwise)
- Uses player.teleportTo(level, x, y, z, yaw, pitch) overload with rotation.

### Break effects fix:
- Portal deactivation from corner break, power loss, or frame validation
  failure now produces same break particles and sound as when portal blocks
  cascade-break from mining a frame Oddstone.
- Changed PortalUtils.clearPortalBlocks() from level.setBlock(pos, AIR, 2)
  to level.destroyBlock(pos, false). destroyBlock handles break particles
  and the block's SoundType break sound automatically. false = no item drops.
- Removed manual SoundEvents.GLASS_BREAK from unregisterAndClear() since
  destroyBlock covers it.

### VoxelShape hitbox fix:
- Fixed portal block hitbox being 90 degrees off from rendered model.
- Swapped shape mapping in getShape(): X-axis portals (thin along X) now
  correctly use the X-pinched VoxelShape, Z-axis uses Z-pinched shape.

  moveBlocks() on the client via the block event system -- NOT via chunk sync.
- Any mod feature that places MovingPistonBlock MUST use the block event
  system (level.blockEvent -> triggerEvent on both sides) or the animation
  will be invisible.
