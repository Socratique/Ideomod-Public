# Ideomod Changelog

## [2026-02-21] Frame Blocks -- Machine-Activated Stickiness System

Implemented Iron Frame and Copper Frame blocks with activation-based stickiness
driven by adjacent Machine Blocks. Frame blocks are passive conductors analogous
to redstone dust: Machine Blocks are the signal source, and frames propagate
activation through same-material chains.

### New system: Frame Activation (redstone-style wipe-and-rebuild)

The activation system uses a "turn it off and on again" approach. When anything
changes (machine or frame placed/broken/neighbor updated), the entire connected
frame network is discovered via BFS, wiped to inactive, then rebuilt from all
adjacent Machine Block sources. This avoids incremental update race conditions
where frames in chains would see still-active neighbors and incorrectly retain
their activation state.

- FrameActivation.recalculate(level, pos): Single entry point called by all
  lifecycle hooks on both Machine Blocks and Frame Blocks.
  1. DISCOVER: BFS from change point through all connected frames (any material)
  2. WIPE: Set all frames to active=false (UPDATE_CLIENTS only)
  3. FIND SOURCES: Check all frames + change position for adjacent Machine Blocks
  4. RE-ACTIVATE: Flood-fill from each Machine Block through same-material chains
     (capped at 12 blocks per chain, matching piston push limit)

- com/ideomancer/ideomod/block/FrameMaterial.java -- Enum: IRON, COPPER
- com/ideomancer/ideomod/block/FrameBlock.java -- Base frame block with ACTIVE property

## [2026-02-21] IPistonMovable -- Block Entity Piston Movement System

Complete implementation of block entity data preservation during piston moves.
Machine Frame (formerly Machine Block) block entities now retain their
specialization item through all movement types: vanilla pistons (push and
sticky retract), Repulser, Attractor, and Machine Track/Trolley.

### New system: IPistonMovable interface + data pipeline
- New interface: IPistonMovable (com.ideomancer.ideomod.block)
  - saveMovementData() -> CompoundTag: serialize data before move
  - loadMovementData(CompoundTag): restore data after move
  - Opt-in system: only block entities that implement it are affected
- New class: MovingBlockEntityData (com.ideomancer.ideomod.block)
  - Static ConcurrentHashMap registry for data in transit
  - Keys: "dimension:x,y,z" at DESTINATION position
  - store() and retrieve() (destructive -- removes on read)
- MachineFrameBlockEntity implements IPistonMovable
  - Saves/loads inventory contents via ContainerHelper

### New mixin: PistonBaseBlockMixin (PistonBaseBlock)
- Feature 1 (isPushable): Allows IPistonMovable block entities to be
  pushed by pistons. Vanilla hardcodes return !hasBlockEntity() -- our
  HEAD inject returns true for IPistonMovable blocks instead.
- Feature 2 (moveBlocks): Saves IPistonMovable data before vanilla
  destroys block entities during the move.
  - Extension path: uses PistonStructureResolver to find toPush blocks
  - Retraction path: resolver fails for our blocks (internal isPushable
    calls with different parameters). Falls back to direct position scan
    at pistonPos + direction * 2, then BFS for sticky group members.
  - Sticky group scan respects isStickyBlock(), canStickTo(), and
    12-block push limit.

### New mixin: PistonMovingBlockEntityMixin (PistonMovingBlockEntity)
- Injects at TAIL of tick() to restore data after 2-tick animation
- Guards: server-only, waits for real block (not MOVING_PISTON)
- Retrieves data from MovingBlockEntityData (destructive read)
- Loads into fresh block entity via IPistonMovable.loadMovementData()

### BlockMoveHelper updated (step 2.5)
- Added server-side guard (if (!level.isClientSide())) around the
  IPistonMovable save logic in step 2.5
- This was the same bug as the PistonBaseBlockMixin client overwrite

### Machine Frame block entity refactor
- MachineBlock renamed to MachineFrameBlock (class only, registry ID
  stays "machine_block" for world compatibility)
- MachineFrameBlockEntity: single-slot GUI, item determines specialization
- MachineFrameMenu + MachineFrameScreen: container menu + client GUI
- onRemove() drops contents only when broken, NOT when moved by piston
  (movedByPiston guard)

### Bugs resolved:

Bug 1 -- "item deleted on move" (onPlace timing):
Block lifecycle order during setBlock(): onPlace() fires BEFORE
newBlockEntity() creates the block entity. If onPlace() calls
MovingBlockEntityData.retrieve(), data is consumed but block entity
does not exist yet to receive it. Fix: removed all retrieval logic from
onPlace(). PistonMovingBlockEntityMixin is the sole consumer.

Bug 2 -- "client overwrites server data":
moveBlocks() runs on BOTH client and server (via triggerEvent block
events). Client-side block entities do not have synced inventory data
(container inventories are not sent to clients by default). Without a
client guard, the client's save (with empty inventory) overwrites the
server's valid save in the shared static MovingBlockEntityData map.
Fix: added if (level.isClientSide()) return; to both PistonBaseBlockMixin
and BlockMoveHelper step 2.5.

Bug 3 -- "retraction resolver fails":
PistonStructureResolver.resolve() returns false for retraction
(extending=false) with our IPistonMovable blocks. Root cause: the
resolver's internal isPushable calls use different parameters during
retraction that our HEAD mixin does not intercept the same way. Yet
vanilla's own moveBlocks succeeds because its triggerEvent pre-check
passes separately. Fix: retraction path bypasses the resolver entirely.
Instead scans the pull position directly and BFS-scans the sticky group.

### Key lessons learned:
1. Vanilla block lifecycle: setBlock() -> onPlace() -> newBlockEntity().
   Block entity does NOT exist during onPlace().
2. Static maps shared between logical sides: integrated server shares
   JVM statics between client and server threads. Client writes can
   clobber server data. Always guard with isClientSide().
3. retrieve() is destructive: ConcurrentHashMap.remove() consumes data.
   Multiple consumers = race condition. Single consumer only.
4. PistonStructureResolver behaves differently for extension vs
   retraction. Do not assume a resolver that works for push will work
   for pull.
5. Debug logging at INFO level is essential during development. Forge
   filters DEBUG by default in latest.log.

## [2026-02-18] BlockMoveHelper Refactor + Machine Track & Trolley

Major refactor of the ranged piston movement system into a general-purpose
block movement utility, plus two new Machine Family blocks.

### BlockMoveHelper extraction:
- Extracted the core resolve-and-move logic from RangedPistonUtil into a
  new general-purpose utility: BlockMoveHelper.java.
- BlockMoveHelper.moveBlockAt(level, initiatorPos, targetPos, pushDir) is
  the single entry point for any system that needs piston-style block movement.
  Handles structure resolution, animation, safety checks, neighbor updates,
  sound -- everything.
- RangedPistonUtil slimmed down to scanning logic + filter predicates only.
  tryRepulse/tryAttract now delegate to BlockMoveHelper.moveBlockAt().
- RangedPistonFlags.java unchanged -- still handles ThreadLocal coordination.

### AbstractRangedPistonBlock base class:
- Extracted shared code from OddstoneRepulserBlock and OddstoneAttractorBlock
  into AbstractRangedPistonBlock. Handles FACING/POWERED states, rising edge
  detection, block event scheduling, rotation/mirror.
- Subclasses implement fire(level, pos, facing) only.
- OddstoneRepulserBlock: ~15 lines. OddstoneAttractorBlock: ~15 lines.
- Eliminates the ~90% code duplication noted in design docs.

### Machine Family helper methods:
- Added MachineBlock.isMachineFamily(Block) -- returns true for MachineBlock,
  MachineTrackBlock, MachineTrolleyBlock. Used by stickiness rules.
- Added MachineBlock.isRedstoneConduit(Block) -- returns true for MachineBlock
  and MachineTrackBlock. Used by calculatePower() in both classes.
- Added MachineBlock.canMachineFamilyStickTo(BlockState) -- shared canStickTo
  logic used by all three Machine Family blocks.
- Grab immunity rules in Ideomod.java updated to use isMachineFamily() so
  Track and Trolley automatically inherit all Machine Block stickiness rules.
- MachineBlock.calculatePower() updated to use isRedstoneConduit() so
  Machine Block <-> Track conduction chains work seamlessly.

### Machine Track (new block):
- Non-directional Machine Family block that pushes adjacent Trolleys.
- Push direction determined by signal source direction: signal from north
  face -> push south. Checks actual signal sources (conduit blocks with
  higher POWER, tagged redstone components) rather than vanilla's
  level.hasSignal() to avoid weak power misfires.
- Pushes ALL adjacent Trolleys in the computed direction, not just the one
  on the push face. Example: Track at (0,0), Trolley at (0,1), signal
  from west -> Trolley moves to (1,1).
- Conducts redstone like Machine Block (POWER 0-15, decay by 1 per block).
  Interoperable with Machine Block conduction chains.
- Block event param packs two directions via bit shifting (pushDir in
  bits 0-2, trolleyFace in bits 3-5) for proper client-server sync.
- Part of Machine Family -- sticks to Machine Block, Track, Trolley.
  Track protected from being dragged during pushes because its position
  is passed as initiatorPos (resolver treats it as pistonPos).

### Machine Trolley (new block):
- Passive Machine Family cargo carrier. No active behavior.
- Pushed by Tracks, carries anything stuck to it.
- Part of Machine Family -- same stickiness rules as Machine Block.
- Does NOT conduct redstone (pure cargo).
- Can be pushed by regular pistons.

### Bugs fixed during development:
1. Track only checked push-face for Trolleys. Fixed: checks all 6 faces.
2. After adding redstone conduction, vanilla's weak power mechanic caused
   Trolleys to appear as signal sources (solid blocks adjacent to signal
   source inherit weak power). Track was computing push direction from
   Trolley position instead of actual signal origin. Fixed: replaced
   level.hasSignal() with direct source interrogation -- only conduit
   blocks with higher POWER and tagged redstone components are recognized
   as signal sources.

## [2026-02-18] Multiblock Structure Framework -- Phase 1 & Furnace Array

Implemented the Multiblock Structure Framework and its first structure type,
the Furnace Array. The framework provides registration-based detection,
tracking, and evaluation of multiblock structures as world data -- individual
blocks don't know they're part of a structure. The Structure Manager (SavedData)
holds all knowledge.

### Framework architecture (9 new Java files):

- **StructureDefinition.java**: Abstract base for structure type rulesets.
  Defines core blocks, frame tags, scan parameters. Subclassed per type.
- **FurnaceArrayDefinition.java**: Concrete definition for furnace arrays.
  Cores: furnace, blast_furnace, smoker. Frame tag: #ideomod:furnace_array_frame.
  Max cluster 3x2 (6 furnaces), requires open front face (air).
- **StructureScanner.java**: Directional pattern scanner. Phase 1: flood-fill
  cluster of adjacent same-type cores. Phase 2: compute frame bounds from
  cluster + facing direction. Phase 3: validate back/side/top/bottom frame
  layers + front face air openings. Normalizes bounds with Math.min/max to
  handle all facing directions (NORTH/WEST produce inverted coordinates).
  Normalizes core position to clusterMin for consistent exclusivity keying.
- **StructureResult.java**: Immutable scan output. Holds core pos, facing,
  cluster bounds, structure bounds, effector positions, frame positions,
  validity. Builder pattern for construction.
- **StructureRegistration.java**: Persistent registration entry. UUID, definition
  name, core position, last valid scan result, bounding box for chunk indexing.
  NBT serialization. Null bounds guard on load.
- **StructureManager.java**: Per-dimension SavedData. Stores all registrations,
  chunk index, type index, core exclusivity map, event-populated trackedCores
  set. Listens for block place/break events. Reactive core detection via block
  entity iteration (no chunk scanning). Query API for consuming systems.
  Debug stick notifications for register/deregister events.
- **StructureEffectHandler.java**: Interface for structure-type-specific effects.
  onFormed(), onRemoved(), onTick(), onUpdated().
- **FurnaceArrayEffect.java**: Sets custom GUI names ("Enhanced Furnace" etc.)
  on formation, clears on removal.
- **AbstractFurnaceBlockEntityMixin.java**: Injects into furnace tick to boost
  cooking speed by 50% (extra +1 progress on even ticks) when furnace is part
  of a registered furnace array. Safety clamp prevents progress from meeting or
  exceeding cookingTotalTime (vanilla uses equality check, not >=).

### Wiring files:

- **Ideomod.java**: Registers StructureManager.EventHandler on FORGE event bus
  and registers FurnaceArrayDefinition with StructureManager in commonSetup().
- **ideomod.mixins.json**: Added AbstractFurnaceBlockEntityMixin.
- **furnace_array_frame.json**: New block tag at
  data/ideomod/tags/blocks/furnace_array_frame.json. Contains 18 stone-family
  blocks (stone, cobblestone, stone_bricks, deepslate variants, etc.).
- **en_us.json**: Added Enhanced Furnace/Blast Furnace/Smoker container names
  and Structure Debug Stick item name.

### Debug tooling:

- **Structure Debug Stick**: New item (ModItems.STRUCTURE_DEBUG_STICK). Hold in
  either hand (mainhand or offhand). Color-coded chat messages appear when
  structures register (green) or deregister (red), showing structure type,
  core position, and core count. Zero overhead when nobody holds it.
- **structure_debug_stick.json**: Item model using vanilla stick texture.

### Key design decisions:

- **Reactive core detection**: Instead of scanning ~98K blocks per chunk on load
  (which froze the game), uses two complementary approaches: (1) block entity
  map iteration from nearby chunks when a frame block is placed (catches
  furnaces, typically 0-10 entries per chunk), and (2) event-populated
  trackedCores set for future non-block-entity cores. Combined with
  isRelevantForAnyDefinition() filter, most block placements skip the search
  entirely.
- **Canonical core position**: Scanner normalizes corePos to clusterMin so that
  scanning from any furnace in a cluster produces the same exclusivity key.
  Without this, each furnace registered a separate duplicate structure.
- **Bounds normalization**: Direction.relative() offsets can produce inverted
  min/max coordinates when facing NORTH or WEST (negative axis directions).
  Scanner normalizes with Math.min/max after directional calculation.
- **Cooking progress clamp**: Vanilla completes smelts via equality check
  (cookingProgress == cookingTotalTime), not >=. Mixin clamps progress to
  totalTime - 1 after boosting, so vanilla's next increment lands exactly
  on the target.

### Bugs found and fixed during testing:

1. **World load freeze**: onChunkLoaded() scanned 98K blocks per chunk.
   Hundreds of chunks loading during spawn prep = millions of lookups on
   server thread. Fix: eliminated chunk scanning entirely in favor of
   reactive block entity iteration.
2. **Duplicate structure registration**: Each furnace in a cluster registered
   its own structure because corePos differed. Fix: normalize to clusterMin.
3. **Bounds inversion**: NORTH/WEST facing structures had frameMin > frameMax,
   causing expanded bounds checks to always fail. Frame block breaks didn't
   trigger rescans. Fix: Math.min/max normalization.
4. **Infinite smelting progress**: Mixin could push cookingProgress past
   cookingTotalTime. Vanilla's equality check never passed, progress climbed
   forever, GUI arrow extended infinitely. Fix: safety clamp to totalTime - 1.
5. **Missing re-formation on block break**: Breaking a block covering a
   furnace's front face didn't trigger re-scan. Fix: added
   findAndScanNearbyCores() to block break path (cheap with BE iteration).
6. **Six messages per registration**: Debug stick showed one message per
   furnace. Same root cause as bug #2 (duplicate registrations). Fixed by
   canonical core position.

## [2026-02-15] Portal System -- Deactivation Fix, Cross-Axis Rotation, Break Effects
- Fixed critical bug: Z-axis portals randomly deactivating when blocks
  placed/broken near the frame exterior. X-axis portals less affected.
  Root cause: OddstonePortalHandler.onNeighborChanged() checked ALL
  neighbors of ALL frame Oddstone blocks, interpreting any non-frame
  neighbor (levers, redstone dust, dirt, air) as "corner broken" and
  triggering deactivation. Z-axis portals hit harder because redstone
  wiring on East/West faces caused more false-positive triggers.
- Secondary bug: power-loss check was hair-trigger. Single neighborChanged
  where hasNeighborSignal() momentarily returned false would kill portal,
  even from unrelated block updates. Caused flicker on Z-axis portals.

### Fix -- full frame re-validation (validateOrDeactivate):
- Replaced single-block deactivation logic with full frame re-validation.
  When any frame Oddstone gets neighborChanged and is adjacent to a portal:
  1. Navigate from adjacent portal block to frame structure
  2. Measure interior dimensions, derive all four corner positions
  3. Check all four corners are still valid corner blocks
  4. Walk entire frame perimeter: every Oddstone must be present AND powered
  5. Only deactivate if validation genuinely fails
- Mirrors activation path (which also validates full frame). Prevents false
  deactivation from exterior block updates or momentary signal fluctuations.

### Previous attempts that informed the fix:
- Attempt 1: isCornerPosition() -- checked if neighborPos was adjacent to
  portal block. But corners are DIAGONAL to portal blocks, not adjacent.
  Check always returned false, corners could never trigger deactivation.
- Attempt 2: isInPortalPlane() filter -- only ran check on in-plane neighbors.
  Still false-triggered because hasNeighborSignal() could return false
  during update cascades. Fundamental problem was reacting to single block's
  momentary state rather than validating the whole frame.

### New feature -- cross-axis portal rotation:
- When linked portals have different axes (X vs Z), player's yaw is rotated
  90 degrees to face through the destination portal's plane.
- Same-axis pairs: no rotation, player keeps their facing.
- X-axis to Z-axis: yaw += 90 (clockwise)
- Z-axis to X-axis: yaw -= 90 (counterclockwise)
- Uses player.teleportTo(level, x, y, z, yaw, pitch) overload with rotation.

### Break effects fix:
- Portal deactivation from corner break, power loss, or frame validation
  failure now produces same break particles and sound as when portal blocks
  cascade-break from mining a frame Oddstone.
- Changed PortalUtils.clearPortalBlocks() from level.setBlock(pos, AIR, 2)
  to level.destroyBlock(pos, false). destroyBlock handles break particles
  and the block's SoundType break sound automatically. false = no item drops.
- Removed manual SoundEvents.GLASS_BREAK from unregisterAndClear() since
  destroyBlock covers it.

### VoxelShape hitbox fix:
- Fixed portal block hitbox being 90 degrees off from rendered model.
- Swapped shape mapping in getShape(): X-axis portals (thin along X) now
  correctly use the X-pinched VoxelShape, Z-axis uses Z-pinched shape.

### Files changed:
- OddstonePortalHandler.java: rewrote deactivation as full frame
  re-validation (validateOrDeactivate), removed hair-trigger checks,
  removed manual GLASS_BREAK sound
- OddstonePortalBlock.java: added cross-axis yaw rotation to
  linkedTeleport(), swapped VoxelShape mapping in getShape()
- PortalUtils.java: clearPortalBlocks uses destroyBlock instead of
  setBlock for proper break effects, removed unused Blocks import

## [2026-02-15] Ranged Piston -- Device Destination Protection Fix
- Fixed bug where Attractor could be overwritten by blocks pulled into
  its position. Scenario: Attractor at pos 0, Oddstone at pos 1 and pos 3
  with air at pos 2. Sympathetic movement connected both Oddstones across
  the gap. The pull moved pos 3 -> 2 correctly, but also moved pos 1 -> 0,
  overwriting the Attractor block.
- Root cause: resolveAndMove() checked that the device wasn't IN the push
  list, but never checked if any block's DESTINATION was the device position.
- Fix: Added destination check loop after existing safety checks. For each
  block in toPush, computes destPos = sourcePos + pushDir. If any destination
  equals devicePos, the entire move is rejected. Mirrors how vanilla pistons
  can't push blocks into the piston base.
- Also protects Repulser from similar edge cases with sticky/sympathetic
  chains routing blocks back toward the device.

### Files changed:
- RangedPistonUtil.java: added destination safety check in resolveAndMove()

## [2026-02-14] Ranged Piston System -- Repulser & Attractor (Animation Fix)
- Repulser and Attractor blocks now animate correctly using vanilla's
  MovingPistonBlock + PistonMovingBlockEntity system. Blocks slide smoothly
  from source to destination over 2 ticks with proper texture, entity
  pushing, collision, waterlogging, and all vanilla edge-case handling.

### Sympathetic boundary fix:
- Fixed bug where Attractor couldn't pull sympathetic Oddstone at the
  boundary of scan range (e.g. Oddstone at pos 13 not joining when target
  at pos 12). Caused by resolver's pistonPos overlapping with sympathetic
  block positions.
- Fix: Virtual piston placed at devicePos (far from action). ThreadLocal
  in RangedPistonFlags stores real target position. PistonStructureResolver
  mixin redirects startPos from (devicePos + pushDir) to actual targetPos.
  Resolver walks from correct position, pistonPos can't collide.

### Animation fix (the hard one):
- Root cause: MovingPistonBlock.newBlockEntity() returns null. The client
  never creates PistonMovingBlockEntity through the normal block entity path.
  Vanilla creates it on BOTH client and server by running moveBlocks() inside
  triggerEvent(), which executes on both sides via the block event packet system.
- Our code was running movement in neighborChanged() (server-only), so the
  client never had a PistonMovingBlockEntity to render -- blocks disappeared
  for 2 ticks then popped into place at the destination.
- Fix: Repulser/Attractor now use level.blockEvent() in neighborChanged()
  and do the actual movement in triggerEvent(), matching vanilla piston
  architecture. triggerEvent runs on BOTH client and server. RangedPistonUtil
  accepts Level (not ServerLevel) so both sides execute the full resolve-
  and-move logic, creating PistonMovingBlockEntity on both sides.
- Movement logic in RangedPistonUtil closely mirrors vanilla
  PistonBaseBlock.moveBlocks(): same ordering (snapshot -> destroy -> place
  MovingPistonBlock at destinations while sources still exist -> clear
  sources -> neighbor updates -> sound), same flags (68 placement, 82 cleanup),
  same factory method (MovingPistonBlock.newMovingBlockEntity()).

### Files changed:
- OddstoneRepulserBlock.java: blockEvent + triggerEvent pattern
- OddstoneAttractorBlock.java: blockEvent + triggerEvent pattern
- RangedPistonUtil.java: rewritten to mirror vanilla moveBlocks(), accepts Level
- RangedPistonFlags.java: new -- ThreadLocal for resolver startPos redirect
- PistonStructureResolverMixin.java: added Feature 4 -- startPos redirect
- Ideomod.java: no custom entity registration needed (vanilla handles rendering)

### Key lessons -- see BLOCK_EVENT_LESSON.md for full writeup:
- Vanilla's MovingPistonBlock is a BaseEntityBlock whose newBlockEntity()
  returns null. Client-side PistonMovingBlockEntity is created by running
  moveBlocks() on the client via the block event system -- NOT via chunk sync.
- Any mod feature that places MovingPistonBlock MUST use the block event
  system (level.blockEvent -> triggerEvent on both sides) or the animation
  will be invisible.

## [2026-02-13] Stage 5 -- PistonStructureResolver Mixin & Stickiness Overhaul
- New file: PistonStructureResolverMixin.java (com.ideomancer.ideomod.mixin)
  - Feature 1: One-way stickiness (grab immunity via StickinessRules)

  - Deactivation: portal clears and unregisters when frame is invalid

  - Per-dimension address spaces using Minecraft SavedData
