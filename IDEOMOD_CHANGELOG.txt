## [2026-02-25b] Priority 2 Performance Fixes

Resolved three Priority 2 performance issues identified during the 2026-02-23a
codebase review. Also removed stale known issues from IDEOMOD_DESIGN.md.

### Fix 1: MovingBlockEntityData log spam [FIXED]

File: block/movement/MovingBlockEntityData.java

Issue: store() and retrieve() logged at INFO level, causing console spam during
heavy piston activity (every block entity moved = two INFO messages).

Fix: Changed both LOGGER.info() calls to LOGGER.debug(). Messages still available
when log level is set to DEBUG, but no longer spam the console during normal play.

### Fix 2: ModCreativeTabs registry iteration [FIXED]

File: registry/ModCreativeTabs.java

Issue: The framed blocks creative tab iterated BuiltInRegistries.BLOCK (the entire
block registry — hundreds of blocks) every time the tab was opened. Each open
re-checked every block against FrameabilityHelper.isFrameable().

Fix: Added a static cachedFrameableBlocks list populated lazily on first tab open.
Subsequent tab opens read the cached list directly. Registry iteration happens once
per session, not per tab open.

### Fix 3: OddstonePortalBlock.findAnyPortalBlock() brute-force scan [FIXED]

File: block/portal/OddstonePortalBlock.java

Issue: findAnyPortalBlock() used a nested 20×20 loop (400 block checks) to find
any portal block in a partner portal. This ran during every linked teleportation.

Fix: Check the expected interior position first — (hDir+1, above+1) from the frame
corner, which is always the bottom-left of the interior for any valid portal. This
is a single block check in the common case. Falls back to a 5×5 scan (24 checks)
for edge cases instead of 20×20 (400 checks).

## [2026-02-25] Priority 1 Bug Fixes — Defensive Guards

Resolved three Priority 1 potential crash bugs identified during the 2026-02-23a
codebase review. One previously-listed item (FramedBlockRenderer NPE) was found
to already be guarded.

### Bug fix 1: Portal division-by-zero in linkedTeleport [FIXED]

File: block/portal/OddstonePortalBlock.java

Issue: linkedTeleport() computed horizontal and vertical fractions by dividing
player offset by portal span (maxH - minH, maxV - minV). If a corrupted
SavedData entry produced a portal with zero span, this would divide by zero,
producing NaN coordinates and breaking teleportation.

Fix: Pre-compute hSpan and vSpan. If either is <= 0, default the fraction to
0.5 (center of portal) instead of dividing. Player lands at the center of the
destination portal rather than crashing.

### Bug fix 2: OddstoneConfig lazy-load race condition [FIXED]

File: config/OddstoneConfig.java

Issue: loaded flag was checked without synchronization in getSympatheticRadius()
and isMobAffected(). Two threads could both see loaded == false simultaneously
and trigger concurrent loadConfig() calls, corrupting the affectedMobs set.

Fix: Double-checked locking pattern. Added private static final Object LOCK.
Made loaded volatile. Both accessor methods now use:
if (!loaded) { synchronized (LOCK) { if (!loaded) loadConfig(); } }
reloadConfig() also synchronized on LOCK. Outer check is the fast path -- once
config is loaded, zero synchronization overhead.

### Bug fix 3: FramedBlockRenderer sampleBestLight NPE [ALREADY FIXED]

File: client/render/FramedBlockRenderer.java

Issue was listed as: be.getLevel() used before null guard in sampleBestLight().
Finding: The null guard already exists (if (level == null) return fallbackLight).
No code change needed. Struck from the issues list.

### Bug fix 4: OddstoneBlock unsafe ForgeRegistries.ENTITY_TYPES.getKey() [FIXED]

File: block/OddstoneBlock.java

Issue: Both getBlockPathType() and getAdjacentBlockPathType() called
ForgeRegistries.ENTITY_TYPES.getKey(mob.getType()).toString() without checking
if getKey() returned null. Unregistered entity types (from other mods) could
trigger an NPE.

Fix: Extract ResourceLocation into a local variable, null-check it, fall back
to DAMAGE_OTHER / DANGER_OTHER if null. Unknown entity types are repelled by
Oddstone rather than crashing.

### Files changed:
- block/portal/OddstonePortalBlock.java — division-by-zero guard in linkedTeleport
- config/OddstoneConfig.java — double-checked locking on lazy load
- block/OddstoneBlock.java — null-safe entity type key lookup

## [2026-02-22f] Framed Blocks — Rendering Overhaul + FACING + INNER_STICKY

Major rendering rewrite and two new blockstate properties for framed blocks.
Resolves all known framed block rendering issues and implements directional
inner sticky behavior.

### New blockstate properties: FACING + INNER_STICKY

Added two properties to FramedBlock:

1. **FACING** (DirectionProperty, 6 values): Set from player look direction on
   placement (piston-style). Transfers to inner block's orientation property
   during rendering — DirectionalBlock.FACING (6-way), HorizontalDirectionalBlock
   .FACING (4-way, vertical clamped to NORTH), RotatedPillarBlock.AXIS (logs,
   mapped FACING→axis). Also controls Framed Odd Slime's directional stickiness.

2. **INNER_STICKY** (IntegerProperty, 0-3): Synced from inner block type.
   0=none, 1=slime, 2=honey, 3=odd_slime. Computed by
   FramedBlockEntity.updateBlockstateFromInner() on setInnerBlock(), onLoad(),
   loadMovementData(), and onPlace(). Enables inner sticky behavior at the
   blockstate level without needing block entity lookups in hot paths.

Total blockstate count: 2 → 48 (ACTIVE × FACING × INNER_STICKY).

### Inner sticky behavior

Framed blocks with sticky inner blocks (slime, honey, odd slime) now preserve
their native stickiness. A Framed Slime Block grabs normal blocks like real
slime. Implementation:

- FramedBlock.isStickyBlock(): returns true when ACTIVE || INNER_STICKY > 0
- FramedBlock.canStickTo(): combines frame rules (ACTIVE-gated, same-material
  + machine family) with inner sticky rules (INNER_STICKY-gated, applies
  vanilla exclusions per type)
- Grab immunity rules 1-3 extended: Framed Slime/Honey/Odd Slime also blocked
  from grabbing Oddstone (matching real sticky behavior)
- Grab immunity rules 9-11 carve-out: when a FramedBlock's INNER_STICKY matches
  the target sticky type, grab immunity is lifted (Framed Slime CAN grab slime)

### Framed Odd Slime directional behavior

Framed Odd Slime only has inner stickiness when pushed in FACING direction.
However, frame stickiness (ACTIVE + same-material) must work in ALL directions.
A blanket directional rule would kill both, so directional gating is handled in
PistonStructureResolverMixin with a second-chance check:

- ideomod$isFramedOddSlimeDirectionallyBlocked(): checks if inner stickiness
  should be blocked by direction
- ideomod$wouldFrameStickinessAllow(): second-chance — if ACTIVE and neighbor
  is same-material frame or machine family, allow despite directional block
- ideomod$isActivePuller(): covers both real Odd Slime and Framed Odd Slime
  for backward-walk active puller exemption

No blanket directional rule registered in Ideomod.java. Rule count: 11 grab
immunity + 1 directional (real Odd Slime only).

### Rendering overhaul — renderSingleBlock approach

Replaced manual per-face quad drawing with BlockRenderDispatcher.renderSingleBlock().
This handles all model geometry natively:

- **Multi-element models**: Slime's nested cubes render correctly
- **Translucent/cutout blocks**: Glass, slime, odd slime render with proper
  alpha blending via the block's native render type
- **Block tinting**: Grass, leaves get biome colors
- **Directional textures**: Inner state constructed with FACING from framed
  block — odd slime front/back/side textures match placement direction
- **Axis-based blocks**: Logs, pillars, hay bales rotate via AXIS property
  mapped from FACING

Inner block rendered at 0.998 scale (0.001 inset per side) via poseStack
scale + translate, replacing old manual epsilon vertex positions.

Lighting: brightest-of-6-neighbors (max block + max sky light from all face
neighbors). Single packed light value passed to renderSingleBlock.

### See-through-world fix

Root cause: framed blocks were registered WITHOUT noOcclusion() in their block
properties. Neighboring blocks culled their faces against the framed block.
When the inner block was translucent (glass, slime), the culled neighbor faces
were invisible, and the inner block's transparent pixels showed void.

Fix: Added .noOcclusion() to both IRON_FRAMED_BLOCK and COPPER_FRAMED_BLOCK
in ModBlocks.java. Neighbors now keep all faces rendered.

Previous attempts at renderer-level fixes (custom depth-only render types,
two-pass rendering, depth backing cuboids) were all unnecessary — the single
missing noOcclusion() was the root cause.

### Transit data pipeline update

MovingFrameData expanded from Map<BlockPos, ResourceLocation> to
Map<BlockPos, FrameTransitInfo> where FrameTransitInfo is a record containing
innerBlockId, facing, and innerSticky. PistonBaseBlockClientMixin captures all
three values before vanilla destroys block entities during piston movement.
Transit renderer constructs inner state with correct FACING from cached data.

### Item model update

FramedBlockItemModel.CompositeModel now stores and uses the inner block's
defaultBlockState() when querying quads (was passing null). Fixes multi-element
model resolution and state-dependent texture lookup for item display.

Known limitation: translucent inner blocks don't show transparency in item
rendering. The quad-compositing approach renders everything in one pass.
Purely cosmetic — in-world rendering is correct.

### Updated files:
- block/FramedBlock.java — FACING, INNER_STICKY properties, combined stickiness
- block/FramedBlockEntity.java — computeStickyType(), updateBlockstateFromInner()
- registry/ModBlocks.java — added noOcclusion() to framed block properties

## [2026-02-22c] Framed Blocks — Piston Transit Flicker Fix

Resolved the dark flicker artifact during piston transit of framed blocks.
The flicker was most noticeable on vertical pushes (especially downward)
and appeared as a brief brightness pop mid-animation.

### Root cause:

The transit renderer (PistonMovingBlockEntityRendererMixin) was using a
SINGLE light value for all 6 faces of the inner block cuboid. The BESR
(FramedBlockRenderer) uses PER-FACE light sampling — each face checks
its own directional neighbor for light. The mismatch between these two
lighting models caused a visible brightness "pop" at the transition
boundaries (BESR → transit renderer → BESR).

Vertical movement was worst because the UP face (bright sky neighbor)
and DOWN face (dark ground neighbor) have the largest light difference.
When the transit renderer averaged them into a single value, the UP face
suddenly dimmed and the DOWN face suddenly brightened for the duration
of the animation. Horizontal movement was barely affected because all
side-face neighbors are at the same Y level with similar light.

### Fix:

PistonMovingBlockEntityRendererMixin now samples light PER FACE from
the face-direction neighbor, matching the BESR approach exactly. It
samples at both the source and destination positions and smoothly
interpolates based on animation progress using Mth.lerp(). At
progress=0.0 the lighting matches the BESR at the source position; at
progress=1.0 it matches the BESR at the destination. No pop at either
boundary.

### Updated files:
- mixin/client/PistonMovingBlockEntityRendererMixin.java — per-face
  light sampling with source/dest interpolation

### Diagnostic tooling:
- Added per-push diagnostic counter (DIAG_FRAMES_PER_PUSH). Set to 0
  (disabled) by default. Set to e.g. 60 to log per-frame light data
  for debugging. Resets per piston operation, not globally.
- Previous diagnostic (global counter) was broken — burned through all
  frames on first push, never logged subsequent pushes. Fixed by
  resetting when a new destPos is detected.

## [2026-02-22b] Framed Blocks — Visual Polish (Piston Transit + Item Rendering)

Resolved both deferred visual polish items from the Framed Blocks implementation.
Inner block textures now render during piston transit animations and in
inventory/creative menu items.

### Fix 1: Piston Transit Rendering (inner block visible during 2-tick animation)

**Problem**: During piston movement, framed blocks showed only the empty frame
overlay. The inner block texture disappeared because vanilla's PistonHeadRenderer
doesn't know about FramedBlockRenderer's two-layer rendering system.

**Solution**: Two client-side mixins + a data cache:

1. `client/MovingFrameData.java` — ConcurrentHashMap cache storing destination
   position -> inner block ResourceLocation. Client-only, populated before
   vanilla destroys block entities.

2. `mixin/client/PistonBaseBlockClientMixin.java` — Injects at HEAD of
   PistonBaseBlock.moveBlocks() on client side. Captures FramedBlock inner
   block IDs before vanilla destroys the block entities during the move.
   - Extension: uses PistonStructureResolver (handles branching groups)
   - Retraction: resolver fails for IPistonMovable blocks (documented Bug 3).
     Uses sticky-group-aware BFS mirroring the server-side PistonBaseBlockMixin
     approach: line walk from pull position + isStickyBlock()/canStickTo()
     neighbor expansion.
   - Clears stale MovingFrameData at start of each capture pass.

3. `mixin/client/PistonMovingBlockEntityRendererMixin.java` — Injects at HEAD
   of PistonHeadRenderer.render(). When the moved block is a FramedBlock:
   - Looks up inner block ID from MovingFrameData
   - Applies animation offset using vanilla's own getXOff/getYOff/getZOff
   - Draws inner block cuboid with epsilon inset (same geometry as BESR)
   - Uses ItemBlockRenderTypes.getMovingBlockRenderType() for proper Forge
     render pipeline compatibility
   - Per-face light sampling from directional neighbors, blended between
     source and destination positions by animation progress
   - Vanilla then renders the frame overlay on top with the same transform

### Fix 2: Item Rendering (inner block visible in inventory/creative)

**Problem**: All framed block items looked identical in inventory — just the
frame texture. "Iron Framed Stone" vs "Iron Framed Dirt" indistinguishable.

**Solution**: Custom BakedModel wrapper:

1. `client/FramedBlockItemModel.java` — BakedModel with custom ItemOverrides.
   Reads BlockEntityTag.InnerBlock from ItemStack NBT, looks up inner block's
   BakedModel, returns CompositeModel merging inner block quads + frame overlay
   quads. ConcurrentHashMap cache keyed by ResourceLocation.

2. `Ideomod.java` — Added onModifyBakingResult(ModelEvent.ModifyBakingResult)
   listener. Wraps iron_framed_block and copper_framed_block item models with
   FramedBlockItemModel at bake time.

### Updated files:
- Ideomod.java — Added onModifyBakingResult listener, ResourceLocation import
- ideomod.mixins.json — Added client mixins to common array (Forge dev
  environment does not process the "client" array reliably; client mixins

### New files:

- client/FramedBlockItemModel.java
- mixin/client/PistonBaseBlockClientMixin.java

### Challenges resolved:
1. Mixin config "client" array: Forge dev environment silently ignores the
   "client" array in mixin JSON configs. Mixins applied but never fired.
   Fix: moved client mixins to "mixins" (common) array with runtime guards.
   Discovered via debug.log — mixins showed as "Mixing into..." but produced
   no runtime log output. The "client" array showed zero trace in logs.

2. INVOKE ordinal mismatch: Initial approach targeted renderBlock() ordinal=2,
   but Forge patches the method (renderPistonMovedBlocks replaces vanilla code
   inside if(false) block), changing the call count. The normal moved block
   branch is ordinal=3, not ordinal=2. Fix: switched to HEAD injection with
   vanilla's own getXOff/getYOff/getZOff offset methods.

3. Retraction capture failure: PistonStructureResolver.resolve() returns false

4. Animation offset math: PMBE sits at destination position but animates from
   source. Initial manual offset calculation (direction * (progress - 1.0))
   caused position mismatches. Fix: use vanilla's getXOff/getYOff/getZOff
   which internally call getExtendedProgress() handling both extension and
   retraction correctly.

5. Lighting model mismatch: Transit renderer initially used single light value
   for all faces. BESR uses per-face neighbor sampling. Mismatch caused visible
   brightness pop at animation boundaries, worst on vertical moves. Fixed in
   [2026-02-22c].

  connected to a Machine Block via the FrameActivation system, same as Frame
  Blocks. The isStickyBlock() method likely returns true unconditionally
  instead of checking the ACTIVE state. Needs investigation and fix.

## [2026-02-22] Framed Blocks — Dynamic Block Wrapping System

Implemented Iron Framed Block and Copper Framed Block — blocks that wrap any
valid "inner block" with a metal frame, preserving the inner block's functional
behavior while adding frame-family stickiness on top.

### Architecture: Proxy Block Entity + BESR Rendering

Two registered block IDs (iron_framed_block, copper_framed_block) serve as
transparent proxies. A shared FramedBlockEntity stores the inner block's
ResourceLocation. FramedBlock overrides ~15 behavioral methods, each querying
the inner block's defaultBlockState() for delegation. The BESR renders the
inner block's per-face textures as a full-size cuboid with epsilon inset
(0.001 blocks) to prevent z-fighting, with the frame overlay JSON model
rendering on top.

### New files:
- block/FrameabilityHelper.java — Static checks for frameability (full cube,
  no BE, not already framed, etc.). Try-catch on getCollisionShape(null, null)
  for blocks like MovingPistonBlock that NPE without world context.
- block/FramedBlock.java — IFrameBlock + EntityBlock. ACTIVE property.
  Delegates ~15 methods to inner block. getCloneItemStack() for middle-click.
  isStickyBlock() always true, canStickTo() combines frame + inner block rules.
- block/FramedBlockEntity.java — Stores ResourceLocation innerBlockId.
  Client sync via getUpdateTag/getUpdatePacket. IPistonMovable.
- block/FramedBlockItem.java — Dynamic getName() ("Iron Framed Stone" etc.).
  Static createStack() helpers for NBT setup.
- block/FramedBlockRecipe.java — CustomRecipe: 1 frame + 1 frameable block.
- block/ModRecipeSerializers.java — DeferredRegister for recipe serializers.
- block/FramedBlockLoot.java — Helper for manual drop creation.
- client/FramedBlockRenderer.java — BESR. Per-face TextureAtlasSprite from
  inner block's BakedModel. Epsilon inset, per-face light sampling.
- client/FramedBlockDebugOverlay.java — F3 debug overlay showing inner block.

### New creative tab:
- framed_blocks_tab: Dynamically populated from ALL registered blocks via
  FrameabilityHelper.isFrameable(). Iron + copper variants for each valid block.

### New recipe type:
- ideomod:framed_block — Special shapeless recipe: frame + block = framed block
  with inner block NBT.

### 1-tick piston data preservation fix (affects ALL IPistonMovable blocks):
- PistonMovingBlockEntityMixin.java — Added finalTick() TAIL inject. Vanilla
  calls finalTick() (non-static instance method) instead of tick() (static) for
  1-tick piston pulses. Without this hook, data was saved but never restored.
  Root cause: finalTick() immediately places the real block without the normal
  2-tick tick() animation. Our restore in tick() never saw the "real block placed"
  condition. Fixes data loss for BOTH FramedBlockEntity AND MachineFrameBlockEntity.

### Updated files:
- ModBlocks, ModItems, ModBlockEntities, ModCreativeTabs, Ideomod.java
- PistonStructureResolverMixin.java — sympathetic movement "sees through" frames
- PistonMovingBlockEntityMixin.java — added finalTick() hook (see above)

### Bugs resolved:
1. FrameabilityHelper crash: MovingPistonBlock NPE during creative tab population.
   Fix: try-catch wrapper on getCollisionShape(null, null).
2. BESR winding: Side faces rendered backfaces. Fix: CW winding on sides, CCW on
   top/bottom matching Minecraft convention.
3. BESR z-fighting: Inner texture and frame overlay flickered on same plane.
   Fix: epsilon inset (0.001 blocks).
4. BESR darkness: BESR faces lack chunk ambient occlusion.
   Fix: per-face light sampling from neighboring block positions.
5. Item model missing texture: models/item/ files had _item suffix instead of
   matching registry name. Fix: iron_framed_block.json not iron_framed_block_item.json.
6. 1-tick piston data loss: finalTick() hook (see above).
7. Middle-click gave empty frame: Added getCloneItemStack() override.

## [2026-02-21] Frame Blocks -- Machine-Activated Stickiness System

Implemented Iron Frame and Copper Frame blocks with activation-based stickiness
driven by adjacent Machine Blocks. Frame blocks are passive conductors analogous
to redstone dust: Machine Blocks are the signal source, and frames propagate
activation through same-material chains.

### New system: Frame Activation (redstone-style wipe-and-rebuild)

The activation system uses a "turn it off and on again" approach. When anything
changes (machine or frame placed/broken/neighbor updated), the entire connected
frame network is discovered via BFS, wiped to inactive, then rebuilt from all
adjacent Machine Block sources. This avoids incremental update race conditions
where frames in chains would see still-active neighbors and incorrectly retain
their activation state.

- FrameActivation.recalculate(level, pos): Single entry point called by all
  lifecycle hooks on both Machine Blocks and Frame Blocks.
  1. DISCOVER: BFS from change point through all connected frames (any material)
  2. WIPE: Set all frames to active=false (UPDATE_CLIENTS only)
  3. FIND SOURCES: Check all frames + change position for adjacent Machine Blocks
  4. RE-ACTIVATE: Flood-fill from each Machine Block through same-material chains
     (capped at 12 blocks per chain, matching piston push limit)

### Bugs resolved:

Bug 1 -- "item deleted on move" (onPlace timing):
Block lifecycle order during setBlock(): onPlace() fires BEFORE
newBlockEntity() creates the block entity. If onPlace() calls
MovingBlockEntityData.retrieve(), data is consumed but block entity
does not exist yet to receive it. Fix: removed all retrieval logic from
onPlace(). PistonMovingBlockEntityMixin is the sole consumer.

Bug 2 -- "client overwrites server data":
moveBlocks() runs on BOTH client and server (via triggerEvent block
events). Client-side block entities do not have synced inventory data
(container inventories are not sent to clients by default). Without a
client guard, the client's save (with empty inventory) overwrites the
server's valid save in the shared static MovingBlockEntityData map.
Fix: added if (level.isClientSide()) return; to both PistonBaseBlockMixin
and BlockMoveHelper step 2.5.

Bug 3 -- "retraction resolver fails":
PistonStructureResolver.resolve() returns false for retraction
(extending=false) with our IPistonMovable blocks. Root cause: the
resolver's internal isPushable calls use different parameters during
retraction that our HEAD mixin does not intercept the same way. Yet
vanilla's own moveBlocks succeeds because its triggerEvent pre-check
passes separately. Fix: retraction path bypasses the resolver entirely.
Instead scans the pull position directly and BFS-scans the sticky group.

### Key lessons learned:
1. Vanilla block lifecycle: setBlock() -> onPlace() -> newBlockEntity().
   Block entity does NOT exist during onPlace().
2. Static maps shared between logical sides: integrated server shares
   JVM statics between client and server threads. Client writes can
   clobber server data. Always guard with isClientSide().
3. retrieve() is destructive: ConcurrentHashMap.remove() consumes data.
   Multiple consumers = race condition. Single consumer only.
4. PistonStructureResolver behaves differently for extension vs
   retraction. Do not assume a resolver that works for push will work
   for pull.
5. Debug logging at INFO level is essential during development. Forge
   filters DEBUG by default in latest.log.

## [2026-02-18] Multiblock Structure Framework -- Phase 1 & Furnace Array

Implemented the Multiblock Structure Framework and its first structure type,
the Furnace Array. The framework provides registration-based detection,
tracking, and evaluation of multiblock structures as world data -- individual
blocks don't know they're part of a structure. The Structure Manager (SavedData)
holds all knowledge.

### Framework architecture (9 new Java files):

- **StructureDefinition.java**: Abstract base for structure type rulesets.
  Defines core blocks, frame tags, scan parameters. Subclassed per type.
- **FurnaceArrayDefinition.java**: Concrete definition for furnace arrays.
  Cores: furnace, blast_furnace, smoker. Frame tag: #ideomod:furnace_array_frame.
  Max cluster 3x2 (6 furnaces), requires open front face (air).
- **StructureScanner.java**: Directional pattern scanner. Phase 1: flood-fill
  cluster of adjacent same-type cores. Phase 2: compute frame bounds from
  cluster + facing direction. Phase 3: validate back/side/top/bottom frame
  layers + front face air openings. Normalizes bounds with Math.min/max to
  handle all facing directions (NORTH/WEST produce inverted coordinates).
  Normalizes core position to clusterMin for consistent exclusivity keying.
- **StructureResult.java**: Immutable scan output. Holds core pos, facing,
  cluster bounds, structure bounds, effector positions, frame positions,
  validity. Builder pattern for construction.
- **StructureRegistration.java**: Persistent registration entry. UUID, definition
  name, core position, last valid scan result, bounding box for chunk indexing.
  NBT serialization. Null bounds guard on load.
- **StructureManager.java**: Per-dimension SavedData. Stores all registrations,
  chunk index, type index, core exclusivity map, event-populated trackedCores
  set. Listens for block place/break events. Reactive core detection via block
  entity iteration (no chunk scanning). Query API for consuming systems.
  Debug stick notifications for register/deregister events.
- **StructureEffectHandler.java**: Interface for structure-type-specific effects.
  onFormed(), onRemoved(), onTick(), onUpdated().
- **FurnaceArrayEffect.java**: Sets custom GUI names ("Enhanced Furnace" etc.)
  on formation, clears on removal.
- **AbstractFurnaceBlockEntityMixin.java**: Injects into furnace tick to boost
  cooking speed by 50% (extra +1 progress on even ticks) when furnace is part
  of a registered furnace array. Safety clamp prevents progress from meeting or
  exceeding cookingTotalTime (vanilla uses equality check, not >=).

### Wiring files:

- **Ideomod.java**: Registers StructureManager.EventHandler on FORGE event bus
  and registers FurnaceArrayDefinition with StructureManager in commonSetup().
- **ideomod.mixins.json**: Added AbstractFurnaceBlockEntityMixin.
- **furnace_array_frame.json**: New block tag at
  data/ideomod/tags/blocks/furnace_array_frame.json. Contains 18 stone-family
  blocks (stone, cobblestone, stone_bricks, deepslate variants, etc.).
- **en_us.json**: Added Enhanced Furnace/Blast Furnace/Smoker container names
  and Structure Debug Stick item name.

### Debug tooling:

- **Structure Debug Stick**: New item (ModItems.STRUCTURE_DEBUG_STICK). Hold in
  either hand (mainhand or offhand). Color-coded chat messages appear when
  structures register (green) or deregister (red), showing structure type,
  core position, and core count. Zero overhead when nobody holds it.
- **structure_debug_stick.json**: Item model using vanilla stick texture.

### Key design decisions:

- **Reactive core detection**: Instead of scanning ~98K blocks per chunk on load
  (which froze the game), uses two complementary approaches: (1) block entity
  map iteration from nearby chunks when a frame block is placed (catches
  furnaces, typically 0-10 entries per chunk), and (2) event-populated
  trackedCores set for future non-block-entity cores. Combined with
  isRelevantForAnyDefinition() filter, most block placements skip the search
  entirely.
- **Canonical core position**: Scanner normalizes corePos to clusterMin so that
  scanning from any furnace in a cluster produces the same exclusivity key.
  Without this, each furnace registered a separate duplicate structure.
- **Bounds normalization**: Direction.relative() offsets can produce inverted
  min/max coordinates when facing NORTH or WEST (negative axis directions).
  Scanner normalizes with Math.min/max after directional calculation.
- **Cooking progress clamp**: Vanilla completes smelts via equality check
  (cookingProgress == cookingTotalTime), not >=. Mixin clamps progress to
  totalTime - 1 after boosting, so vanilla's next increment lands exactly
  on the target.

### Bugs found and fixed during testing:

1. **World load freeze**: onChunkLoaded() scanned 98K blocks per chunk.
   Hundreds of chunks loading during spawn prep = millions of lookups on
   server thread. Fix: eliminated chunk scanning entirely in favor of
   reactive block entity iteration.
2. **Duplicate structure registration**: Each furnace in a cluster registered
   its own structure because corePos differed. Fix: normalize to clusterMin.
3. **Bounds inversion**: NORTH/WEST facing structures had frameMin > frameMax,
   causing expanded bounds checks to always fail. Frame block breaks didn't
   trigger rescans. Fix: Math.min/max normalization.
4. **Infinite smelting progress**: Mixin could push cookingProgress past
   cookingTotalTime. Vanilla's equality check never passed, progress climbed
   forever, GUI arrow extended infinitely. Fix: safety clamp to totalTime - 1.
5. **Missing re-formation on block break**: Breaking a block covering a
   furnace's front face didn't trigger re-scan. Fix: added
   findAndScanNearbyCores() to block break path (cheap with BE iteration).
6. **Six messages per registration**: Debug stick showed one message per
   furnace. Same root cause as bug #2 (duplicate registrations). Fixed by
   canonical core position.

## [2026-02-15] Portal System -- Deactivation Fix, Cross-Axis Rotation, Break Effects
- Fixed critical bug: Z-axis portals randomly deactivating when blocks
  placed/broken near the frame exterior. X-axis portals less affected.
  Root cause: OddstonePortalHandler.onNeighborChanged() checked ALL
  neighbors of ALL frame Oddstone blocks, interpreting any non-frame
  neighbor (levers, redstone dust, dirt, air) as "corner broken" and
  triggering deactivation. Z-axis portals hit harder because redstone
  wiring on East/West faces caused more false-positive triggers.
- Secondary bug: power-loss check was hair-trigger. Single neighborChanged
  where hasNeighborSignal() momentarily returned false would kill portal,
  even from unrelated block updates. Caused flicker on Z-axis portals.

### Fix -- full frame re-validation (validateOrDeactivate):
- Replaced single-block deactivation logic with full frame re-validation.
  When any frame Oddstone gets neighborChanged and is adjacent to a portal:
  1. Navigate from adjacent portal block to frame structure
  2. Measure interior dimensions, derive all four corner positions
  3. Check all four corners are still valid corner blocks
  4. Walk entire frame perimeter: every Oddstone must be present AND powered
  5. Only deactivate if validation genuinely fails
- Mirrors activation path (which also validates full frame). Prevents false
  deactivation from exterior block updates or momentary signal fluctuations.

### Previous attempts that informed the fix:
- Attempt 1: isCornerPosition() -- checked if neighborPos was adjacent to
  portal block. But corners are DIAGONAL to portal blocks, not adjacent.
  Check always returned false, corners could never trigger deactivation.
- Attempt 2: isInPortalPlane() filter -- only ran check on in-plane neighbors.
  Still false-triggered because hasNeighborSignal() could return false
  during update cascades. Fundamental problem was reacting to single block's
  momentary state rather than validating the whole frame.

### New feature -- cross-axis portal rotation:
- When linked portals have different axes (X vs Z), player's yaw is rotated
  90 degrees to face through the destination portal's plane.
- Same-axis pairs: no rotation, player keeps their facing.
- X-axis to Z-axis: yaw += 90 (clockwise)
- Z-axis to X-axis: yaw -= 90 (counterclockwise)
- Uses player.teleportTo(level, x, y, z, yaw, pitch) overload with rotation.

### Break effects fix:
- Portal deactivation from corner break, power loss, or frame validation
  failure now produces same break particles and sound as when portal blocks
  cascade-break from mining a frame Oddstone.
- Changed PortalUtils.clearPortalBlocks() from level.setBlock(pos, AIR, 2)
  to level.destroyBlock(pos, false). destroyBlock handles break particles
  and the block's SoundType break sound automatically. false = no item drops.
- Removed manual SoundEvents.GLASS_BREAK from unregisterAndClear() since
  destroyBlock covers it.

### VoxelShape hitbox fix:
- Fixed portal block hitbox being 90 degrees off from rendered model.

### Known issue discovered during testing:
- One-way stickiness mixin only blocks grabs during addBranchingBlocks
  (sideways sticky expansion). It does NOT block the backward sticky
  pull-along inside addBlockLine's internal line-tracing. This means:
  - Slime in front/behind Oddstone in the push direction still pulls it
  - Machine Block in front/behind slime in the push direction still pulls it
  - Sideways grabs are correctly blocked
  Fix requires injecting into addBlockLine's backward walk loop, which
  is a more complex mixin change. Deferred to a future pass.

## [2026-02-12] Oddstone Portals
- Added Oddstone Portal system - overworld-to-overworld teleportation
  - Frame: rectangular ring of Oddstone (minimum 5x5 outer, 3x3 interior)
    with crafted mineral blocks in all 4 corners
  - Corner Address System: the 4 corner blocks form a "frequency" / address
    - Position-sensitive: TL, TR, BR, BL order matters
    - Normalized across viewing direction (front/back produce same address)
    - 14 valid corner types: coal, iron, copper, gold, redstone, lapis,
      diamond, emerald, netherite, quartz, amethyst, raw_iron, raw_copper,
      raw_gold blocks
    - 14^4 = 38,416 possible unique addresses per dimension
  - Activation: ALL Oddstone blocks in the frame must receive redstone signal
  - Deactivation: portal clears and unregisters when frame is invalid
  - Linked Travel: teleports player to partner portal (preserves position)
  - Unlinked Travel: scatter teleport (200-1000 blocks, 5 hearts damage)
  - Per-dimension address spaces using Minecraft SavedData
- Status: Working (see entry above for full details)
